从 A 股 Level-2 逐笔数据里找「正在准备拉升的庄」。V1 已判定为工程失败。这是经四种独立切法与三方异构红队之后收敛的结构。

这套体系保证的不是「能找到 alpha」。它保证的是：当研究结论错了的时候，你能确定错的是研究，不是工程。

V1 的失败，是连这一点都做不到

01 — 共同前提

为什么按知识切，而不是按层切

V1 是分层的：原始 → 因子 → 面板 → 信号 → 回测。结果是 scripts/ 与 src/ 的行数比达到 24:1，684 个顶层脚本里 473 个从未被任何文件 import。

分层不产生模块化。层没有窄接口，于是每个脚本都能伸手进每一层。切法的推导起点不是「系统有哪些功能」，而是：哪些知识一旦泄漏，就会重演已经发生过的事故？

红队修正了一条：深度放错了位置。1,123 次调用不是 1,123 种业务逻辑，而是约 15–20 种访问模式被复制了几十遍。把它们压成一个万能入口后，旁路脚本不会消失——它会变成 raw.read(...).filter(...)，然后每个脚本继续自己做时间过滤、样本过滤、异常日处理。V1 的事故不是只有读取分散，而是「读完之后的语义判断分散」。所以真正需要唯一住所的是：样本宇宙定义（→ 预注册）、异常日处理（→ 缺陷账本）、时段口径与切割规则（→ 事件注册表）、聚合口径（→ 因子）。

02 — 系统结构

十一个模块，一条门禁线，两根跨线的数据箭头

门禁必须硬拒 ⇒ 不能跑在提交者机器上 ⇒ 跑在 CI ⇒ CI 拿不到那 2.585 TB ⇒ 能被机械证明的，只有不碰数据的那半。

03 — 事件层

一次性降维，然后所有研究脱离慢盘

「跟庄」天然是跨日的——吸筹要 20–60 个交易日。算第 T 天的因子需要 T−30…T 天的逐笔数据；在 4 IOPS 的盘上每前进一天就要重读 30 天，全量回测从 15 小时变成 450 小时。而这些数据也摊不平存下来：trades 每天 5,300 万行 × 1122 天 = 594 亿行，加一个 2 字节标记列就是 118 GB，内置盘只有 148 GB。「跨日」同时撞死了 IO 和存储。

三个数字必须先实测，否则事件层是空中楼阁：事件流实际体积（5–8 GB 是估算）· 一次全量提取实际耗时（15 小时是按 89 MB/s 推的）· 「宽而中性」能宽到什么程度（字段越多越不用重跑，但流越大提取越慢）。取 20 个真实交易日、1 个 stream 跑一遍，三个数字全出来。该次扫描须同时产出日级参考层，否则日后要补第二趟。

05 — 收敛点

四种切法独立走到、且经红队存活的机制

01
计划是纯函数产出的值，CI 断言计划而不是墙钟时间
plan() 纯 ⇒ CI 可在不碰任何数据时硬断言：「≤1 趟扫描」「回退 seek = 0」「列子集在下推谓词里」「pre_buffer 恒为 True」。把「CI 拿不到 TB 数据」这个死结解开了一半。红队修正：字节数只做趋势告警，硬门禁只断言计划——pyarrow 没有标准 IO 计数器。
垂直切门禁倒逼
02
缺陷是登记数据，未登记形状硬失败
默认处置是拒绝不是放行。红队修正：IO 阶段只能基于缺陷账本与元数据分支，不能基于研究统计结果分支——不是「完全不分支」；「无 override」会在账本错时无法救火，要有显式的、留痕的救火通道。
细垂直切门禁倒逼
03
参数只有一个来源：预注册
回测签名里没有 stop_loss；研究包内禁数值字面量。红队修正：参数集可以临时创建，但必须内容寻址、不可变、自动进入校正族——否则会出现 tmp_param_set_20260901_7，只是换皮。
细门禁倒逼
04
裁决接口上没有旋钮
没有阈值参数、没有 --relax、没有人工复核入口。「裁决不可解读」靠工具上没有旋钮可拧，不靠纪律。
细垂直切门禁倒逼
05
缺口是一等公民，必须携带归因码
「查不到 = 没有」被禁止。缺口对象是下游纯核入口的必需参数，构造不出它就跑不了因子。接口里不存在 ignore_missing。
细垂直切门禁倒逼
06
结论落在证据包，代码只读
「写回代码注释」被红队证明与收据机制死锁（写回改变 tree_sha ⇒ CI 必然硬拒）。结论存 .lineage/<id>/receipt.json，代码里只留假设 id。
红队
07
不为单适配器的地方引入 port
真实卷与 CI 夹具卷不是两个实现，是同一实现的两个实例——缝在路径参数上。红队修正：「不透明句柄无 .path」在 Python 里只是薄壳且伤害调试；生产接口返回句柄，审计接口可受控解析路径并记录调用者。

06 — 开发方式

一个接口，三个角色

接口先于实现。如果同一个 agent 既定接口又写实现，它会把接口塑造成最容易实现的形状——那正是浅模块的生成机制。

红队否决了四角色流水线（设计→实现→验证→增强→review）。退化路径：接口看起来窄所以人签字 → 实现时发现缺陷太多加 escape hatch → 验证 agent 没看实现正好漏掉它 → 增强 agent 为性能加 force、skip_bad_day → review 只看局部 diff → 两个月后每个假设都有自己的薄 wrapper，684 个脚本换了名字回来。「多 agent 适合并行做粗活，不适合把责任切碎。」

能证明什么，不能证明什么

档内容可被 CI 硬证

而这一档正是 alpha 的所在

最容易被关掉的门禁（红队清单，要预先想好误报时的救火通道）：diff-cover 增量覆盖率 · ruff 复杂度（Polars 表达式天然密集）· 禁私有 import（测试与内部工具首先撞上）· 金标准回归（库版本、浮点、排序稳定性造成「合理变化」）· 血缘校验（hash 含太多环境细节则频繁误报）· 全局批裁决（阻塞节奏后被拆 family 绕过）。

08 — 未决与已知风险

还没定的、还在验的、可能致命的

最大待定

事件的具体定义。落点是事件注册表，目前为空。V1 的微观信号（Build-Up→Cancel→Sweep、冰山补单、假墙撤单等）是候选种子，公式正从 V1 代码中逐条取回——不能凭名字猜。见数据表第五节。

三个数字

事件流实际体积 · 一次全量提取实际耗时 · 「宽而中性」的宽度。20 个交易日、1 个 stream 跑一遍即得，同一趟须顺带产出日级参考层。目前跑不了：机器上有生产作业在读同一块盘，且项目有 kernel panic 前科。

最大风险

不是被攻破，是被绕过。摩擦一旦大到某个程度，研究员会活在沙盒里手抄结论。血缘校验拒得了沙盒产物，拦不住手抄的结论。必须有一条「快速探索也走计划」的低摩擦路径。

判断前置

事件提取器里嵌着「记哪些字段」这个决定，锁在 15 小时才能重跑的位置。缓解：宽而中性，只抽统计量。但「宽」本身有代价——三个数字里的第三个就是它。

公理

列位表无法被证明。表头在摄取时被丢掉，没有真值源；金标准回归也是用这张表生成的，存在循环。已用幸存 7z 的真实 GBK 表头逐字段对照 + V1 设计文档双重印证，但仍须一次性人工校准并留证据。

时间戳

_cont_session_mask（fan-in 56）在 6 位时间戳的天上会静默丢掉整个交易所。正确检测子已验证（str.len_bytes().min()），全语料扫描待空闲窗口执行。范围未知之前，任何走这条原语的模块都是地雷。

存储

先改读取代码（零迁移拿到 row group 裁剪 68.7×；pre_buffer 只在争用时救命，2026-09-02 复测），做完再评估重编码。若重编码必须含 DELTA_BINARY_PACKED——只改 dtype 会让文件变大 7–25%。
