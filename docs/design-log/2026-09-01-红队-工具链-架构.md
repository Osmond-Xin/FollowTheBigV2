# 红队原文 · 对象：红队工具链自身（tools/redteam, 建仓提交后的工作区）· 攻击面：架构

> 归档过程文档。fail-open、REDTEAM_ONLY 可清空、crapkit 失败被吞、文件名拆分、输出目录串扰、manifest 缺失均已按此修正；Lens×Runner 矩阵解耦与对 LLM 评审做多重检验校正未采纳。

该架构实现将门禁聚合逻辑、评审视角（Lens）与执行引擎（Runner）紧耦合在单体脚本中，且核心门禁存在「执行异常时静默放行（Fail-Open）」的不变量破坏漏洞，裁决解析契约缺乏状态完整性与防递归保护。

### 【致命】
* **证据**：`tools/redteam/redteam.sh:38,42,46`（`|| echo "[xxx 失败，见 $2.err]" >> "$2"`）与 `tools/redteam/redteam.sh:65-72`（`v=$(grep '裁决' "$f" | tail -n 1); case "$v" in *不得合并*) BLOCK=1;; esac`）
* **攻击路径**：当外部 CLI（mmx/agy/codex）因网络中断、配额耗尽、子进程 crash 或超时退出时，退出码被 `|| echo` 吞掉，输出文件仅含错误提示。裁决扫描循环无法匹配到 `不得合并`，`BLOCK` 维持 `0`，脚本以退出码 `0` 放行。**在审查基础设施全面瘫痪时，门禁反倒全部自动放行（Fail-Open）**，任何违规改动均可无阻合入。
* **修正**：实施 Fail-Closed 契约。必须对并发子进程退出状态进行聚合校验（非 0 即失败）；裁决判定采用白名单制（必须且仅当所有选定评委均显式输出有效合规的 `裁决：通过` 且无任何执行错误时，才允许 `exit 0`；其余情况包括执行失败、`需改`、`不得合并` 或无裁决，一律置 `BLOCK=1` 并返回非 0 退出码）。

### 【严重】
* **证据**：`tools/redteam/redteam.sh:67-72`（`case "$v" in *不得合并*) BLOCK=1;; esac`）
* **攻击路径**：① **状态机不完整**：规范明确定义裁决三态为 `通过 / 需改 / 不得合并`，但门禁判定逻辑只阻断 `不得合并`。模型判定为 `需改` 时，门禁直接放行，导致「需改」状态形同虚设；② **文本接口缺乏防污染锚定**：使用无正则锚点的 `grep '裁决' | tail -n 1`，若模型在分析正文中引用了他人结论或在最后给出补充说明，会导致判定提取失效或被正文关键字误杀。
* **修正**：补齐裁决状态机：严格仅放行 `Pass`（通过），将 `NeedsRevision`（需改）与 `Blocked`（不得合并）均列为阻断态；使用严格正则接口契约提取（如 `^裁决[:：]\s*(通过|需改|不得合并)\s*$`），未精确命中该格式的输出一律视为无效并阻断。

* **证据**：`tools/redteam/redteam.sh:56-57`（`case $cli in mmx) lens=方法论;; agy) lens=架构;; codex) lens=工程;; esac` 与 `[ "$cli" = mmx ] && inject=1`）
* **攻击路径**：架构上「评审视角（Lens）」与「模型执行器（Runner）」属于两个正交的抽象维度。脚本将两者硬编码为单射绑定，破坏了深模块抽象：无法使用 `agy` 跑全部三个视角，也无法在特定引擎不可用时做降级替换；且词汇表注入逻辑（`inject=1`）直接耦合到特定的 CLI 名字上，而非根据 Lens 属性与 Runner 能力进行声明式配置。
* **修正**：将 Lens 与 Runner 解耦为独立配置或矩阵调度，使调度器（Scheduler）仅面向 `(Lens, Runner)` 组合接口工作；将上下文注入策略（词汇表、活文档路径）提升为 Lens 规范或 Runner 适配器的属性，而非主流程中的 hardcoded switch。

* **证据**：`tools/redteam/redteam.sh:41`（`run_agy() { agy -p "$(cat "$1")" ... --mode plan ... }`）
* **攻击路径**：`agy` 是具备自主工具调用能力的 Agent。当处于 `review` 模式且改动包含 `redteam.sh` 自身时，若受测 Agent 在分析过程中尝试通过执行命令或调用子 Agent 验证脚本，会再度调用 `redteam.sh review`，导致不受控的多级进程 fork 与递归调用死锁。
* **修正**：在入口处建立防重入缝（Re-entrancy Guard）：进入脚本前检测并导出环境变量（如 `_REDTEAM_ACTIVE=1`），在已处于评审上下文时拒绝执行二级并发评审或降级为纯文本静态解析模式。

### 【建议】
* **证据**：`tools/redteam/redteam.sh:84`（`for f in $(... diff --name-only ... | grep '\.py$'); do`）
* **攻击路径**：全文提取逻辑仅限定 `.py` 且硬编码目录 `src tests tools`。若架构变更涉及脚本（`.sh`）、配置（`.toml`、`.yaml`、`.json`）、数据库迁移或根目录结构文件，模型只能看到 diff 片段而看不到文件全貌，导致架构红队对跨文件契约与模块边界的判断出现视野盲区。
* **修正**：移除语言硬编码过滤，依据变更列表（排除二进制与忽略文档后）全量注入全文（按大小阈值截断），确保架构视图完整。

* **证据**：`tools/redteam/redteam.sh:34,58`（`local p="$out/.prompt-$cli.md"` 在 `design` 模式下直接写入 `$REPO/docs/design-log/`）
* **攻击路径**：在 `design` 模式下，中间过程文件 `.prompt-*.md` 和临时生成的 `.json` 直接留在业务文档目录 `docs/design-log/` 下，污染 git 工作区与版本树，且缺少并发隔离与清理 trap。
* **修正**：统一将中间 prompt 和临时序列化文件收拢到 `.redteam/tmp/` 或系统 `mktemp -d` 目录，并在脚本退出时通过 `trap` 统一清理。

裁决：不得合并
