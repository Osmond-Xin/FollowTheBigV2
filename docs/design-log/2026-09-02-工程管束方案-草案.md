# 工程管束方案（草案，待三方红队）

## 0. 背景与目标

V1 的数字：`src` 8,164 行 vs `scripts` 198,279 行（24 : 1），684 个顶层脚本只有 5 个被 import 过，1,279 处 `read_parquet`，113 万词文档，无 CI。
根因不是代码质量，是没有缝：研究即写脚本，事实只能写进文档，文档与代码脱节。

V2 今天的骨架是对的（两个深模块、七道 CI 硬门禁、纯核 / IO 分离），但已露出四个苗头，全在代码之外：
① 16 个未经 review 的探针脚本在 scratchpad；② 三份活文档手改 HTML，同一事实今天写了 5 遍；③ 形状登记分叉（机器账本 6 条 vs HTML 表 12 行）；
④ design-log 两天 22 个文件，研究文件平铺。

**目标**：这一版不得松散、不得不可控。可以接受找不到赚钱的策略，不能接受因工程问题而找不到。
**原则**：每条规则必须有机械执行的门禁，无门禁的规则不算规则；规则的成本必须低于它防的事故，否则会被关掉（V1 门禁就是这样死的）。

## R1 工具与脚本：仓库无 `scripts/`，只有 `tools/`

工具 = 有目标、经 review、有测试、有登记的可执行入口。脚本 = 以上皆无。V2 只允许前者。

- `tools/` 是唯一放可执行入口的目录。每个工具：模块 docstring 首行写**一个**目的；只 import `src` 的公开接口（私有 import 门禁已有）；不含判断逻辑（有第二个调用者的逻辑下沉进 `src`）；至少一条用合成夹具的烟雾测试；经 PR review 合入。
- `tools/README.md` 是工具登记表：名字 · 目的 · 输入 / 输出 · 最近一次用于哪份 design-log。
- scratchpad 探针允许存在但不入库；**跑第二次即必须工具化**；探针的结果只能以账本条目 / 数据表行 / design-log 数字入库，脚本本体不入。
- 门禁（CI）：(a) 仓库出现 `scripts/` `bin/` `notebooks/` 目录即红；(b) `tools/*.py` 文件集合 == README 登记集合；(c) 每个 `tools/*.py` 至少被一条测试引用；(d) `tools/` 单文件 ≤ 300 行。
- 今天 16 个脚本的处置：
  - 工具化 4 个：`tools/audit_preserve.py`（V2 产物 vs V1 preserve 逐 row group 比对 → JSON；合并 compare_v1_v2 / compare2）· `tools/scan_shapes.py`（全语料形状扫描 → TSV，可续跑；time_shape_scan）· `tools/ingest_days.py`（批量摄取驱动：非规范文件名跳过、磁盘余量下限、幂等、逐日日志；合并 ingest_20days / ingest_one_day / ingest_two）· `tools/bench_read.py`（读取耗时基准 → 表；合并 extract_floor / bench_rawstore）。
  - 死在 scratchpad 8 个：bench_decode / bench_decode2 / bench_time / profile_b / resident / disk_probe / time_len / bench_b2（一次性探针，结论已落数据表与实施记录）。

## R2 活文档生成：手改 HTML 被门禁挡住

- 数据表第四节（形状 / 缺陷登记）从 `ledger/*.toml` 生成；词汇表从 `CONTEXT.md` 生成；架构图模块表从各模块 `__init__` 的导出名与 docstring 生成。生成器 `tools/render_docs.py`。
- HTML 里用 `<!-- generated:begin name -->` / `<!-- generated:end -->` 标记生成区块，其余手写区块保留。
- 门禁：CI 重新生成后与仓库 HTML 逐字节 diff，非空即红。
- 过渡顺序：先词汇表（源已是 CONTEXT.md）→ 数据表第四节（需 R3）→ 架构图模块表。

## R3 形状登记单源：一个账本收全部形状

- `ledger/defects.toml` 扩展为全部形状的登记（含良性形状），每条：`id · code · kind(defect|shape) · stream · days|structural · evidence · read_layer_action(patch|gap|none)`。
- `DefectCode` 枚举从账本校验：CI 检查账本 code 集合 ⊆ 代码枚举；账本 **append-only**：已存在条目的 id / code / days 只能增不能删改（与预注册同一纪律，`git diff` 门禁）。
- 今天四个形状入账本：`quote_only`（structural, none）· `empty_file`（待裁决：推荐登记进收据）· `no_trailing_comma`（56 天, none, 注明枚举空值为 null）· `stream_symbol_mismatch`（5 天, gap）。
- `ledger/observed` 观测集合 ⊆ 登记集合的门禁（接手清单第 4 条）一并建。

## R4 设计日志生命周期：写一次，24 小时内落地，定期归档，只留一个活的

- 三类文档：**活文档**（三份 HTML + CONTEXT.md + `docs/STATE.md`，唯一裁决）· **设计日志**（`docs/design-log/`，写一次不改）· **归档**（`docs/archive/YYYY-MM/`）。
- 规则：日志里的每个事实 24 小时内落到活文档 / 账本 / 代码之一，否则视为丢失；事实已落地的日志即可归档。
- `docs/STATE.md` = 唯一的「现在在哪、卡在哪、下一步」页，取代 README 的阶段段；README 只留入口。
- **定时总结与归档**：每周一次（或 design-log 顶层新增满 20 个）由 CI cron 跑 `tools/digest_logs.py`：用 MiniMax（CI 已有 key）读新日志，产出 STATE.md 草案与归档移动，**以 PR 提交，人合并**——模型只起草，不裁决。备选：Claude Code `/schedule` 云端例程；推荐 CI cron（同一门禁体系、无第二套凭证）。
- 门禁：design-log 顶层文件数 ≤ 30 即红（逼归档）；`docs/` 总词数 ≤ 5 万即红（V1 是 113 万）；README 只允许链接活文档。

## R5 包结构：接口 = `__init__`

- 每个模块的公开接口 = `__init__.__all__`；跨模块只能从包顶层 import（import-linter contract）；`types.py` 杂物箱按所属概念归位；单文件 > 400 行由 crapkit ratchet 拦。

## R6 研究阶段：执行器存在前不产脚本

- 验证执行器 + 预注册 + 证据包存在之前，任何研究问题只允许两种产物：`tools/` 里经 review 的工具、以及收据文件；预注册目录与账本共用 append-only 门禁，现在就建。

## 请红队攻击的点

1. 哪条规则的摩擦会大到被关掉？关掉的路径是什么？
2. 门禁能怎么被绕过（改名、放别的目录、生成器本身手改、账本 append-only 被 supersedes 滥用）？
3. 「文档从代码生成」与「活文档是唯一裁决依据」是否循环？谁裁决谁？
4. 定时总结的幻觉与漂移：模型起草 STATE.md 会不会把未裁决的东西写成事实？人签字够不够？
5. 工具化 4 个脚本的边界对不对：哪些逻辑该下沉进 `src`，哪些不该存在？
6. 缺了什么：V1 还有哪种松散方式这里没防？
