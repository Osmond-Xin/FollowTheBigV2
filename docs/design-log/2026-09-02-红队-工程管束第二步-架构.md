总判：该简报看似构建了严密的管束与收据网，实则缝落在错误层级，纯逻辑核与 IO 严重缠绕，收据哈希与实际核心源码及数据脱钩沦为伪承诺，且审计与摄取关键路径上存在多处可致系统崩溃、静默漏扫或穿透核心不变量的致命逻辑缺陷。

### 【致命】

#### 1. `compare_preserve` 存在硬编码类型崩溃、双 null 误判及物理块强绑定导致的假阴性
- **证据**：`src/ftbv2/io/raw/audit.py:48-56`
  ```python
  if ma.num_rows == mb.num_rows and ma.num_row_groups == mb.num_row_groups and schema_equal:
      for i in range(ma.num_row_groups):
          ...
          for c in names:
              if a[c].null_count:
                  nulls[c] = nulls.get(c, 0) + a[c].null_count
              ne = pc.fill_null(pc.invert(pc.equal(pc.fill_null(a[c], ""), b[c])), True)
              if k := (pc.sum(ne).as_py() or 0):
                  differ[c] = differ.get(c, 0) + k
  ```
- **攻击路径**：
  1. **类型崩溃**：`pc.fill_null(a[c], "")` 硬编码了字符串标量 `""`。Parquet 中若包含非字符串列（例如成交价格、成交量、订单序号、纳秒时间戳等整型或浮点型），PyArrow 会在非字符串列上直接抛出 `ArrowTypeError: Value '' does not match type int64`，审计工具在真实行情数据上首个 row group 必崩。
  2. **双 null 误判为不同**：若 A 与 B 在某位置同为 `null`，`pc.fill_null(a[c], "")` 仅对 A 填充 `""`，B 保持 `null`。`pc.equal("", null)` 返回 `null`，`invert` 仍为 `null`，经 `fill_null(..., True)` 被强行判定为不同！两个本应完全相等的空值被持续累加进 `differ`。
  3. **NaN 误判为不同**：浮点列中双方均为 `NaN` 时，底层相等判断返回 false/null，经反转和兜底同样被计入 `differ`。
  4. **物理行组绑定导致假阴性（静默失效）**：前置守卫要求 `ma.num_row_groups == mb.num_row_groups`。Parquet 的 row group 数量仅是编码器的物理分块大小（如写入缓冲配置不同），并非逻辑数据属性。若 V1 与 V2 行组数不同，循环直接跳过，`differ` 为 `{}`，`cells_differ` 输出空字典；更严重的是，一旦行组边界对齐稍有漂移，按 `i` 逐行组对齐比对将导致完全错位的行进行比对，整列全报差异。
- **修正**：
  将比对判据解耦为逻辑核：
  ```python
  # 统一处理双 null 相等及常规值相等
  both_null = pc.and_(pc.is_null(a[c]), pc.is_null(b[c]))
  val_eq = pc.equal(a[c], b[c])
  differ_mask = pc.invert(pc.or_(both_null, val_eq))
  ```
  移除 `num_row_groups` 必须完全相等的硬断言，按逻辑行流式迭代或表级比对，禁止物理分块参数侵入数据逻辑一致性检查。

#### 2. `_load_stream` 纯逻辑核与 IO 倒置，且 0 字节 CSV 穿透“跨流单边缺失”核心不变量
- **证据**：`src/ftbv2/io/raw/ingest.py:83-118` 与 `CONTEXT.md` 三之样本宇宙：“只缺委托、成交之一，或缺行情，仍是残缺归档硬失败。”
  ```python
  def _load_stream(stream: Stream, csvs: list[tuple[str, Path]]) -> ...:
      for symbol, path in csvs:
          data = path.read_bytes()
          if not data:
              empty.append(symbol)
              continue
          n_symbols += 1
          newline = data.find(b"\n")
          if newline < 0 and not data.strip():
              raise RuntimeError(f"CSV 没有表头：{path}")
          header_bytes = (data if newline < 0 else data[:newline]).rstrip(b"\r")
  ```
- **攻击路径**：
  1. **脏空行穿透空表头防御**：若文件并非 0 字节，而是仅包含一个换行符（如 `b"\n"` 或 `b"\r\n"`），`newline = data.find(b"\n") >= 0`，第 91 行条件 `newline < 0` 失效，成功绕过校验！随后 `header_bytes` 变为 `b""`。若该文件排在首位，`header_text` 被赋予 `""`，后续所有正常文件的非空表头全被当作“表头不一致”抛出异常；若排在后面，报表头不一致而非空表头，根因归因被彻底破坏。
  2. **0 字节穿透跨流完整性硬门禁**：若标的 `600001` 在 `orders` 是 0 字节文件，但在 `trades` 和 `xinqing` 中有正常数据。`_load_stream` 简单将其放入 `empty`，`orders` 中不计该标的。三流分别读取完毕后，该标的在 `orders` 缺失但在 `trades` 存在，属于典型的“只缺委托之一”的残缺归档。然而简报中的设计直接给其打上 `IngestReceipt.empty_files` 标签并放行，绕过了 `CONTEXT.md` 规定的残缺归档硬失败底线。
  3. **职责越界**：`_load_stream` 同时处理磁盘字节流读取（IO）与 ASCII 校验、引号禁用、表头一致性、空值规约等核心领域判据，导致 CI 无法在纯内存中脱离物理文件系统进行快速 fuzzing 与变异测试。
- **修正**：
  1. 将解析与校验下沉为纯函数 `parse_csv_bytes(symbol: str, raw: bytes) -> ParseOutcome`，位于 `core` 层；
  2. 修复空判据：`if not data: return EmptySymbol`；若 `not data.strip(): raise RuntimeError(f"CSV 仅含空白字符无有效表头: {path}")`；
  3. 在三流摄取汇合处增加全局跨流不变量强门禁：凡非 `quote_only_symbols` 的标的，三流必须全有或全无；若出现单流 0 字节而另一流有数据，严禁静默吞下，必须触发残缺归档硬失败。

#### 3. `receipt.py` 存在伪可复现性（Fake Reproducibility），指纹与核心源码及实际数据脱钩
- **证据**：`src/ftbv2/io/receipt.py:22-26`
  ```python
  body = {
      "kind": kind, "argv": sys.argv, "tool": str(tool), "tool_sha256": sha256_file(tool),
      "inputs": inputs, "outputs": outputs, "summary": summary,
      "written_at": dt.datetime.now(dt.UTC).isoformat(timespec="seconds"),
  }
  canonical = json.dumps({k: v for k, v in body.items() if k != "written_at"}, ...)
  receipt_id = hashlib.sha256(canonical.encode("utf-8")).hexdigest()[:16]
  ```
  以及 `tools/audit_preserve.py:28`：`inputs = {"a": str(args.a), "b": str(args.b)}`
- **攻击路径**：
  1. **代码修改无法破坏旧收据**：`tool_sha256` 仅计算传入的 `tool`（40 行的 CLI 薄壳 adapter）。若核心逻辑 `src/ftbv2/io/raw/ingest.py` 或 `src/ftbv2/core/...` 发生修改或存在恶性 Bug，只要 adapter 自身代码未变，`tool_sha256` 完全不变！运行后计算出的 `receipt_id` 与历史完全重合，由于 `if not path.exists()` 机制，系统静默保留旧收据，掩盖代码变更事实。这直接违反了 `CONTEXT.md` 中“证据指纹必须绑定源码树与依赖”的定义。
  2. **数据哈希退化为本地路径字符串**：`audit_preserve`、`scan_shapes`、`bench_read` 在调用 `write_receipt` 时，`inputs` 传入的是 `str(args.root)` 等本地路径。本地数据被任意篡改或损坏，只要路径不变，收据签名完全不变；在不同挂载路径或 CI 机器上跑相同数据，仅因路径名不同，又会裂变出全新收据。
  3. **未规范化的 `sys.argv` 击穿确定性**：`sys.argv` 直接参与哈希。相对路径 vs 绝对路径、参数顺序变动（`--root A --scratch B` vs `--scratch B --root A`）会导致语义完全相同的运行产出完全不同的 `receipt_id`。
- **修正**：
  1. `write_receipt` 必须采集全仓源码状态（`git rev-parse HEAD` 或 `src` 的 tree hash 及 dirty 标识）并注入 `body`；
  2. `inputs` 必须是内容寻址哈希（如数据集的 manifest sha256、输入文件的 content sha256），严禁使用未经校验的本地路径字符串；
  3. `canonical` 计算必须剔除原始 `sys.argv`，改为基于解析后规范化的参数字典（canonical sorted key-values）。

#### 4. `check_entrypoints.py` 存在顶层脚本逃逸、脆弱正则与无操作烟雾测试
- **证据**：`tools/check_entrypoints.py:30-45`、`82-88`
  ```python
  def _is_py_entry(text: str) -> bool:
      ...
      for node in ast.walk(tree):
          if isinstance(node, ast.If) and "__main__" in ast.dump(node.test):
              return True

  if kind == "gate" and re.search(r"^\s*from ftbv2|^\s*import ftbv2", text, re.M):
  ```

- **攻击路径**：
  1. **无 `__main__` 的直接执行逃逸**：`_is_py_entry` 只扫 `if __name__ == "__main__"` 和 `CLI_MODULES`（argparse/click/typer）。若在 `src/` 或测试目录下编写一个直接依赖 `sys.argv` 的顶层执行脚本，文件权限 `0644`、无 shebang，AST 检查直接将其判为非入口。此脚本可被 `python -m ...` 或 `python path/to/script.py` 直接调用，门禁完全失明。

- **修正**：
  1. 禁止 `src/` 中出现任何包含可执行顶层语句的非定义模块；
  2. 将 Gate 导入校验替换为 AST 节点分析，遍历 `ast.Import` 和 `ast.ImportFrom`，阻断所有对 `ftbv2` 的静态与动态调用；
  3. 烟雾测试必须在 AST 层面核验包含实际调用语句（如 `subprocess.run` 或运行该工具主函数）。

#### 5. `ingest_days` 异常退出语义破坏批处理完整性，且失败仍颁发收据
- **证据**：`src/ftbv2/io/raw/ingest.py:46-57` 与 `tools/ingest_days.py:27-33`
  ```python
  low = _low_disk(...)
  if low:
      outcomes.append(DayOutcome(day, archive, "stopped_disk", 0.0, error=low))
      break
  ...
  except Exception as exc:
      outcomes.append(DayOutcome(day, archive, "failed", ...))
      if stop_on_error:
          break
  return BatchOutcome(tuple(outcomes), tuple(skipped))
  ```
- **攻击路径**：
  1. **未执行集合静默消失**：若在批量处理第 2 个文件时触发 `stopped_disk` 或发生异常 `break`，后续第 3 至第 N 个归档文件既不在 `outcomes` 中，也不在 `skipped` 中，从调用结果中凭空消失，调度系统无法判定哪些天尚未执行。
  2. **失败批次污染证据库**：即使 `result.ok` 为 `False`（单天失败或磁盘中断），`tools/ingest_days.py` 仍无差别调用 `write_receipt` 生成收据存入 `.lineage/receipts/`。残缺、失败的批次在此被固化为看似合法的收据，破坏了血缘账本的纯洁性。
  3. **中途崩溃无原子保护**：若某天在解包写入时崩溃，未完成的中间产物未被清理，将直接污染 `root`，且占满 `scratch` 导致后续重跑持续触发 `stopped_disk`。
- **修正**：
  1. `BatchOutcome` 增加 `unprocessed: tuple[Path, ...]` 显式记录 `break` 后剩余未处理的归档路径；
  2. 收据写入增加强后置约束：仅在 `result.ok is True` 时签发权威收据；若失败，退出前禁止写入收据或必须写入独立的 `failed_abort` 记录；
  3. `ingest` 必须保证 scratch 的 `finally` 强制清空，写入 `root` 必须采用临时目录落盘后原子重命名（atomic rename）。

#### 6. `scan_shapes.py` 断点续跑粗糙导致整天永久漏扫
- **证据**：`tools/scan_shapes.py:25`
  ```python

  ```
- **攻击路径**：

#### 7. `symbol_mismatches` 的聚合结构与 `only_in` 命名产生语义冲突
- **证据**：`src/ftbv2/io/raw/audit.py:79-82`
  ```python
  common = set.intersection(*sets.values())
  only = {s: tuple(sorted(v - common)) for s, v in sets.items() if v - common}
  ```
- **攻击路径**：
  数据结构命名为 `only_in`（只出现在该流）。在三流比对中，若标的 X 在 `orders` 和 `trades` 均存在，但 `xinqing` 缺失，X 不属于三流交集 `common`。计算 `v - common` 时，X 会同时出现在 `only_in["orders"]` 与 `only_in["trades"]` 中，严重误导使用者的审计排查。
- **修正**：
  改用语义准确的结构体，分别输出 `missing_in: dict[Stream, tuple[str, ...]]`（某流缺失的标的）与严格的单流独有标的。
