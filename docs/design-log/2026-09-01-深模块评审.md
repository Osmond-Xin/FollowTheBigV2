# 深模块评审（codebase-design 视角）

> 过程文档，归档用，不作裁决依据。采纳的条目须先改 `CONTEXT.md` / 架构图 / 数据表。
> **状态（2026-09-01 晚）**：H1–H4 用户全部采纳，已落进 CONTEXT.md → 架构图 → 数据表 → 词汇表；M1–M6、L1–L5 待裁决。
> 评审对象：架构图十个模块 + 词汇表 + 数据表。评审词汇按 `codebase-design` 技能：
> **接口** = 调用者必须知道的一切（签名、不变量、顺序约束、错误模式、必需配置、性能特征）；
> **缝** = 接口所在的位置；**一个适配器 = 假想的缝，两个适配器 = 真缝**；**删除测试** = 删掉它复杂度是消失还是回流。
> 用这个 skill 而不是再跑一轮对抗式评审的理由：三方红队已经攻过一遍并归档；现在缺的不是攻击面，是逐模块检查「接口是否完整、缝是否落在对的位置、纯/IO 两半是否分对」。

## 总判

十个模块的**缝位置基本对**：事件层把门禁线落在「反常观测 → 判断」之间，是全图最强的一刀；
两类存储分开、`force` 删除、参数只来自预注册、缺口为必需参数——都经得起删除测试。
问题集中在两类：**① 最重要的那条缝（事件流）没有接口定义**；**② 词汇表里定义了、图上却没有住所的东西**——按「图上没有的视为不存在」，它们现在不存在。

## 高（结构性缺口，会在第一个假设跑通前撞上）

### H1 事件流 schema 是全系统最重要的接口，但没有拥有者、没有版本

门禁线正好落在事件流上：事件提取写它、因子读它、CI 用 10 KB 合成事件测因子。
因子的调用者「必须知道」的第一件事就是事件有哪些字段、什么语义、什么顺序——这就是接口，而它目前不属于任何模块。

连带一条硬矛盾：**「参数只有一个来源：预注册」** vs **「事件提取在任何预注册之前运行」**。
把 5,300 万行切成几万行必须有切割规则（哪怕是「只留分位数 ≥ p90 的窗」），这些规则是参数，锁在 15 小时重跑的位置，且不可能来自预注册。

**建议**：
- 新增纯模块 **事件注册表**：每种事件的字段、统计量定义、切割规则、版本号。事件提取与因子都只从它 import。
- 事件与因子存储的 `recipe_hash` 必须含注册表版本；预注册必须声明所依赖的事件流版本。
- 词汇表把「提取参数」定义为**独立于预注册的第三类参数**：不可由假设修改、每个假设必须声明、进证据指纹。
- 「事件的具体定义」这个最大待定，落点就是这张注册表，而不是散在数据表第五节的文字里。

### H2 因子状态机缺「日界」——无反常的标的-日不会让状态机前进

事件流只含反常观测。一只票某天没有任何反常 ⇒ 没有事件 ⇒ `step` 不被调用 ⇒
滚动计数类因子（V1 的 `sweep10` 形态）无法衰减，`(标的, 日)` 的输出也没有落点。
缺口对象管的是「数据不存在」，不管「数据存在但安静」——两者必须区分。

**建议**：事件流的接口不变量写明：**每个 (标的, 交易日) 至少一条边界记录**（日界事件），
且流按 (标的, 时间) 有序。因子在日界事件上产出值。这条不写进接口，因子的合成夹具与真实流会在第一天分叉。

### H3 执行模拟与置换检验的价格输入不存在于数据表

`simulate(positions, prices, spec)` 要日级价格、涨跌停状态、停牌、成交量约束；
置换检验要「保持真实波动率与流动性约束」；样本宇宙要 PIT 的主板成员、ST、新股状态。
数据表里两类存储只有「原始层」与「事件流 + 因子值」，**没有日级参考数据**；V1 的 `daily` 库一个字节不带进来。
按「表里没有的视为不存在」，执行模拟现在没有输入。

**建议**：新增派生数据产品 **日级参考层**（可重算、带血缘、几十 MB），列入数据表第一节；
由事件提取**同一趟扫描顺带产出**（否则要第二趟 15 小时）。这也是 F182 教训的落点：涨跌停是标记列，不是删行依据。

### H4 研究 episode / 污染级别 / 解读 / fresh-eyes 对照：词汇表有定义，图上无住所

红队指出「预注册可被逆向成过拟合洗白工具」，词汇表的回答是「对策不在工具里，在 episode 预算与污染级别声明里」。
但 episode 预算、`correction_family_id` 的审计、污染级别字段、解读的存放处、对照结果的存放处，**没有一个出现在模块表里**。

**建议**：并入 **假设与裁决**（纯）——
- episode 账本 append-only，预算计数是纯函数，`run` 前先查预算；
- `Hypothesis` 必填字段：`episode_id` / `correction_family_id` / `contamination_level` / `event_stream_version`；
- 解读与对照结果落 `.lineage/<id>/interpretation.json`，与 `receipt.json` 并列、明确非权威。

## 中（缝放错半边，或接口缺关键约束）

### M1 `plan()` 是收敛点 01 的核心，但没有模块拥有它
CI 要在不碰数据时断言计划 ⇒ `plan` 必须纯 ⇒ 不能藏在 IO 模块「原始层存储」的实现里。
**建议**：原始层存储拆一条内部缝：纯 `plan(request) → Plan`（进纯逻辑核、进 CI）+ IO `execute(plan)`，两者都写进接口。

### M2 验证执行器里的 DAG 解析是纯逻辑，放在 IO 半
「策略假设的验证以其依赖的组合假设已确证为前提」是纯判断。
**建议**：移到假设与裁决：`resolve(dag, verdicts) → 可运行 / 阻塞(原因)`；执行器只做取数、注入、写包。

### M3 附加标签不是机械可算的，与「接口无旋钮」冲突
`abandoned_for_cost` / `not_worth_more_data` 是经济判断，`adjudicate(prereg, stats)` 算不出来。
**建议**：`adjudicate` 只出三态；标签来自 append-only 的**关闭记录**（须 `reason`，机制同 `supersedes`）。这样「无旋钮」仍然成立，判断留痕。

### M4 缺陷账本的救火通道没画
红队要求「显式、留痕的救火通道」，收敛点 02 也接受了，但缺陷账本没有写接口。
**建议**：缺陷账本作为数据产品明确两个入口：`register(defect)` 与 `override(day, defect, reason)`，后者进证据指纹。

### M5 事件提取的统计计算全在 IO 半，只能靠金标准
分位数、持续时长、吃穿档数是逻辑，不是 IO。全部留在线下 ⇒ CI 覆盖率表里的「行为性质 ≈ 65%」再掉一截。
**建议**：内部缝 `scan(day) → batches`（IO）+ `detect(batch, registry) → events`（纯、进 CI）。红队说的「宽而中性」正是 `detect` 的规格。

### M6 `step(state, event)` 只能表达单标的时序，横截面因子无形状
市场相对排名、行业中性化这类因子在这个形状里写不出来。要么明确禁止，要么给出第二个纯形状。
**建议**：接口写明「因子只在单标的时序上定义；截面变换属于组合层 `build`」——一句话即可，但必须写。

## 低（接口细节，第一次写契约测试时补）

- **L1 预注册哈希的对象**：假设是 Python 对象（Q16），哈希源文本还是规范化后的判据值？源文本会因格式化失配，规范值需定义序列化。
- **L2 `put(recipe_hash, table)` 让调用者算哈希**：血缘知识泄漏到两个调用者。改 `put(recipe, table)`，哈希在存储内算。
- **L3 因子值只应是「可重建缓存」类**：秒级可重算的东西不该被收据绑定；证据指纹绑事件流版本 + 因子代码即可。
- **L4 错误模式几乎全部缺失**：`run` 遇上游无定论、`get` 遇缺口、`step` 遇乱序事件、`extract` 遇单读者锁被占——各做什么，接口没说。
- **L5 CLI 入口没画**：`--force` / `--relax` 真正生长的地方是命令行层。图上不画等于「不存在」，但第一天就会有人写 `python -m ... run`。建议在模块表加一行「入口：只暴露 `run` 与 `extract`，无其他参数」。

## 与红队结论的关系

三方红队打的是方法论与工程可行性；本评审只看接口完整性与缝位置，不重复其结论。
两处本评审与红队交叉印证：H4 是红队「预注册洗白」攻击的唯一对策却未落图；M4 是红队「救火通道」修正未落图。
