# 事件流设计收口（2026-09-03，第二次 session）

> 承接 `2026-09-02-事件定义.md`（C 方案）与 `2026-09-03-交接.md` §1.5 的三条待裁。
> 本文只记这一轮定下的东西与理由；定义已写进 CONTEXT.md 第三 / 四 / 六节、architecture.toml、三份 HTML。
> 裁决依据仍是活文档与代码，不是本文。

## 一、定了什么

1. **每类事件各自一张表。** 落盘按类分开，「按 (标的, 时间) 有序的事件流」是**读时归并出来的视图**。
   理由：几何度量逐类不同，合成宽表会让「新增一种事件」变成改 schema，与已定的版本规则
   「新增独立事件类型 = minor，增量追加」冲突，逼出 17 小时全量重跑。分表之后 minor 名副其实，
   注册表每条自带自己的字段表（单一职责），归并只在 `io.derived` 的读接口里实现一次（同一功能一个入口）。

2. **事件三型：区间 / 组 / 时刻。** 注册表每条必须声明。
   C 方案把事件统一成「一段区间」是过度统一——假墙是真区间（墙确实存在着），冰山是**一组**离散委托
   （时间上未必连着，起止只是这组的头尾），隐藏深度是**一个时刻**（无跨度）。
   三型的 `end_time` 含义不同，因子层不得一概当作「事情结束了」。

3. **边界由结构触发，不由时间触发**（用户裁定）。
   开段结段只能被结构事件触发：出现一笔价或量不同的本方委托、方向反转、该笔委托被撤或成交完。
   不得写「隔了 T 久没动静就结段」。
   用户给的理由，原样收进 CONTEXT：**庄家不掐表，是子弹打光了或者量到了。**
   时间阈值既是判断，也不符合被观测对象的行为。
   由此 §五.1「切割参数能否完全不含幅度」化掉了——开组规则是「出现同价同量的第 2 笔」，
   2 是「成组」的词义下限不是阈值；≥ 3 才是判断，归因子层。

4. **回看范围四档：段内 / 日内 / 跨日 / 周期。** 注册表每条必须声明。
   含义是「提取器为了切出一段，最远要往回看到哪」。第四档由用户提出：
   粮食、矿业、能源有需求周期，可跨年，同一行业不同轮长短还不一样——**回看范围写不出一个数**。
   跨日与周期的分界不在看得远不远，在**能不能事先写下一个常数**：写得出 `lookback_days` 就不是周期型。
   这个字段最重要的用途是**重跑代价**：段内 / 日内改了重跑那一天，跨日改了重跑那个窗口，
   周期型改了必须从语料起点全量重跑。

5. **周期型不产出事件行，产出日级参考层的列**（用户采纳推荐）。
   周期尺度的量没有起止、每天都有值，回答的是「现在处于什么处境」而不是「发生了什么」——**处境不是事件**。
   若落成事件行，一个周期就是一条横跨数年的事件，起止要等周期走完才知道，提取器就在等未来，单向流式破掉。
   配套约束：**周期型不许自己判定周期**（「周期在这儿转了」与 p90 是同一类判断，只是尺度大了几年），
   只许记机械可累计的无界量；冷启动缺口在这一档是「够不够未知」，不是「前 N 天不足」。

6. **提取参数只能是拓扑量。** CONTEXT 原写法把「分位点」列为提取参数的例子，与「事件不含判断」直接冲突，删除。
   三条机械判据（维度切分 · 单调同伦 · 不可调出空集）从 `2026-09-02-事件定义.md` §三 收进 CONTEXT 正文。

7. **不得用「反常」定义事件。** 「统计上反常」要有分布做参照，分布是判断。三份活文档里的「反常观测」
   「只回答这是不是统计上反常」全部改掉。

## 二、驱动层怎么跑（注册表声明「要什么」，驱动层决定「怎么跑」）

**外层按日期升序，内层同一天内按标的并行。**

这一段是本轮被用户当场纠正的地方，记下来防止再犯：我一度以「跨日型会强制串行、多流型贵」为由
主张把第一批种子从 5 条砍到 3 条。用户裁定这是**按工程方便砍业务需求**，出发点错了——
不同事件本来就该有不同的提取器，串行的活给串行提取器，并行的活给并行提取器，按需选，不是按贵贱选。

而且我那个前提本身是错的：原始层按天存在 4 IOPS 的机械盘上，**按天推进是被存储布局逼的，不是被跨日依赖逼的**
（顺序扫是最快读法，16.9 h 是读取下界）。既然外层必然按日期走，跨日型要的 T−1 就在手边，
**一分钱额外成本都没有**。一遍扫满足四档回看范围，不需要为并行砍掉任何一类事件。

配套：日级参考层同趟写出。**写**它不需要读昨天（只是当天数据的汇总），**读** T−1 才制造跨日依赖——
两者不可混为一谈。写完 day T 再进 day T+1，跨日型在 T+1 读到的就是完整的 T。

## 三、第一批种子：五条全留，理由换掉

不是「5 条可以接受」，是**每类提取器至少要有一条，否则这套分类没被验证过**：

| 种子 | 验的是哪一类 |
|---|---|
| `DayBoundary` | 系统型（驱动层产生，不走注册表条目） |
| `QuoteThenWithdrawWithinT` | 区间 · 段内 · 单流（orders） |
| `Seq_RepeatedSamePxVol` | 组 · 段内 · 单流（几何度量与上一条完全不同，验「每类一张表」撑不撑得住） |
| `SnapshotRestGeqDisp` | 时刻 · 日内 · 多流对齐（xinqing + trades） |
| `VolClockBar` | 区间 · 跨日 · 读日级参考层 |

第一片要验证的不是「能不能切出一段」，是**注册表接口与驱动层调度这套分类立不立得住**。
只做段内型，第二批一来跨日型就得改接口，那才是真返工。

必测数字因此加一个：**跨日型比段内型贵多少**（决定以后加跨日与周期尺度的量付不付得起）。

## 四、污染级别三档（本轮一并裁定，最后一项待定关闭）

用户采纳推荐标度，按**知道多少**分，不按**是否看过**分（看没看过不可核查，知道什么可以自陈）：
`unaware`（不知道 V1 碰过这个问题）· `knows_prior`（知道 V1 做过，不知结论方向）· `knows_verdict`（知道 V1 的结论）。

用户同时给了定性：**这只是一个参考值**。据此写进 CONTEXT 的约束是——它必填、进证据指纹、可被审计，
但**不进入任何机械判定**：不因污染级别高就降级裁决，也不据它加权或过滤。
这与「盲验降级为对照与声明」同源：污染不可能被机械消除，工具能做的只有把它记下来让人看见。

第一批五条种子的出处都是 V1 失效模式审计，按此标度全部是 `knows_verdict`——写下来比假装干净好。

**CONTEXT 第六节的事件与污染两项待定至此关闭**，剩下的三项（假设的形式结构 / 存储引擎 / 必测数字）
都不挡第一刀。

## 五、本轮踩到的坑

- **词汇门禁不稳定，两种失败模式都见过**：
  ① 同样的文件、内容、基线（origin/main），一次报 8 处定义冲突、下一次通过——语义判定由 MiniMax 出，判定本身有随机性；
  ② 「语义判定失败 ⇒ 不放行。判定输出不是合法 JSON」——模型返回的 JSON 截断或不合法，重跑即过。
  这是一道**硬门禁**，飘意味着 CI 可能红在一个上一次绿过的 commit 上，而且失败信息看不出是真冲突还是抖动。
  尚未修。可能的修法（未做）：判定输出加 schema 校验 + 失败重试 N 次；把「判定不可用」与「判定为冲突」
  分成不同退出码，前者在 CI 里可重试、后者才是真红。
- 它当时抓到的两处是**真问题**，都是我生造了 CONTEXT 里没有的说法：一处把「归因码」写成了别的词，
  一处从 2026-09-02 红队原文里顺手带出了一个 CONTEXT 未定义的量词。两处都已改回定义词。
  （这里不复述那两个词本身——记录也是文本，写出来就是再犯一次，词汇门禁会照样抓。）
  所以「飘」和「误报」是两件事，别因为它飘就不看它报什么。
- `bash tools/gate.sh | tail` 会把退出码吞成 `tail` 的 0——门禁失败也照样往下走。本轮因此
  在门禁红的情况下提交了一次，随后修正。**门禁不许接管道判成败。**
