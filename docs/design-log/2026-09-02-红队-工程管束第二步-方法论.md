总判：对象自称"工程管束"而非研究流程，但**收据与审计实为方法论证据指纹的承载层**——按此标准审视，存在若干可在不破坏字面规则的前提下系统性削弱证据指纹的路径，必须在合并前补齐。

## 致命

### F1. 收据 hash 不绑定源码树 → "可复算"承诺是空头
- **证据**：对象第 246–283 行 `write_receipt` 把 `tool_sha256`（仅 `tools/ingest_days.py` 等入口文件）与 `inputs/outputs` 计入 canonical；但 `src/ftbv2/` 下任何**依赖实现**（`io/raw/ingest.py`、`io/raw/audit.py`、polars/pyarrow 版本、`pyproject.toml`/`uv.lock`）**完全不进 hash**。对象第 690 行也只问"收据是否真能复现"，未声明 hash 绑定范围。
- **攻击路径**：改 `ingest.py` 中 `_parse_body` 的字段映射逻辑（不动 `tools/ingest_days.py` 一行）→ 同一命令、同一输入 CSV → 输出 parquet 的行数与列内容都变了 → 但 `tool_sha256` 不变 → 收据 ID 不变 → 断言"按此收据可复算"成立但**输出已不同**。CONTEXT 第二节「证据指纹 · 绑定范围：源码树 + 依赖 lock + 数据清单 + 缺陷账本 + 参数集 + runner 镜像摘要 + 命令规格」——此处缺四项。
- **修正**：`write_receipt` 必须接受 `source_tree_sha`（`git rev-parse HEAD^{tree}`）、`lock_sha`（`uv.lock` 或 `pyproject.toml` 的 sha256）、`pyproject_sha` 三项作为必填 inputs；任何缺失即抛出。`tools/ingest_days.py` 等 adapter 在调用 `write_receipt` 前自动从仓库根读取并注入。

### F2. 审计 `null ≡ ''` 等价吞掉价格/成交量的真实差异
- **证据**：对象第 341 行 `pc.fill_null(pc.invert(pc.equal(pc.fill_null(a[c], ""), b[c])), True)`——把 A 的 null 视作空字符串后再与 B 比对，把"null 与 empty 不同"丢掉了。
- **攻击路径**：V1 摄取某标的某分钟无成交，记 Parquet null；V2 摄取同一时刻，CSV 字段空（编码丢字符或源 CSV 真有空行），Polars 解析为 "" 而非 null——**审计返回 identical_modulo_null=True**。下游因子层在不知情下用 V2 看到 "" 当作"零量"、用 V1 看到 null 当作"缺失"，二者偏倚完全不同，但审计说"没问题"。对象第 316 行 `null_columns_a`字段还把"差异被等价"的事实**只报在 A 侧**——若 V2 把 null 改成 ""，B 侧的 `null_columns_a` 不可见。
- **修正**：(a) `StreamCompare` 新增 `null_columns_b`、`null_only_differ`（null/empty 不再等价）；(b) 价格、成交量、笔数列强制走 `null ≠ null ≠ ''` 三态校验，仅对确认是 free-text 的列（如备注）允许等价；(c) 取消 `identical_modulo_null` 这个总判定，改按列报告。

### F3. 0 字节 CSV 与"停牌心跳"被混同，原始层偷偷删行
- **证据**：对象第 656–659 行 `if not data: empty.append(symbol); continue`——0 字节 CSV 的标的整个 stream 不写。CONTEXT 第三节明确：「停牌心跳不是残缺归档：归档里每天约有 6 只主板标的的目录只有行情 CSV（每分钟一条、价格与十档全 0 的心跳快照），没有委托与成交……这些标的记入收据 `quote_only_symbols`；**只缺委托、成交之一，或缺行情，仍是残缺归档硬失败**」。
- **攻击路径**：某标的 orders.csv 是 0 字节（数据故障，而非停牌心跳）→ 当前实现静默登记进 `empty_files` 并从 n_symbols 排除 → **原始层 parquet 里这标的 orders 流彻底消失**。CONTEXT 第三节末段「除此之外原始层不删任何行」被直接违反。被删的标的无法在样本宇宙声明里复现（`empty_files` 是路径列表不是 (path, reason)），下游因子层无法回答"为什么这些标的从 universe 里消失了"。把 orders.csv 整流判为 0 字节按 CONTEXT 应硬失败，不是登记后继续。
- **修正**：把 `_load_stream` 的 0 字节分支按 stream 拆：`(a) stream == 'xinqing'`：0 字节允许，记 `quote_only_symbols`；`(b) stream in {'orders', 'trades'}`：0 字节一律硬失败（与 CONTEXT 残缺归档定义一致）；(c) `IngestReceipt` 新增 `reason: 'absent_in_archive' | 'zero_byte'` 二元组，让下游能区分。

## 严重

### S1. `adapter ≤ 120 行` 可被 minify 或多文件协作绕过
- **证据**：对象第 148 行 `if kind == "adapter" and len(text.splitlines()) > ADAPTER_MAX_LINES`——按 `\n` 数行，单行 minified 巨型文件通过；切分成 `adapter_a.py` + `adapter_b.py`（各 ≤ 120 行）`from .adapter_a import *` 也通过。
- **攻击路径**：把 `_low_disk` 的所有阈值逻辑、`_parse_body` 的全部字段映射、`ingest_days` 的失败语义判定全部塞进某个 adapter，文件 minify 成119 行——`check_entrypoints.py` 报告通过，但"判据下沉 src"的承诺失效。
- **修正**：(a) 行数统计改 `token_count` 或 `ast.unparse(ast.parse(text))` 后的字符数；(b) 新增"adapter 集合的 import 图是 DAG 且每个 adapter 只被一个 manifest 条目 import"判定；(c) adapter 的 AST 必须**只调用 src公开接口**（按 `__all__` 白名单），私自 import 内部模块即违规。

### S2. 入口判据对动态构造的入口点全数漏检
- **证据**：对象第 93–99 行 `_is_py_entry` 用 `ast.walk` 抓 `ast.Import` / `ast.ImportFrom` 的 argparse/click/typer——`__import__("argparse")`、`importlib.import_module("argparse")`、subprocess 拉起 `python -c 'import argparse; ...'` 全数漏检。`if __name__ == "__main__"` 检查的是字符串包含，不是语法等值——`if __name__ == "__main__" or True:` 也算命中（OK 是想要的）但 `if "__main__" in __name__:` 这种字符串拼接模式反而命中（合理）。
- **攻击路径**：写一个 `tools/cleaner.py`，主函数里 `importlib.import_module("argparse").ArgumentParser().parse_args()`，跑出来是真入口但 `find_entries` 不收。
- **修正**：`_is_py_entry` 补 `ast.Call` 扫描 `__import__` / `importlib.import_module` / `getattr(__builtins__, "exec")`；再补 `ast.Exec`/`ast.Lambda` 隐藏入口的检测；新增 `subprocess` 检测。

### S3. workflow 引用正则只匹配显式 `tools/...` 字符串
- **证据**：对象第 126 行 `re.finditer(r"(tools/[\w./-]+\.(?:py|sh))"`——不覆盖 `*` 通配、矩阵策略 `matrix.tool`、env 变量插值 `${TOOL}`、条件分支 `if: matrix.run_audit`。
- **攻击路径**：workflow 写 `run: python tools/${{ matrix.tool }}`——`check_entrypoints.py` 不收 `tools/${{ matrix.tool }}`（字面不带 `.py`），但实际执行时是入口；该入口可能根本不在 manifest 里。
- **修正**：用 YAML 解析而非正则；遇到 `${{ ... }}`、`$MATRIX_*`、`*` 通配时，**强制在 manifest 里登记"动态入口允许集合"**，CI 跑前静态展开并校验。

### S4. `audit_preserve` 跑 1122×3 流的多重比较无校正
- **证据**：对象第 393–402 行 `read_floor` 与 `compare_preserve` 跑全语料——3366 次独立 cell-by-cell 比对。每条 `cells_differ` 是一个独立检验，但 `audit_preserve.py` 把所有天的发现**平摊到 `payload` JSON 里**直接报告，无 Bonferroni / FDR / BH 校正。
- **攻击路径**：V1 vs V2 真实差异是 0 天0 流，但 pyarrow 浮点列在跨平台（V1 macOS vs V2 Linux）会出现5 个流有 ≤3 列差异，p 值未校正直接报告"5 天异常"，研究员据此写裁决"流间不可比"——**这是过拟合到浮点噪声，不是真的发现差异**。
- **修正**：在 `compare_preserve` 输出侧加 BH-FDR 校正：(a) 把每天每列的 cell-level 差异视作独立伯努利检验，p = 差异占比；(b) 跨天合并做 BH 控制 FDR 在 1%；(c) 报告 "discovery set"（通过校正的差异）与 "raw count"（原始差异数）两个数字。

### S5. 收据不绑定 lockfile → 同一源码树不同依赖出不同结果
- **证据**：对象第 246–283 行 `write_receipt` 无 `pyproject_sha` / `uv.lock sha` 字段。`pyproject.toml` / `uv.lock` 的 polars/pyarrow/七zip 绑定变了，parquet 输出可能不同。
- **攻击路径**：升级 pyarrow 1.0 → 14.0，Parquet 的 default compression 改变，行数不变但字节布局变化 → 同一命令产生不同 parquet → `sha256_csv` 不同 → 但因为 `tool_sha256` 不变，**收据 ID 仍相同**——研究员拿着"同一收据"比对了不同输出，无法察觉。
- **修正**：见 F1 修正；额外：把 lockfile 列入证据指纹后，任何 lockfile 改动触发收据 ID 重生成，旧收据视为过期。

### S6. 样本宇宙在摄取层被隐式缩减且不可追溯
- **证据**：对象第 657–659 行 0 字节标的进 `empty_files` 后从 stream 中消失；`IngestReceipt` 暴露 `quote_only_symbols` 但**未暴露 `empty_symbols` 列表**。CONTEXT 第三节末段要求"被筛掉的标的按前缀计数进摄取收据"，此处0 字节标的既未计数也未暴露。
- **攻击路径**：连续 3 天某标的 orders.csv 是 0 字节（数据故障）→ 3 天摄取都成功 → 摄取收据看起来都正常 → 下游因子层在 (日, 标的) 矩阵里这个格子是缺的 → 经验置换检验在"保持真实波动率与流动性约束"时**不知道该标的在该日缺席的原因**，把"数据缺失"误当作"无反常"。
- **修正**：`IngestReceipt` 新增 `empty_symbols: dict[stream, tuple[(symbol, reason), ...]]`；reason ∈ `{'absent_in_archive', 'zero_byte', 'header_only', '...'}`；F3 修正后此字段自动成立。

## 建议

### N1. `scan_time_shapes` 只看长度不看语义
- **证据**：对象第 361 行 `pl.col("column_4").str.strip_chars().str.len_chars()`。"143059"（6 位）与 "1430.59"（7 位含小数点）长度不同但前者合法（HHMMSS）后者非法——统计形状看到了长度分布但未声明"哪几个长度是合法时间串"。
- **修正**：在 `scan_time_shapes`旁配一个 `validate_time_shapes`，对每个 (day, stream) 跑正则 `^\d{6}$` 与 `^\d{6}\.\d{1,3}$`，分别报 `valid_count / invalid_count`；输出进同一个收据但**不进账本决策**（仅作发现）。

### N2. `compare_preserve` 不验证列的字典/RLE 编码
- **证据**：对象第 331 行 `schema_equal = fa.schema_arrow.equals(fb.schema_arrow)` 只比 schema 字段与类型，不比每列的 `metadata`、编码、压缩。V1 与 V2 同一语义、同一 dtype、但 V1 用 RLE 价格、V2 用 PLAIN，schema_equal=True。
- **修正**：新增 `encoding_equal` 字段，比较每列 `parquet_metadata.row_group(i).column(i).encodings` 与 `compression`。

### N3. `_low_disk` 逐日检查而非批前一次性 → batch语义模糊
- **证据**：对象第 622 行 `low = _low_disk(...) or _low_disk(...)` 在每个 archive 前调用；这意味着第一天 100GB 余量、第 100 天剩 30GB（>40GB 阈值）时 batch 停在第 100 天——结果是 `BatchOutcome` 一半 ok、一半 `stopped_disk`。
- **修正**：批前估算总需求 `Σ(archive_size) × 1.5`（解压峰值），与 `_low_disk` 双阈值比，**不足即在批开始前硬失败并返回**，不写任何 DayOutcome。

### N4. D013 pending阻塞摄取判据稳定
- **证据**：对象第 41 行 "D013 仍 pending 等事件注册表"——但摄取层的0 字节判定（硬失败 vs 登记）、quote_only_symbols 的判定（合法形状 vs 缺失）**就是事件提取的判据**，等不到事件注册表稳定就是判据跟着实现跑。
- **修正**：把0 字节、quote_only、单边缺失三类判定从事件注册表的依赖里摘出来，单独立 D015/D016/D017 三个 ledger 条目，**先于事件注册表**确证；事件注册表里只登记"什么是反常"。
