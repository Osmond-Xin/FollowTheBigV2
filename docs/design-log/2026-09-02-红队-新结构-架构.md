本简报在数据物理层面上无法在 A 股上交所标的落地，新增防线完全由不可执行的字符串门面构成，三条反常结构在微观结构中均会发生 1–2 个数量级的严重爆量，是一份披着结构外衣却无法机械判定的伪降维方案。

### 【致命】

#### 1. 上交所主板逐笔数据缺失委托成交关联字段，导致 `RefillAfterFill` 物理不可判定
- **证据**：
  待审对象一 · 2. RefillAfterFill：“跨行结构关系（三个角色）：被成交耗尽的本方委托 · 耗尽它的成交 · 同价同量的补单；开段：某 (side, price) 上一笔委托被成交耗尽后，同 (price, vol) 的新委托出现”。
  CONTEXT.md 第三节 & 六节：“标的宇宙（沿用主板 `000/001/002/003/600/601/603/605`）”。
- **攻击路径**：
  全市场约一半主板标的为上交所（600/601/603/605）。深交所 Level-2 逐笔成交包含 `BidApplSeqNum` 与 `OfferApplSeqNum`，但上交所 Level-2 逐笔成交（trades）**根本不提供买卖双方的原始委托订单号**，仅有成交序号、成交价量与方向标志。在没有订单号穿透关联的物理限制下，提取器在原始数据流中根本无法得知“某笔成交究竟耗尽了哪一笔本方委托”。若要在上交所强行计算，提取器必须在内部维护完整的撮合回放引擎，但上交所未公开集合竞价撮合与复杂市价单撤单撮合细节，无歧义的逐笔精确匹配在底层数据上是不可能的。该结构在上交所标的上直接在物理层面破产。
- **修正**：
  在 `EventSpec` 接口中显式增加数据源能力约束字段 `supported_exchanges: tuple[Literal['SZSE', 'SSE'], ...]`。若无法在全市场运行，必须将适用范围声明为仅限 `SZSE`，在上交所标的上直接输出显式缺口归因码（`Gap(reason='unsupported_sse_trade_feed')`）；若要在全市场通用，必须将“单笔委托耗尽”重构为“档位物理深度归零”，不再追踪单笔 Order ID 的生命周期。

#### 2. 新增防线均为查非空的纯字符串门面，违反「事实单源」原则并欺骗 CI
- **证据**：
  待审对象二：
  ```python
  @dataclass(frozen=True)
  class Relation:
      roles: tuple[str, ...]      # 少于 2 个即构造失败：单行过滤只说得出一个角色
      invariant: str              # 角色之间必须成立的关系（署名字段，机器只查非空）
  ```
  CONTEXT.md 第四节：「事实单源」——“判据：一个事实如果能被代码执行出来，就不得被文档声明。”
- **攻击路径**：
  `Relation.roles` 仅校验元组长度，传入 `("role1", "role2")` 两个无语义字符串即可通过；`Relation.invariant` 明文注明“机器只查非空”，传入 `"any string"` 或 `"dummy"` 即可绕过。这与上一版被退回的“查 docstring 是否包含某句话”完全同构，属于典型的安全错觉。机器对这些角色究竟是什么类型、它们之间存在何种时序断言一无所知，不变量完全无法被代码执行与验证，却被包装成“结构性防线”试图骗过 CI。
- **修正**：
  废弃字符串形式的不变量描述。将 `Relation` 改为强类型可执行断言契约：
  ```python
  @dataclass(frozen=True)
  class Relation:
      roles: tuple[type[EventRole], type[EventRole], ...]
      assert_invariant: Callable[[tuple[EventRole, ...]], bool]
  ```
  在 CI 中引入基于属性的合成测试（Property-based testing），强制验证当注入破坏时序或数量关系的对抗样本时，`assert_invariant` 必须返回 `False` 或抛出指定异常。

#### 3. 三条反常结构（1/2/3）密度全面击穿，高于目标 1–2 个数量级，摧毁全量重跑与因子层
- **证据**：
  项目约束：“目标密度：事件层要把 5300 万行/天坍缩成「几万条/天」（全部标的合计），即约 10–30 条 / (标的·日)。”
  待审对象一中 1 (假墙), 2 (冰山), 3 (隐藏深度) 的判定逻辑。
- **攻击路径**（以一只中等活跃主板标的日均 orders 3–5 万笔、trades 2–3 万笔、快照 4800 帧实测估算）：
  - **假墙 (`LevelBuildThenVanish`)**：盘口深档（买五至买十、卖五至卖十）被量化做市与网格算法高频挂撤。由于远离买一卖一，90% 以上的远端挂撤天然一笔都不成交。全天仅深档无成交挂撤就会切出 **500–1,500 条**事件；
  - **冰山 (`RefillAfterFill`)**：A 股市场算法拆单与散户普遍采用默认固定手数（如 10 手、100 手）。全天 TWAP 算法在多档位均匀补单，加之整数关口被动撮合后新挂单涌入，满足“成交后出现同量新单”的事件全天达 **200–800 条**；
  - **隐藏深度 (`FillExceedsDisplayed`)**：盘口激烈博弈时，买一卖一在 3 秒快照间隙被吃掉几百手，做市商或追随者在 3 秒内迅速重新挂入单子。下一帧快照该档位依然存活。全天活跃时段此类“吃光后补单（Replenishment）”至少发生 **150–400 次**；
  - **合计**：单标的·日事件量达 **850–2,700 条**，超出 10–30 条目标上限近 **100 倍**。全市场 3000 只标的一天产生数百万条事件，不仅无法降维，更将导致 15 小时全量提取 IO 阻塞，彻底粉碎因子层秒级重跑的架构基石。
- **修正**（严格不引入分位、阈值、幅度倍数与时间上界的纯结构性收窄）：
  - **假墙收窄（盘口前沿拓扑约束）**：强制增加结构不变量——“该档位在建立时必须曾处于最优买/卖价（Touch，即 `ticks_to_touch == 0`），且在其存续期间，盘口价差未曾向不利方向扩大”。直接剔除所有深档挂撤噪声；
  - **冰山收窄（档位耗尽瞬时拓扑约束）**：强制增加结构不变量——“补单必须在上一笔委托耗尽导致该档位从公开盘口完全消失（Depleted）的下一笔委托中立即恢复该档位，且该档位在两笔委托之间不得存在任何其他价位的新增委托插入”；
  - **隐藏深度收窄（零新增挂单拓扑约束）**：强制增加结构不变量——“两帧快照之间，trades 在该 (side, price) 上的累计成交量 ≥ 前一帧 displayed_vol，**且两帧快照之间 orders 流中该 (side, price) 的新增委托笔数严格为 0（零流入）**”。彻底在物理结构上剔除 3 秒内新挂单补充的假隐藏。

### 【严重】

#### 4. `FillExceedsDisplayed` 忽视 3 秒穿档与回档，将微观流动性补充误判为隐藏深度
- **证据**：
  待审对象一 · 3. FillExceedsDisplayed：“跨行结构关系（三个角色）：前一帧快照在该档的展示量 · 两帧之间在该档的成交 · 后一帧快照上该档仍然存在；不变量：成交量 ≥ 前一帧的展示量，而该档位在后一帧仍然活着。”
- **攻击路径**：
  A 股 Level-2 快照周期为 3 秒。在这 3 秒内，高频价格完全可能经历“穿档再反弹”：t0 时刻卖一 10.00 元展示 100 手；t0+1s 市价大单击穿 10.00 元并推升至 10.02 元；t0+2s 卖方新订单大批涌入，将价格重新打压回 10.00 元（挂出 80 手）；t1 (t0+3s) 快照到达，卖一显示为 10.00 元（80 手）。
  依照对象的纯几何定义：两帧之间 10.00 元成交 100 手（≥ 前一帧展示量），且后一帧该档依然存在。系统将机械判定此为“隐藏深度”。这实际上是极为普通的价格穿透与流动性再铺设，根本不存在暗单幸存。
- **修正**：
  必须基于订单簿（OrderBook）的单调状态定义幸存：要求在两帧之间该档位发生耗尽性成交后，该价位在订单簿内部的订单链表中依然存在未成交的初始订单，或者如前述第 3 条修正，要求两帧之间 orders 流中该档位净新增委托为零。

#### 5. `Density` 将运行时实测度量硬编码在纯逻辑核中，造成架构死锁
- **证据**：
  待审对象二：
  ```python
  @dataclass(frozen=True)
  class Density:
      rows_per_symbol_day: float  # 必须 > 0
      collapse_ratio: float       # 必须 > 1，否则「这条提取器没有降维」
      receipt: str                # 必须非空：入库数字一律带血缘
  # EventSpec.density: Density | None = None
  ```
- **攻击路径**：
  `Density` 本质上是一个依赖于样本宇宙、市场波动周期与执行环境的经验测量值。将其作为纯逻辑核中静态对象 `EventSpec` 的属性，导致死锁：静态代码中它只能是 `None`；若要求“全量提取前必须通过 `require_density()` 检查”，则必须有人在跑完小样本后反向修改代码文件填入数值。这直接违反了 CONTEXT.md 第二节“代码保持只读，严禁运行时反向修改源码……写回会立刻改变 `tree_sha`，与收据机制死锁”。此外，单一样本上测出的标量 float 根本无法代表极端行情下的全域密度。
- **修正**：
  将 `Density` 彻底移出 `EventSpec`。纯逻辑核只声明 `TargetDensityRange(min_ratio, max_rows)`。实测密度作为**全量提取前置检查任务（Pre-flight Profiler）**产出的独立收据（`density_receipt.json`）。由任务编排驱动层在读取该收据并校验满足目标范围后，方可下发 15 小时全量任务，严禁将测量数据反向写回逻辑代码。

#### 6. 未定义集合竞价、涨跌停与停牌心跳的错误模式与时序边界
- **证据**：
  待审对象一中 1、2、3 条未声明交易时钟过滤条件；
  CONTEXT.md 第三节：“停牌心跳不是残缺归档……三 stream 分别计标的，这些标的记入收据 quote_only_symbols；每个 (标的, 交易日) 至少一条日界事件”。
- **攻击路径**：
  - **集合竞价（09:15–09:20）**：该时段允许撤单且撮合未开始（trades 绝对为空）。主力大额诱多诱空挂单后撤销，完全符合“建档、撤回零、期间 0 成交”，直接引发假墙结构海量误报；
  - **停牌心跳（`quote_only_symbols`）**：每日约 6 只标的只有心跳快照，无 orders 和 trades 流。提取器若默认执行三流或双流对齐，将因等待 trades 到达而导致时间轴死锁，或抛出未捕获的流中断异常，无法生成每日必需的日界事件；
  - **涨跌停封板**：涨停板买一封单数十万手，后排排队撤单且 0 成交，病态触发大量假墙；开板瞬间巨额成交与排队单并存，导致隐藏深度连续误判。
- **修正**：
  在 `EventSpec` 接口中显式增加交易时段与异常流配置：
  - 增加 `applicable_phases: tuple[TradingPhase, ...]`，默认排除 `CALL_AUCTION`（集合竞价）；
  - 明确定义在遭遇 `quote_only_symbols` 或无成交日时的纯逻辑短路规则：直接返回空事件流，驱动层仅产出日界事件（Day-boundary event），保证状态机正常前移。

#### 7. `VolClockBar` 缺少除权除息与冷启动处理，跨日均值刻度存在结构性失真
- **证据**：
  待审对象一 · 4. VolClockBar：“刻度：tick_volume = daily_ref.volume 的 20 日均值 ÷ bars_per_day，bars_per_day = 48。日均值取自 T−1 及以前，绝不含当日自身。”
- **攻击路径**：
  - **除权除息跳变**：若标的在 T 日进行高送转（如 10 送 10）或配股，T 日的实际成交股数（Volume）在同等资金交易下将天然翻倍。由于使用的是 T−1 以前未经复权处理的原始成交量均值，T 日的 `tick_volume` 刻度将严重偏小，导致 T 日切出的 bar 数量暴增至近 100 根，彻底破坏日均 48 根 bar 的稳态假设；
  - **冷启动缺口**：新股上市未满 20 日，或标的停牌数月后复牌，`daily_ref.volume` 无法提供 20 个历史有效日，对象完全没有定义降级或缺口处理规则。
- **修正**：
  - 将成交量刻度改为**成交金额刻度**（`daily_ref.amount / bars_per_day`），成交金额天然不受送转股除权影响，具备跨日平稳性；
  - 接口显式声明冷启动缺口模式：若有效历史日 `< lookback_days`，必须显式抛出 `Gap(reason='insufficient_lookback_history')`，严禁静默填 0 或随意缩减窗口天数。

### 【建议】

#### 8. “从盘口消失”语义模糊，未隔离十档截断与真实撤销
- **证据**：
  待审对象一 · 1. LevelBuildThenVanish：“结段：该档位深度回到零并从盘口消失。”
- **攻击路径**：
  价格单边变动会导致某个挂单档位从买十跌出至买十一，在十档快照中表现为“消失”，但实际挂单仍在撮合队列中。若提取器依赖快照判定消失，会将盘口推移误判为假墙；若依赖 orders，必须明确说明是否维护十档外的全深度队列。
- **修正**：
  在几何度量中增加结构枚举：`vanish_reason: Literal['cancelled_to_zero', 'shifted_out_of_depth']`，强制要求结段必须由 orders 流中的撤单事件闭合，不得仅依据快照截断判定。

#### 9. 多流对齐缺少微观时序等待水位（Watermark）接口规范
- **证据**：
  待审对象一中 1、2 声明读取 `orders + trades`，属于“日内”回看范围。
- **攻击路径**：
  在物理机器上，orders 与 trades 是两个独立的流，到达提取器时必然存在微秒级乱序。若接口未声明乱序容忍水位，流式合并可能在成交记录尚未到达前误判补单时序，破坏“补单必须发生在成交之后”的不变量。
- **修正**：
  在事件注册表的数据依赖声明中增加 `max_alignment_skew_ms: int`，明确多流合并时的重排序水位窗口，确保因果顺序在进入提取逻辑前已完全确定。

裁决：不得合并
