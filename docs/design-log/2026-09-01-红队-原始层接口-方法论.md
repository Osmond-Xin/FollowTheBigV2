总判：接口在「原始层只读、dtype 还原逐位复刻 V1、缺陷账本作为登记数据」三处扎实，但 ingest 按 MAIN_PREFIXES 永久删行直接撞上「任何产物不得在未声明样本宇宙前删除行」这条硬约束；其余六处「证据指纹绑定账本 / 数值还原边界表 / 会话边界 / 账本 append-only / 宇宙随时间漂移 / 测试夹具锁账本」每一条都是研究纪律上的结构性缺陷，单独一项就能被一个 sprint 攻穿。

## 致命

**1. ingest 按 MAIN_PREFIXES 永久删行，违反样本宇宙属于预注册**
- 证据：`src/ftbv2/io/raw/ingest.py:486-487`「宇宙筛选按前缀（默认 MAIN_PREFIXES），被丢弃的按前缀计数进 receipt——丢弃是决策（Q15），不是静默」；`tests/raw/test_ingest.py:953` 断言 `r.dropped_by_prefix == {"300": 1}`；`src/ftbv2/core/raw/schema.py:47` 常量定义
- 攻击路径：研究者发起 ChiNext 假设预注册，Universe={300xxx}，但 7z 里的 300xxx 行已在 ingest 时被永久删除。预注册阶段才会发现「数据根本没有保留」→ 必须重新摄取整批归档（此时归档已下线或已删除）→ sprint 卡死。即使归档仍在，原层已是「删除过」的副本，再摄取只能验证「两次删除得到同一个空集」，无法补救历史。即使把 `prefixes` 当成显式参数也无济于事：默认值 + 「默认即可」注释已经把意图钉死。
- 修正：删除 ingest 的前缀筛选；`ingest()` 必须保留全部行（连同 `_symbol` 原值），无 `prefixes` 入参；`MAIN_PREFIXES` 常量下沉到 ReadRequest 或事件提取扫描参数，由预注册持有并作为 hypothesis 参数传入；raw 层接口的 `MAIN_PREFIXES` 只留作研发期「测试用筛子」，摄取路径绝不调用。

## 严重

**2. 缺陷账本未绑入证据指纹，账本变动让同一份原始数据产出不同 ReadResult 且 ReadStats 不告知**
- 证据：`src/ftbv2/core/raw/types.py:269-286` `StreamReceipt` / `IngestReceipt` 字段无 `ledger_sha256`；`src/ftbv2/io/raw/ingest.py:489-509` manifest 不携带读取时的账本摘要；`tests/raw/conftest.py:574-586` 也未注入账本 hash 断言
- 攻击路径：day N 录入新 defect 后，对 day N 之前的数据重跑「时间 6 位」检测：旧产出 0 个 null，新产出 N 个 null。同一份 7z 在不同时间产出不同 ReadResult，但 ReadStats 不告诉调用方「我用的账本是哪个」。下游因子看到的「空值率漂移」无法归因 → 任何观察性研究都会得到「数据在演化」的假象；预注册事后无法复现判据。
- 修正：`DefectLedger` 加 `content_sha256()`；`ScanPlan` 与 `ReadResult` 携带 `ledger_sha256`；`IngestReceipt` 写入 manifest 时固化 `ingest_time_ledger_sha256`；契约测试断言「两次读取 ledger_sha 不同时 results 不应被缓存复用」。

**3. Float64 中转的边界表只给例子、不给判据，UINT64 哨兵「→ null」与「精度丢失 → null」混在同一表**
- 证据：`src/ftbv2/core/raw/decode.py:357-372` 边界表无判定函数；`tests/raw/test_store.py:773-778` 只验证 7 个固定输入
- 攻击路径：交易所某天出现合法但贴近 2^53 的成交编号（9.0e15 量级），Float64 中转会丢精度并静默给 null。该 null 与「真实空值」在事件流里不可区分（同 kind 同列）。研究者把它解读成「编号空缺 = 异常事件」构造「稀疏编号」因子 → 该因子在样本外的标的里虚高，整套信号被污染。V1 路径是「哨兵 null + 精度丢失 null混合」，V2 复刻同一行为 =同一陷阱。
- 修正：边界表每条规则必须给出**判定函数**（如 `abs(int(float(s))) != abs(int(s)) → null`），不止举例；UINT64 哨兵应作为独立 `DefectCode`（如 `uint64_sentinel`）登记而非埋进 dtype 还原；该条进缺陷账本并显式声明「出现即 null，否则走 round-trip 检测，不一致进 null」；独立暴露 `n_roundtrip_failed` 计数进 ReadStats。

**4. CONTINUOUS 静默剔除开盘与收盘集合竞价，「庄」在这两个时段的策略本身就是研究对象**
- 证据：`src/ftbv2/core/raw/types.py:151-155` `CONTINUOUS = (Window(34200000, 41400000), Window(46800000, 52620000))`，注释无剔除说明；`src/ftbv2/core/raw/schema.py:50-53` `AM_START_MS` / `PM_END_MS` 注释把14:57 标为「连续竞价 PM 结束」但未说为何结束在 14:57
- 攻击路径：研究者 A 用 `windows=None` 默认取得全天数据；研究者 B 用 `windows=CONTINUOUS` 取得连续竞价数据。两者无接口强制差异，但样本不同。任何「开盘集合竞价大量撤单」「收盘集合竞价虚假撮合」相关因子假设，A 版本里事件数 10×，B 版本里为 0。预注册预算无法对齐 →假设空间被静默切两半。CONTEXT 第三节事件流要求「安静与缺口是两种信息」，而此处「call auction 安静」与「call auction 缺口」在接口层被合并成同一种「剔除」。
- 修正：`CONTINUOUS` 改名 `CONTINUOUS_AUCTION_EXCLUDED` 或在 docstring 显式写「已剔除 9:15-9:30 开盘集合竞价与 14:57-15:00 收盘集合竞价」；`ScanPlan` 携带 `windows_hash`；契约测试断言「windows=CONTINUOUS 与 windows=全连续（含 call auction）的结果按事件维度可证差」。

**5. 缺陷账本可改写，违反 append-only 纪律；旧 Run 的归因在结论里仍写旧账本**
- 证据：`src/ftbv2/core/raw/ledger.py:339-353` `parse_ledger` 无版本、无 `supersedes`；`ledger/defects.toml` 在 git 历史中可任意修改；与预注册 append-only 纪律不接
- 攻击路径：发现某 defect 登记错误（如 `time_6digit` 误填了某天），研究者直接编辑 TOML；旧 Run 的归因在结论里仍写「time_6digit 补丁」，但 ledger 已经改了。证据指纹比对时找不到当时的 ledger 内容，无法重建结论。
- 修正：ledger 增加 `[version]` 段，每条 `[[defect]]` 带 `id` 与 `supersedes`；CI 校验旧条目 `code/stream/days/note` 在 git history 中不可变更（与预注册同纪律）；`parse_ledger` 拒收 `supersedes` 链断裂的条目。

**6. MAIN_PREFIXES 写死为常量，宇宙按代码前缀划线但上市/退市/ST 切换是动态事件**
- 证据：`src/ftbv2/core/raw/schema.py:47` `MAIN_PREFIXES: tuple[str, ...] = ("000", "001", "002", "003", "600", "601", "603", "605")`；`src/ftbv2/core/raw/types.py` 无任何日期相关字段
- 攻击路径：2024 年某 ST 股退市，2025 年同代码被新 IPO 公司复用；研究「2024 vs 2025」时，前缀字典是同一份，但样本宇宙里的股票完全不同。任何基于「代码前缀 = 主板」的事后切片都隐含错位。
- 修正：MAIN_PREFIXES 不应是常量；应是 (date, prefix) 列表或由日级参考层持有「该日是否主板成员」PIT 表；本期若不做，至少在 `MAIN_PREFIXES` 上挂 `effective_from: date` 字段，并在每次「前缀变更」时按日期切分。

**7. 测试夹具的 `LEDGER_TOML` 锁死全部 defects，无法对单个 defect 跑契约测试**
- 证据：`tests/raw/conftest.py:574-586` `LEDGER_TOML` 写死三条；`tests/raw/test_store.py` 与 `tests/raw/test_ingest.py` 全部共用这一个 ledger fixture
- 攻击路径：新增 `DefectCode` 时，必须先扩 conftest.py 的 `LEDGER_TOML`，再在测试里跑该 def。但 conftest.py 是共享夹具，更动它影响所有测试的契约断言。回归检测变成「新增项 → 跑全测」的 O(N×D)，CI 时间爆炸，且无法定位「哪个 defect 让哪个断言失败」。
- 修正：conftest 提供工厂 fixture `make_ledger(*codes, days=...)`；每个测试自己声明用哪几条；契约测试必须断言「某个 defect 在/不在账本时，ReadResult 行为差异」。

## 建议

**8. `GapReason.STREAM_PARTIAL` 在 `symbols=None` 时语义不清**
- 证据：`tests/raw/test_store.py:855-859` 仅在指定 symbols 时断言 `STREAM_PARTIAL`；`src/ftbv2/io/raw/store.py:461-463` `execute` 在 symbols=None 时如何归因未规定
- 修正：symbols=None 时不把「orders 标的集合小于 trades」归为 stream_partial（无标的级断言基准），整体进新增 `GapReason.DAY_PARTIAL`。

**9. `int` / `price` 的字符串 → Float → Int 中转精度损失无运行时检测**
- 证据：`decode.py:357-372` 表只列 V1 已观察到的边界
- 修正：`to_int64` 增加反向断言 `abs(int(float(s))) == abs(int(s)) for abs(int(s)) < 2^53`，不成立即 null；ReadStats 暴露 `n_roundtrip_failed`。

**10. `kind = "time"` 五位 HMMSS 与六位 HHMMSS 解析同一值，brief 未要求「5 位必带账本登记」**
- 证据：`decode.py:357-372`；`ledger/defects.toml` 只登记 `time_6digit`，未登记 `time_5digit`
- 修正：5 位时间只在 `time_6digit` 已登记的天允许；ledger 增加 `time_5digit`（或文档禁止 5 位并让 decode 拒绝 → null）。

**11. 9 位 HHMMSSmmm 未做小时数合法性检查（h≤23, m≤59, s≤59）**
- 证据：`decode.py:357-372`；`tests/raw` 边界表只测一个 in-range
- 修正：`to_time_ms` 对越界时分秒 → null；ScanPlan.patches 加 `time_invalid` 标签，ReadStats 暴露 `n_time_invalid`。

裁决：不得合并
