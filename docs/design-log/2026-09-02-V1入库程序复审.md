# V1 入库程序复审（2026-09-02，过程文档）

> 用户要求：7z 质量不可靠、写法与记录方式多变，V1 可能已经趟过这些坑，V2 要看一眼并保持。
> 本文只记复审结论与证据；裁决落到三份活文档（数据表第四节已登记）与代码。

## 一、V1 入库链路地图

| 角色 | 文件 | 说明 |
|---|---|---|
| 生产入库 | `scripts/j1_backfill.py` | 7z → `data/preserve/{xinqing,orders,trades}/date=YYYYMMDD.parquet` + `manifest.parquet`。一天一子进程（规避 mmap mapcount 内核崩溃），按 400 标的分批写 part 再流式合并 |
| 7z 封装 | `src/followthebig/data/sevenzip.py` | `7zz l -slt` 列目录、按 listfile 选择性解包；自动识别两种布局 |
| 救援 | `scripts/rescue_partial_l2_day.py` | 7zz Data Error 的天：跳过坏成员、能救多少救多少，写 `data/quality/partial_days.json` 黄条 |
| 更早的规范化路径 | `src/followthebig/data/ingest.py` + `normalize.py` | 逐标的 → events/snapshots 的 Stage-1 路径，不产 preserve；异常处理更松（逐标的 except 后继续） |
| 读取原语 | `preserve_schema.py` | `_i64`（Float64 中转）、`_hhmmssmmm_to_ms`（整数算术，天然接受八位）、`_cont_session_mask` |
| 学到的形状留在测试里 | `tests/test_sevenzip.py` · `test_daily_time_normalize.py` · `test_normalize.py` | 两种 7z 布局；6 位 / 5 位时间与混合口径 fail-loud；SZ 撤单 BS 位是空格、'U' 委托类型 |

## 二、V1 趟过的坑 → V2 现状

| # | 形状 / 异常 | V1 的处理 | V2 现状 |
|---|---|---|---|
| 1 | 7z 两种布局：`{day}/{sym}/{csv}`（2022–202603）与扁平 `{sym}/{csv}`（202604+） | `_has_day_prefix` 看前 200 条目猜，猜不出默认旧布局 | **保持且更严**：两种都接受，其他形状硬失败；敌对测试覆盖扁平布局 |
| 2 | py7zr 在 solid 归档上按目标重复解流（36 分钟挂死、900+ fd） | 改 `7zz` CLI 一趟流式 | **保持**：只用 7zz，列目录 10 分钟 / 解包 4 小时超时 |
| 3 | 非规范文件名：`20260303(1).7z` 重复件、`*.baiduyun.p.downloading` 半成品 | `list_all_days` 正则只收 `^\d{8}\.7z$`，其余跳过并计数 | **缺**：V2 `ingest` 只接一个显式路径，没有批处理驱动。写驱动时必须带这条 |
| 4 | 7zz 返回码：0 成功 / 1 警告（有条目缺）/ ≥2 致命 | **rc=1 放行**，随后缺文件的标的被 `_csv_ncols_if_data` 静默排除 | **更严**：`check=True`，rc≠0 一律 RuntimeError |
| 5 | 7zz Data Error（坏成员） | 严格路径硬失败；另有救援脚本按用户明示接受残缺日，写质量标记 | **硬失败保持**；**没有救援模式**（见第四节待裁决） |
| 6 | CSV 编码：GBK 表头 + ASCII 数据 | `encoding="utf8-lossy"`：非法字节静默替换 | **更严**：表头 GBK 解码、数据体非 ASCII 硬失败；22 天真实数据零命中 |
| 7 | 行字段数多于表头 | `truncate_ragged_lines=True`：**静默截断多出的字段** | **更严**：列数不符硬失败。注意：V1 若真截过，preserve 里已无痕迹，866 天无 7z 的部分永远查不出 |
| 8 | 解析错误 | `ignore_errors=True`：静默置 null | **更严**：数据体含引号硬失败；其余按字符串原样保留 |
| 9 | 只有表头的空文件（0 数据行） | 静默排除该标的（不计入 n_symbols） | 合法，计 0 行、标的计入。22 天两边 n_symbols 完全相同 ⇒ 语料里没有这种文件（或 V1 恰好没遇到） |
| 10 | **0 字节文件（连表头都没有）** | `_csv_ncols_if_data` 返回 0 → 静默排除 | **硬失败**（第二轮复审规则）。真实数据已命中：2022-06-27 `605222.SH/行情.csv` 在 7z 里 Size = 0，该股当天正常交易（orders 11,154 行 / trades 7,224 行）。**待裁决** |
| 11 | 停牌心跳：只有行情、无委托无成交 | 逐 csv 独立处理，天然通过 | **已登记为合法形状**（2026-09-02 裁定 A）；2022-05-05 重摄验证 72 只与 V1 xinqing−orders 差完全一致 |
| 12 | SH/SZ 或跨标的列数不同 | 「列并集」：按当日最大列数补 null，静默 | **更严**：同 stream 表头逐字节一致，否则硬失败。V1 manifest 反查：**56 天三条流各少一列**（2024-11-27、2026-01-30、202602 12 天、202603 21 天、202604 21 天）——少的是尾逗号幽灵列，盘口不变量成立率与正常日相同，语义未错位；但那些天的枚举空值是 **null 而非空格**（CSV 里字段为空），是另一批导出程序 |
| 13 | 6 位 / 5 位时间（无毫秒、无前导零） | `daily.py` 按文件归一化（max<1e6 ⇒ ×1000），混合口径 fail-loud；**preserve 读取原语 `_cont_session_mask` 从未修**（fan-in 56，那两天静默丢整个交易所） | 缺陷账本 + 按行归一化；全语料扫描（本日）：只在 20240206 / 20240208 的 **xinqing** 出现，orders / trades 正常 ⇒ 账本 D001 应收窄到 xinqing |
| 14 | 8 位时间（早盘 10 点前无前导零，每天 13%–34%） | `_hhmmssmmm_to_ms` 整数算术天然正确 | 第一版切片实现漏了，**已修**为算术拆位（PR #4） |
| 15 | 科学计数法 `1.2018e+006`、UINT64 哨兵、`'\x00'`、int32 溢出 | `_i64` Float64 中转；UInt32 溢出曾出真锤（F59 #32） | 边界表逐位复刻，全部 Int64 |
| 16 | 开盘重复帧：09:30 / 13:00 每股各发两帧 | 派生层 `unique(subset=[_symbol, OB_TIME], keep="first")` 去重 | preserve 不删行（正确）；**事件提取必须知道**，现在只记在数据表 V1 公式一节，应提到第四节形状登记 |
| 17 | 内存 / mmap：18 GB 峰值 + mapcount 溢出内核崩溃 | 限线程 6、分批 400 标的、一天一子进程 | 逐流加载即写即释放；本日单进程连摄 22 天无事故（峰值未测） |
| 18 | 磁盘余量 | 跑前查 `free_gb < floor` 软停 | **缺**：解包 17 GB/天到 SSD，满了只会 7zz 失败后清理。批处理驱动要带 |
| 19 | 验收 | 行数校验同义反复、round-trip 是 `10 == 10`、sha256 从未读回 | 独立计数（非空行）、parquet 哈希进 manifest 并在幂等路径核对、规范帧 sha256 |

## 三、用 V1 manifest 反查出的、之前没登记的形状

1. **56 天无尾逗号**（上表 #12）：良性，但枚举空值 null / 空格两套并存——读取层 enum 保持原值，下游把 `' '`、`''`、null 视为同一个「无值」。已登记数据表第四节。
2. **标的级单边缺失，5 个非救援日**（V1 manifest：orders ≠ trades）：
   20230807 `601099.SH`、20230810、20230811（各 1 只有成交无委托）；20250731（1 只）；20250804（`000716.SZ / 000953.SZ / 001221.SZ` 有成交无委托，`600208.SH / 601088.SH / 603377.SH` 只有行情）。
   这 5 天没有 7z，无法分辨是厂商漏文件、0 字节文件还是 V1 rc=1 放行后丢文件。读取层按 stream 给 `SYMBOL_ABSENT` 缺口，已能应对；
   但**新数据若再出现「有成交无委托」，V2 摄取会硬拒**——形状待裁决（见下）。
3. **0 字节文件**（上表 #10）：2022-06-27 一例，有 7z 为证。

## 四、待用户裁决

- **0 字节 CSV**（有 7z 证据的真实形状，V1 静默跳过，V2 硬拒）。选项：
  - **A（推荐）**：0 字节文件 = 该标的该 stream 无数据，登记进收据（如 `empty_files: ((symbol, stream), …)`），该标的不进该 stream；
    「只有表头」仍是 0 行合法文件；其余畸形仍硬拒。与停牌心跳同一哲学：登记而不是静默。
  - B：维持硬拒 ⇒ 2022-06-27 永远无法从 7z 摄取，只能用 V1 preserve（它静默删了 605222.SH 的行情）。
- **单边缺失（有成交无委托 / 有委托无成交）**：目前无 7z 证据，V2 硬拒。建议维持硬拒，等新数据真撞上再按证据裁决，不预设。
- **救援模式**（Data Error 的天）：V1 有独立脚本 + 质量标记。V2 的 `Quality` 只有 `verified_byte_exact / self_consistent / unverified`；
  20260805 / 20260811 已在 V1 preserve 里（账本 D004）。建议：V2 暂不做救援摄取，等再遇到坏归档时按 D004 纪律加 `partial_rescue` 档。

## 五、V1 的硬伤（V2 必须不重蹈）

`utf8-lossy` + `truncate_ragged_lines` + `ignore_errors` 三件套让入库永远不报错，代价是任何脏数据都被静默改写；7zz rc=1 放行 + 空文件静默排除，让「标的少了」没有任何记录；
验收全部同义反复。V2 的每一条硬失败都对应这里的一处静默——真实数据 22 天摄取只撞到两个形状（停牌心跳、0 字节文件），都是用一次硬失败换来一次登记。
