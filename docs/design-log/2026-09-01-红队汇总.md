# 三方异构红队汇总

> 三个不同架构的 agent 独立攻击同一份简报（含四种切法）：
> **MiniMax**（方法论）· **Gemini/agy**（架构）· **Codex**（工程可实施性）。
> 全文见同目录三份 `2026-09-01-红队-*.md`。本文件只记录**结论与需要改的东西**。

## 一、三方独立命中的同一批要害

### 1. 「无定论」会吞噬一切（三方全中）

- **Gemini 的量化**：本项目目标就是「信号稀少、靠右尾不对称获利」。一年 5–10 次开仓信号
  ⇒ 1122 天总样本 **N ≤ 40**，收益偏度 > 3。这种样本下参数化统计功效几乎**永远在 0.1–0.3**，
  于是**有效策略与无效策略被 100% 一律判成「无定论」**，三态裁决沦为只输出「数据不足」的摆件。
- **MiniMax 从另一端**：A 股横截面 IC 真值通常 0.01–0.03，打显著需百万级观测；
  同一只票的多次拉升高度自相关，**iid 假设根本不成立**。
- **Codex 的反向风险**：「功效不足不许推翻」会被滥用成**永不失败**——每个烂假设都能说样本不够，
  **队列会堆满无定论尸体**。

**修正**：
1. 废除参数化功效前置断言，改用**事件时间打散置换检验**（保持真实波动率与流动性约束，
   把开仓信号在时间轴上随机打散 1000 次算经验 p 值；效应落在置换分布前 1% 且绝对样本 ≥15 即确证；
   功效不足时输出**置换分布重叠度**而非一个状态码）。
2. 三态不够，需要第四态或附加标签：`abandoned_for_cost` / `underpowered_but_negative` /
   `not_worth_more_data`。

### 2. 盲验机械实现不可能（三方全中）

- **MiniMax**：简报本身列出 V1 全部失败教训 ⇒ 这些教训**已成为每个 agent 的先验**。
  V2 的 agent 不 import V1 代码，但写出来的东西天然避开 V1 的失败模式——
  *这不是盲验在工作，是 V1 教训已被吸收成「什么是显然正确的」*。
  判词：**任何不满足「不知道有 V1 存在」的盲验都不是盲验，是延迟读取。**
- **Gemini**：Python 里进程污染标记一行 `del os.environ[...]` 就消，`subprocess` 主进程完全看不见；
  真正的污染是**认知污染通过 prompt 在 agent 之间传递**。**把认知层防作弊寄托于 IO 句柄标志位是安全错觉。**
- **Codex**：字段名、假设命名、样本区间、特征选择本身就泄露 V1 偏好。
  **挡不住灵感污染，只能记录污染级别，不能宣称物理保证。**

**修正**：把盲验从「机制」降级为「对照 + 记录」——
① 每个 sprint 引入**不知道项目历史的异构 agent**（不同模型、不同上下文）独立出裁决，
结果不与项目内裁决合并，单独报告一致性差异（fresh-eyes 对照）；
② 假设来源必须**声明污染级别**，而不是假装可以消除污染。

### 3. 预注册可被逆向成「过拟合洗白工具」（Gemini + MiniMax）

**Gemini 给的可照做的退化路径**：本地未注册脚本网格搜索 100 个超参 → 找到 2024 年表现极佳的
`decay=0.94, threshold=2.31` → 新建 Hypothesis 填入 → 冻结哈希 → 声明「接触数据前独立提出」→
执行器机械判定 **CONFIRMED**，证据指纹完全闭环。
**结果比没有系统更糟：系统给有毒的过拟合颁发了一张不可篡改的「确定性收据」。**

**MiniMax 补：预注册锁不住的清单** —— 预处理流水线（缺失值用前收还是行业均值，IC 差 30%）、
特征工程的中间选择、**universe 定义本身**、CV fold 划分、`ExecutionSpec` 里被称作「唯一来源」的参数
（**每一个都是策略，不是技术细节**）。以及拆解式规避：把一个家族假设拆成 5 个独立假设各自校正，
名义合规、实际膨胀 5 倍。

### 4. 多重检验作用域（三方全中，且 Gemini 反证了拆法 A）

- **Gemini 的反例**：周一 H1–H10 裁决，H1 确证；周二受 H1 启发提出 H11–H20；合并批次重跑后
  BH 阈值收紧，**H1 被机械降级为推翻**，下游组合假设级联断裂。研究员被迫在
  「停止提出新假设」与「接受历史结论被不可逆摧毁」之间二选一。
- **MiniMax**：换测试窗口、换 universe 都是多重检验，工具完全看不见。
- **Codex**：「整批」定义不清 ⇒ 必被拆 family 规避。

**修正**：作用域定义在**研究 episode** 上（一个研究问题 + 一个因子空间 + 一个 universe 空间），
episode 开始时**声明假设预算，用完即冻结**；每个假设必须声明 `correction_family_id`，
对 family 的**新增/关闭/分裂做审计**。

## 二、直接推翻既有决定的三条

### A. 结论写回代码注释 —— 与收据机制死锁（Gemini），且是坏主意（Codex）

**Gemini 的死锁**：工具把结果写回 `src/*.py` 注释 ⇒ `tree_sha("src")` 立即改变 ⇒
收据里的 tree_sha 是执行前的 ⇒ **CI 必然硬拒**。要绕过就得在 CI 里内嵌 AST 剥离注释再算 SHA，
摧毁 `git rev-parse` 的原子性与整条标准工具链。

**Codex 追加的实际代价**：合并冲突 · 无意义 diff 淹没 review · rerun 后源码变脏 ·
cherry-pick/backport 困难 · **同一假设多样本区间/多 runner/多版本结果塞不下** ·
格式化或移动代码导致指纹失配 · CI 因「注释陈旧」拒绝非语义改动。

**修正**：代码保持只读，严禁运行时反向修改源码。结论写到**内容寻址的 evidence bundle**
（`.lineage/<hypothesis_id>/receipt.json`），**代码里只保留稳定的 hypothesis id 或 prereg hash**。
CI 校验「当前代码声明的 prereg hash 是否存在对应 bundle」，不把 bundle 内容写回注释。

### B. 「builder 不得过滤行，只能加标记列」—— 会直接爆仓（Gemini + Codex）

**Gemini 的账**：trades 每天 5,300 万行 × 1122 天 = **594 亿行**；即使每行只加 2 字节 UInt8 标记，
**单特征全历史 118 GB**，而派生层预算 100 GB ⇒ **写第二个特征时 SSD 直接拒绝写入，流水线崩溃**。
且庄股特征识别**本质是事件抽取**，必须把 5,300 万行坍缩成几万个高价值事件。

**修正（Codex 的措辞最准）**：**不得在未声明样本宇宙前删除行**，而不是一律不得过滤。
即：凡参与**样本池定义或标签定义**的产物不得过滤行（这才是 F182 的教训）；纯特征抽取可以且应当降维。

### C. 多 agent 四角色流水线 —— 会崩（Codex）

**退化路径**：接口评审时人签字（因为接口看起来窄）→ 实现时发现真实缺陷太多，加内部 escape hatch →
测试 agent 没看实现，漏掉 escape hatch 的语义后果 → 增强 agent 为性能加缓存、批处理、`force`、
`skip_bad_day` → review agent 只能查局部 diff，看不到研究结论是否被污染 →
**两个月后每个假设都有自己的薄 wrapper，V1 的 684 个脚本换了名字回来**。

**修正**：**只保留三个角色——接口 owner、实现 owner、敌对 reviewer。**
验证可以异构，但**必须验证同一个可执行契约，而不是各写各的理解**。
「多 agent 适合并行做粗活，不适合把责任切碎。」

## 三、Codex 最深的一条批评：深度放错了位置

> `删除测试 N≈1,123` 被高估。你不是删除 1,123 个调用点，而是把它们压成了 1 个万能入口。
> 旁路脚本不会消失，它会变成 `raw.read("trades", days, fields=[...]).filter(...)`，
> 然后每个研究脚本继续自己做时间过滤、样本过滤、异常日处理、聚合口径。
> **V1 的事故不是只有 `read_parquet` 分散，而是「读完之后的语义判断分散」。**

**Gemini 同向**：1,123 次调用不是 1,123 种业务逻辑，而是**约 15–20 种核心访问模式被复制了几十遍**；
真实的等价重构消除点 **N ≈ 15–20**。「把调用次数等同于接口杠杆率，制造了虚假的架构收益繁荣。」
同理 `simulate` 的 39 次是**结构性异构**（日频调仓 / 逐笔挂单排队 / 集合竞价偷袭 / 涨跌停强平），
单签名 `simulate` 覆盖不了，除非 `ExecutionSpec` 长成含字节码回调的怪物。

**这条必须接受。** 缝要下移到「读完之后」：**样本宇宙定义、异常日处理、时段口径、聚合口径**
才是真正需要唯一住所的东西。

## 四、一批具体可采纳的修正（Codex 为主）

| 原设计 | 问题 | 修正 |
|---|---|---|
| `materialize(..., force)` | **`force` 是退化入口**：所有「血缘不匹配但我知道没问题」的压力都汇到它，最终变成 V1 的 `audit_v4.py` | 删掉 `force`。要重算就走显式的 invalidate + 重新物化 |
| `max_cost_class` 必填 | 早期不知道是 C2 还是 C3，估错一次硬失败 ⇒ **大家统一写 C4，门禁失去信息量** | 改成 `cost_budget_id`，预算来自队列/周配额，不让调用者手填等级 |
| 「IO 段不允许基于数据内容分支」 | 太绝对：缺陷日、停牌、空表、半日交易、损坏 row group 都需要分支 | **IO 阶段只能基于缺陷账本与元数据分支，不能基于研究统计结果分支** |
| 封闭谓词构造子 | 表达不了复杂条件 ⇒ 研究员被迫只下推 symbol ⇒ **拉进内存的数据比用 lambda 还多** | 谓词分两层：**可下推谓词** + **扫描后过滤表达式**，并在计划里明确哪些不能下推及其成本 |
| 补丁在投影之后应用 | 补丁可能需要用户没投影的列 | 投影分「用户字段」与「补丁所需字段」，扫描器**自动扩展内部投影，返回前再裁剪** |
| 参数集句柄代替 kwargs | 台账太重 ⇒ 出现 `tmp_param_set_20260901_7`（换皮） | 参数集**可以临时创建，但必须内容寻址、不可变、自动进入多重检验族** |
| 100 GB 硬上限 | 太粗，逼人写到仓库外/notebook cache | 分账：**持久派生 / 短期 scratch / 可重建缓存 / 一次性审计产物** |
| 收据绑定 `tree_sha("src")` | 太窄：改 lockfile、schema 账本、缺陷账本、参数台账、夹具都会改变结果 | 绑定 **source tree + dependency lock + data manifest + defect ledger + parameter set + runner image digest + command spec** |
| 自托管 runner | 队列积压 ⇒ 人绕过；状态漂移 ⇒ 不可复现；**「CI 绿但研究假」** | runner 必须是 **cattle 不是 pet**：固定镜像、只读数据挂载、无交互 shell、作业级 scratch、完整输入输出 manifest |
| 不透明句柄 | Python 里下游库最终必须拿到 URI/fd；且伤害调试与人工恢复 | 生产接口返回句柄，**审计接口可受控解析路径并记录调用者** |
| CI 断言 pyarrow IO 字节数 | pyarrow 没有标准计数器；版本/压缩块/row group/metadata 策略都会让计数抖 | 字节数作**回归指标与趋势告警**；**硬门禁只断言扫描计划** |
| 「明确不建通用回测框架」 | 会走反面极端 ⇒ 39 个 simulate 以「本假设专用执行器」的名义重生 | 需要一个**非常窄的执行语义核**：撮合、滑点、涨跌停、停牌、成交量约束、路径依赖 |

## 五、伪承诺（Codex）

**`ingest` 不能承诺「原始层是逐行无损副本」。** 2023-01 → 2026-07 的 7z 已删，
**对 77% 的数据既无法逐字节 round-trip，也无法与源 CSV 做真行数比对**。
ingest 只能验证 **preserve 层自洽**，不能验证「原始无损」。
⇒ **`CONTEXT.md` 里「原始层 = 逐行无损副本」这条定义必须改**，改成分档的可验证性标签
（`verified_byte_exact` 仅对 23% 成立）。

## 六、最容易被关掉的门禁（Codex 清单）

`diff-cover` 增量覆盖率（重构/移动文件/生成代码大量误伤）· ruff 复杂度（Polars 表达式天然密集，
被拆成更差的小函数）· 禁跨模块 import 私有符号（测试、性能优化、内部 schema 工具首先撞上）·
金标准回归（Polars/pyarrow 版本、浮点、排序稳定性、字典编码造成「合理变化」）·
血缘校验（hash 含太多环境细节则频繁误报，含太少则无意义）· 字节数门禁 ·
「无 override」缺陷策略（账本错时无法救火，最后在仓库外绕过）·
「builder 不得过滤行」（存储爆炸后必被关）· 全局多重检验批裁决（阻塞研究节奏后被拆 family 绕过）。

## 七、三方对失败概率的排序（不一致，值得注意）

| | 最先失败 | 理由 |
|---|---|---|
| **MiniMax** | 门禁倒逼版 | 跨日因子必然流式 ⇒ 核心业务逻辑掉出 CI 硬门禁 |
| **Gemini** | 门禁倒逼版 | 伪安全机制在 Python 里一戳就破，开发摩擦逼研究员 48 小时内绕过 |
| **Codex** | **粗切信息隐藏版（我的初稿）** | 太多东西寄托在流程纪律上，物理防线不够；仍允许「临时读一天看看」的旁路脚本自然生长 |

三方一致认为**用例垂直切（成本等级 + 纯计划器 + 账本进 CI）工程直觉最好**，
但它的 100 GB 假设在数学上不成立。

## 八、三方共同的最终建议：不要先建完整架构

**Gemini 的第四种架构（事件化两层微内核）**：

```
2.585 TB 原始 tick（外置盘，C4 单向流式，一次性）
        ↓ 规范事件提取器（异常撤单 / 激进扫盘 / 冰山对倒片段）
微观事件流 5–8 GB → 100% 常驻内置 SSD
        ↓
显式状态机纯核  step(state_t, event_t) -> (state_t+1, signal_t)
        ↓
经验置换检验裁决 + Git-backed 血缘 JSON
```

一次解决四个致命问题：① 容量（8 GB 而非 594 亿行）② 跨日 IO 爆炸
（无状态日批次下 30 日回看是 O(30T)，**全量回测从 15 小时变 450 小时 / 19 天**）
③ **跨日破坏纯函数**（显式状态机让 CI 能用 10 KB 合成事件在 5 ms 内对跨日 60 天做 100% 覆盖断言）
④ 日常不再依赖 4 IOPS 的盘。

**⚠️ 它的代价（我的补充，非红队提出）**：事件提取器里嵌着「**什么算庄的痕迹**」这个判断，
而这恰恰是最需要反复修改的研究问题——现在被锁死在一个**要 15 小时才能重跑一次**的位置。
**降维是对的，判断前置是风险。** 缓解方向：事件提取尽量宽而中性（只抽统计异常，不预判语义），
把语义判断留在状态机层。

**Codex 的窄实验工厂 + 时间线**：只支持 1 个 stream、20 个交易日、3 个假设，
跑通完整的 `request → plan → cost check → execute → defect patch → canonical frame → evidence manifest`
再扩大。

- **3–5 天**：第一个可运行的扫描闭环
- **1–2 周**：缺陷账本 + 成本计划 + 合成语料金标准接进 CI
- **3–4 周**：跑通第一个真实预注册假设
- **在第一个假设跑通前，不要建多 agent 流水线、不要建收据写回注释、不要建全量自托管 runner 编排**
  ——这些现在只会先制造流程复杂度，不会降低失败概率。
