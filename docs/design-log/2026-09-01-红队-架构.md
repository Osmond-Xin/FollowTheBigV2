# 红队架构审查报告：FollowTheBigV2

---

## 零、执行摘要与总体裁决

三版方案均对 V1 的病灶（1,123 处调用点、路径硬编码、schema 摧毁、测试盲区）做了极其详尽的病理诊断，但在工程解法上走向了不同的**致命极端**：

| 方案 | 核心哲学 | 最致命单点 | 裁决结论 |
| :--- | :--- | :--- | :--- |
| **第五节（信息隐藏 7 模块）** | 经典 Ousterhout 深度抽象 | **无成本治理与派生膨胀**：未定义物理存储边界与扫描排队机制，高估抽象纯度，必死于 exFAT 4 IOPS 的物理争用。 | **不可行（物理崩塌）** |
| **第七节（检查点 + 成本等级）** | 显式成本契约 + 状态机 | **存储容量假定破产**：把派生层强行限制在 100GB SSD，但庄股 Level-2 核心特征（撤单、冰山、委托队列）属于不可压缩的 Tick/Event 级，3% 压缩率在数学上不可能。 | **不可行（容量崩塌）** |
| **第八节（句柄 + 封闭谓词 + 污染标记）** | 极权防御性编程 | **过度工程与伪安全**：依赖 Python 进程污染标记、封闭谓词 AST、代码注释回写等在动态语言中无法闭环的假机制，开发摩擦力极大，必将逼迫研究员在 48 小时内彻底绕过框架。 | **不可行（人机工程崩塌）** |

**最可能率先失败的是「第八节」，其次是「第五节」。**
第八节充斥着「看似聪明、实则在 Python 运行时中一戳就破」的防御机制；第五节则是典型的「学院派整洁架构」，在 2.58 TB 外置 exFAT 的极端物理约束下，其接口深度全是纸上谈兵。

## 一、假深度、错位缝与删除测试 N 的虚高

### 1. 假深度模块（Pass-Through / 伪装层）

*   **第五节：`Hypothesis` 类型化对象 + `verdict()`（模块 5）**
    *   **假深度诊断**：`Hypothesis` 被包装成类型化 Python 对象，声称是纯逻辑核。实际上，它只是将检验指标名称、参数字典和阈值打包的 **DTO（数据传输对象）**。它不隐藏任何市场或统计的复杂性，它依赖上游解析 DAG，依赖下游 `verdict()` 做数值判定。整个模块深度趋近于 0，是一个典型的**类型占位转发层**。
*   **第七节：`adjudicate(prereg_hash, derived_ref)`（裁决接口）**
    *   **假深度诊断**：接口声称「没有任何可调参数、无旋钮」。但裁决的本质是 `f(stats, prereg_thresholds)`。如果所有阈值在预注册对象里，所有统计量在派生引用里，`adjudicate` 的实现只有 3 行：读取哈希、对比浮点数、返回枚举。它隐藏的复杂度为零，却在架构图上占据了一个独立切片。
*   **第八节：目录与不透明句柄（Catalog & Handle）**
    *   **假深度诊断**：句柄没有 `.path`，试图隐藏物理路径。但在 Python 中，任何下游计算库（Polars、DuckDB、PyArrow）最终与 OS 交互必须拿到系统调用级别的路径、文件描述符或 Buffer。这个句柄内部必须提供 `_unwrap()` 或暴露 C++ 指针。所谓「不透明句柄」只是在 Python 层做了一层毫无防卫能力的薄壳，徒增 100% 的包装代码。

### 2. 缝放错位置（Misplaced Seams）

*   **错位缝 1：将「物化/衍生层（Materialize）」与「原始层访问（Raw Access）」在物理存储上割裂**
    *   *错误切法*：第五节将 Raw Access 和 Materialize 切成两个独立服务；第七节设 H1 和 H6。
    *   *致命反例*：在 Level-2 庄股分析中，最常见的查询是 **「原始 Tick 委托流 JOIN 派生日级庄板状态」**（例如：只对 `sweep10 >= 2` 的标的在拉升当天加载逐笔委托）。如果 Raw Access 与 Materialize 是两条独立的垂直管道，系统必须先执行全量日级状态查询，物化到内存，提取股票列表，再通过参数喂给 Raw Access。这强行将原本可在 Polars/DuckDB 内部完成的**谓词合并执行计划**切成了多次跨层往返调用。
    *   *正确切缝*：**缝不应该切在「原始 vs 派生」，而应该切在「扫描计划引擎（Scan Planner）」与「底层块读取器（Block Storage Engine）」之间。** 派生层本质上只是带版本号和血缘前缀的 Parquet 表，它和原始层共享同一种谓词下推和统计元数据索引。
*   **错位缝 2：将「检验原语」与「执行模拟」完全隔离为无状态纯函数**
    *   *错误切法*：第五节将 `simulate()`（模拟）与 `ic()` / `layered_return()`（统计）完全切开。
    *   *致命反例*：庄股策略（如尾盘偷袭吸筹、早盘快速封板）具有极强的**流动性反馈与排队阻断特征**。信号出现时，往往伴随着涨跌停、无流动性或自身冲击成本。如果先算纯粹的因子 IC，再用一个完全独立的 `simulate()` 跑固定滑点，会导致大量因子在第一阶段被判定为「极显著」（因为吃到了涨停价的虚假收益），进入模拟阶段却因无法成交全部归零。
    *   *正确切缝*：**缝应切在「撮合状态机」与「组合收益归因」之间。** 任何庄股因子的第一步统计检验，必须内生感知物理可成交性（Tradeability Mask），而不是在纯逻辑核与模拟核之间做两次失真的数据流转。

### 3. 删除测试 N 的严重虚高

*   **第五节：原始层访问（Raw Access）删除测试 $N \approx 1,123$ —— 严重高估**
    *   *攻击*：V1 里的 1,123 次 `read_parquet` 并非调用了 1,123 种不同的业务逻辑，而是因为没有通用提取脚本，**50 个几乎相同的读取范式被复制了 20 次**。如果抽象出一个包含 `pre_buffer=True`、列名映射和时间归一化的 Reader，其真实的等价重构消除点（Deletion Test）仅为 **$N \approx 15 \sim 20$**（即 15 种核心访问模式：全日单股三流合并、全市场单流扫描、截面快照等）。声称 $N=1,123$ 是把「文件行数/调用次数」等同于「接口杠杆率」，制造了虚假的架构收益繁荣。
*   **第五节/第七节：执行模拟 `simulate` 删除测试 $N = 39 \sim 68$ —— 严重高估**
    *   *攻击*：V1 复制 39 次 `simulate*` 的真实原因，是策略状态机存在**结构性异构**：有的是日频调仓，有的是逐笔委托挂单排队，有的是集合竞价偷袭，有的是包含涨跌停锁死的强平。一个单一签名的 `simulate(signals, prices, spec: ExecutionSpec)` 根本无法覆盖这些异构逻辑，除非 `ExecutionSpec` 演化为包含 Python 字节码回调的怪物。这 39 次复制代码不是一个通用的 `simulate` 就能删掉的，它需要的是针对 3 种特定执行范式的微内核。

## 二、无法保证的接口不变量与具体穿透场景

### 1. 「代码执行结果自动回写代码注释」+「HMAC 签名校验 `tree_sha`」（第四节 / 第八节）
*   **自相矛盾的死锁**：
    1. 进程执行完毕，工具将运行结果/指纹写回 `src/strategy_01.py` 的头部注释。
    2. 该文件内容被修改，导致本地 Git 的 `tree_sha("src")` 立即发生改变。
    3. 开发者提交时，CI 校验收据：收据内的 `tree_sha` 是执行前的，而远程 Git 树是包含回写注释后的 `tree_sha`。
    4. **CI 判定签名与 `tree_sha` 不匹配，硬拒绝。**
    5. 若为了绕过该问题让 CI 忽略注释行，则必须在 CI 中内嵌 AST 语法解析器剥离注释后再算 SHA，这直接摧毁了 `git rev-parse` 的原子性与跨语言标准工具链支持。

### 2. 「进程污染标记（Taint Tracking）实现机械盲验」（第八节）
*   **运行时防御归零**：
    1. 在 Python 这一完全动态反射的语言中，任何进程级标记（如全局变量、环境变量、模块属性）均可被一行代码消除：`del os.environ["_TAINTED"]` 或直接使用 `ctypes` 修改内存。
    2. 研究员只需通过 `subprocess.run(["python", "-c", "import v1_legacy..."])` 开辟子进程，主进程的内存状态树根本无法捕获子进程的 IO 行为。
    3. 更致命的是**认知污染（Cognitive Leakage）**：编写预注册假设的 Agent 或人类已经在上下文里看过了 V1 的成败结论，即便数据加载层没有打上 taint，其设置的先验超参数（如阈值选 0.12 而不是 0.15）早已被污染。**将认知层面的防作弊寄托于 IO 句柄的标志位，属于典型的安全错觉。**

### 3. 「派生层 Builder 不得过滤行，只能加标记列」（第五节、第七节）
*   **物理存储直接爆仓**：
    *   逐笔成交（Trades）每天约 5,300 万行。
    *   如果识别「大单压盘」或「冰山委托」的 Builder 必须保留全量 5,300 万行并仅追加 `is_iceberg` 列，1122 天的数据行数将达到 **594 亿行**。
    *   即便每行只多存 2 个字节的 UInt8 标记，单特征全历史就需要 **118 GB**。
    *   第七节规定 SSD 派生层**硬上限 100 GB**。这意味着：**只要有一个特征 Builder 遵守「不删行」的不变量，在写入第 2 个衍生特征时，SSD 就会直接拒绝写入并导致整个流水线崩溃。**
    *   *真实诉求*：庄股特征识别在本质上是**事件抽取（Event Extraction）**，必须将 5,300 万行原始 Tick 坍缩为几万个高价值异常事件（如撤单突增事件、对倒异动区间）。强行要求 100% 保持行数，违背了量化降维的数学常识。

### 4. 「封闭谓词构造子（Closed Predicate Constructor）」（第八节）
*   **引发全表扫描反向暴击**：
    *   为了防止 lambda 逃逸，第八节限制只能使用封闭构造子（如 `col("symbol") == "000001"`）。
    *   但在实际研究中，研究员需要筛选：`“连续 5 档买单量之和 / 卖单量之和 > 3”` 且 `“成交价格偏离 VWAP 超过 2%”` 的时段。
    *   因为封闭构造子不包含这种复杂的滚动时序表达式，调用者只能被迫写出最宽松的谓词（例如只下推 `symbol == "000001"`），把全天 100% 的逐笔委托全量拉进内存，再在本地做过滤。
    *   **结果**：为了在形式上防住 lambda 无法下推的警告，反而迫使调用者进行更大规模的内存搬运，彻底丧失了在 Reader 内部利用 SIMD/Polars 表达式原生优化的机会。

## 三、退化回 V1 的具体路径（系统是如何烂掉的）

系统绝不会因为「某天大家决定不遵守规则」而崩塌，它会通过以下三条**完全符合理性选择的逃生通道**退化回 V1：

```
[严格门禁 / 15小时外置盘排队]
             │
             ▼
[路径 1: Scratch 目录外逃] ──► 绕过 CI，在本地 Notebook 直接读盘
             │
             ▼
[路径 2: 预注册逆向工程]   ──► 本地 P-Hacking 跑出最优解 ──► 倒推伪造 Pre-Reg
             │
             ▼
[路径 3: 锁竞争私拆驱动器] ──► 多进程争用 4 IOPS 锁 ──► 拷贝数据到本地私盘
             │
             ▼
       [回到 V1 的混沌状态]
```

### 退化路径 1：Notebook 与 Scratch 目录的暗度陈仓
1. **触发点**：第七节的 `max_cost_class=C4`（全量扫描需 10-20 小时），且规定必须提交 CI 收据。研究员需要调整一个移动平均窗口（从 10 档平滑改为 20 档），发现提交流程需要等待 CI 门禁、生成签名、排队等锁，整个回路耗时 1 天。
2. **行动**：研究员在 `scratch/` 目录下新建 `quick_explore.py`，直接引用未受管制的底层 PyArrow（因为 Python 无法彻底禁止 `import pyarrow.parquet as pq`），将 2023 年某一个月的 Parquet 拷到本地。
3. **沉淀**：1 个月后，`scratch/` 目录下累积了 80 个端到端脚本；3 个月后，核心策略已在 `scratch/` 里孵化成型，`src/` 彻底沦为应付 CI 门禁的摆设。**V1 的 684 个顶层脚本在 `scratch/` 中完美复活。**

### 退化路径 2：预注册（Pre-registration）的逆向工程
1. **触发点**：预注册要求「接触数据前写死判据哈希」，但机器无法检测人脑在写代码前是否看过数据。
2. **行动**：
   - 步骤 A：研究员在未注册的本地脚本中，对 100 个因子超参数做网格搜索，找到在 2024 年表现极佳的特定组合（如 `decay=0.94, threshold=2.31`）。
   - 步骤 B：研究员新建一个形式上的 `Hypothesis`，填入 `decay=0.94, threshold=2.31`。
   - 步骤 C：调用系统工具生成该假设的固定哈希，声明「这是我接触数据前独立提出的假说」。
   - 步骤 D：触发执行器，系统机械判定：`Verdict: CONFIRMED`，证据指纹完全闭环。
3. **后果**：预注册机制从「防过拟合工具」退化为**「过拟合洗白工具」**。系统不仅没能防住数据窥探，反而给有毒的过拟合结果颁发了具备不可篡改伪证的「确定性收据」。

### 退化路径 3：单读者锁引发的私拆驱动器
1. **触发点**：第七节 H1 的硬不变量：`acquire_raw_lock()`（外置机械盘单读者排它锁）。
2. **行动**：Agent-A 启动了一次全市场 C4 扫描（预计耗时 16 小时）。此时 Agent-B 与人类研究员的所有交互式查询全部卡死在 `acquire_raw_lock()`。
3. **行动升级**：人类研究员无法忍受 16 小时的等待，将外置盘上的核心目录直接 `rsync` 到本地剩余的 100GB SSD 上，并修改本地代码绕过 H1 的锁机制。
4. **后果**：一旦本地副本存在，数据血缘（Lineage）立刻分叉，私有路径字面量（777 处硬编码）重新萌发。

## 四、未考虑到的核心失效模式

### 1. 跨日庄股状态机的时空坍缩（Cross-Day Stateful Collapse）
*   **业务现实**：庄股的典型行为模式是「长期低吸（20-60 个交易日） $\to$ 锁仓缩量 $\to$ 盘中脉冲试盘 $\to$ 快速拉抬 $\to$ 派发」。
*   **设计盲区**：
    *   所有三版方案都将数据分区和 Reader 抽象为 `day: int` 的无状态批处理单元。
    *   如果因子需要跟踪「过去 30 个交易日主力净流入占比」，且该主力识别依赖逐笔委托的微观特征，在无状态日批次切分下，计算第 $T$ 天的特征需要将 $T-30 \dots T$ 天的原始 Level-2 数据全量重读一遍。
    *   这将导致计算复杂度从 $O(T)$ 暴增至 $O(30 \times T)$。在原本就只能跑 50-89 MB/s 的 exFAT 上，全量回测时间将从 **15 小时拉长到 450 小时（近 19 天）**，整个系统陷入计算停滞。

### 2. 统计功效（Power）与极端右尾稀疏信号的根本冲突
*   **设计盲区**：方案要求「实测功效不足时不允许输出『推翻』，只能输出『无定论（Inconclusive）』」，并认为「无定论」与「推翻」分离是先进机制。
*   **数学陷阱**：
    *   简报第一节明确指出：本项目目标是识别**「信号稀少、需长期等待、靠右尾不对称获利」**的模型。一年可能仅有 5-10 次开仓信号，1122 天总样本量 $N_{trades} \le 40$。
    *   对于这种样本极度稀疏、收益分布极度偏态（Skewness > 3）的右尾策略，标准统计功效（Power Analysis）公式在小样本非正态下要求极大的效应量才能达到 0.8 的功效。
    *   **后果**：系统计算出的统计功效几乎**永远处于 0.1 ~ 0.3 的极低区间**。这意味着，**99% 的真正有效策略和无效策略，在机械裁决时都会被 100% 判定为 `INCONCLUSIVE`**。
    *   三态裁决由于硬卡功效阈值，在右尾低频量化场景下彻底丧失了判别力，沦为一个只输出「数据不足」的无用摆件。

### 3. 多重检验校正（FDR/FWER）的时序动态失真
*   **设计盲区**：第八节规定「裁决器必须一次看到整批假设，分批调用硬失败」。
*   **科研悖论**：
    *   真实的研究是**时间序列推进**的：周一提出假设 H1-H10 并裁决；周二在 H1 启发下提出 H11-H20。
    *   当周二运行裁决器时，由于假设总数从 10 增加到了 20，多重检验校正的显著性阈值（如 Benjamini-Hochberg 阈值）被动收紧。
    *   **现象发生**：周一被判定为 `CONFIRMED` 的 H1，在周二合并批次重跑后，由于 H11-H20 的稀释，**机械降级为 `DISPROVEN` 或 `INCONCLUSIVE`**。
    *   这导致历史证据指纹在逻辑上产生自我否定，下游基于 H1 构建的组合假设全部产生级联断裂。研究员必须在「停止提出新假设」与「接受历史结论被不可逆摧毁」之间做出荒谬选择。

## 五、三版方案详细横向剖析

```
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│   第五节方案    │       │   第七节方案    │       │   第八节方案    │
│ (信息隐藏7模块) │       │ (检查点+成本类) │       │(极权防御性编程) │
└────────┬────────┘       └────────┬────────┘       └────────┬────────┘
         │                         │                         │
         ▼                         ▼                         ▼
 ┌──────────────┐          ┌──────────────┐          ┌──────────────┐
 │  物理争用崩塌 │          │ 存储容量崩塌 │          │ 认知规避崩塌 │
 │  (exFAT IOPS)│          │  (100GB SSD) │          │ (开发摩擦力) │
 └──────────────┘          └──────────────┘          └──────────────┘
```

### 1. 致命缺陷对比

*   **第五节致命伤（无物理感知）**：
    它假设只要接口设计得像经典教科书一样深（Raw Access 隐藏一切），底层就能跑好。它完全忽略了 2.585 TB 位于 4 IOPS 的 exFAT 上这一残酷现实，未设计任何并发控制、扫描成本前置预检和全局查询合并器。多个 Agent 同时调用 `read()` 时，机械盘将直接陷入物理寻道死锁。
*   **第七节致命伤（容量假设虚妄）**：
    它是三版中工程直觉最好的（引入成本等级 C0-C4、纯计划器、单读者锁、账本进 CI），但它的核心支柱——**「SSD 派生层限额 100 GB」**——在微观庄股研究中直接违背了信息熵定律。Tick 级的微观结构特征不可能在保留有效信息的同时压缩到 3%。
*   **第八节致命伤（伪安全与官僚机制）**：
    它把大量精力花在「防作弊」上（不透明句柄无 `.path`、闭合谓词、进程污染 Taint、代码注释写回），但所有这些机制在 Python 解释器内均无法形成真正的安全闭环，反而引入了极度晦涩的元编程和调试灾难。

## 六、第四种替代架构（红队合成方案：事件化两层微内核）

为了克服上述三版的致命缺陷，提出第四种切法：**摒弃「表到表（Table-to-Table）的派生范式」，建立「原始流 $\to$ 规范事件日志（Canonical Event Log） $\to$ 内存纯逻辑」的两层确定性架构。**

```
                  【离线重活：外置盘 C4 批处理】
                  2.585 TB 原始 Level-2 (exFAT)
                                │
                                ▼ [单向流式还原与过滤]
                    ┌────────────────────────┐
                    │  Event Extractor 内核  │ ◄── 每日模式解码与缺陷账本
                    └───────────┬────────────┘
                                │
                  【降维产物：极窄事件流 (5-10 GB)】
                                ▼
                   SSD Canonical Parquet Events
                 (大单撤单 / 扫盘 / 冰山异动 / 锁单)
                                │
            ┌───────────────────┴───────────────────┐
            │ 【纯逻辑研究区：100% CI 门禁 / 毫秒级】   │
            ▼                                       ▼
 ┌──────────────────────┐               ┌──────────────────────┐
 │  时序状态机 (纯函数) │               │ 假设与蒙特卡洛裁决   │
 │ (跨日累积 / 庄股画像)│               │  (置换检验 / 功效)   │
 └──────────────────────┘               └──────────────────────┘
```

### 1. 核心架构设计

#### A. 第一层：规范事件提取器（Canonical Event Extractor）—— 物理降维
*   **解决痛点**：消除 2.585 TB 与 100 GB SSD 的物理冲突，消灭跨日扫描的 IO 灾难。
*   **机制**：
    *   不搞通用的全量派生表，只定义单一的 **Event Engine**。
    *   以 C4 成本等级对外置盘进行单向流式扫描，将 5,300 万行/天的微观 Tick 数据坍缩为**结构化微观事件流（Microstructure Event Stream）**：
        1. 异常撤单事件（金额超阈值、挂单维持时间短）。
        2. 激进扫盘事件（单笔连续击穿多档）。
        3. 冰山/对倒特征片段（买卖队列微观失衡）。
    *   **数据量剧降**：全市场 1122 天的事件流总大小仅为 **5 ~ 8 GB**（压缩后），可直接 100% 常驻内置 SSD。
    *   所有研究员和 Agent 99% 的时间只需在 SSD 上对这 8 GB 的事件流进行高速迭代，彻底切断对 4 IOPS 外置盘的日常依赖。

#### B. 第二层：基于显式状态机的纯逻辑研究核（Stateful Pure Kernel）
*   **解决痛点**：跨日依赖破坏纯函数、导致无法进 CI 的问题。
*   **机制**：
    *   将因子计算显式拆分为：`step(state_t, event_t) -> (state_t+1, signal_t)`。
    *   因子不是黑盒流式计算，而是**显式状态机（State Machine）**。
    *   输入是纯事件序列，输出是确定性信号。CI 可以用 10KB 的合成事件数据，在 5 毫秒内对跨日 60 天的状态转移做 100% 覆盖的确定性回归断言。

#### C. 第三层：经验置换检验（Permutation Test）替代形式化功效门禁
*   **解决痛点**：小样本偏态分布下，参数化 Power 检验全量报废为 `INCONCLUSIVE` 的问题。
*   **机制**：
    *   废除基于正态假设的参数化功效前置断言。
    *   对稀疏信号采用**事件时间打散置换检验（Event-Time Permutation Test）**：在保持真实波动率和流动性限制的前提下，在时间轴上随机打散开仓信号 1,000 次，计算经验 p-value。
    *   只要实测效应位于置换分布的前 1% 且绝对样本量 $\ge 15$，即判定为确证；若经验统计功效不足，明确输出置换分布的重叠度（Overlap Metric），而非简单抛出冷冰冰的「无定论」。

#### D. 第四层：Git-Backed 外部元数据治理，彻底废除代码自修改
*   **解决痛点**：代码回写注释破坏 `tree_sha` 和 Git 原子性的荒谬设计。
*   **机制**：
    *   代码（`.py`）保持只读与纯粹，严禁任何工具在运行时反向修改源码注释。
    *   所有预注册假设、证据指纹、回测收据，作为**结构化 JSON 资产**统一存放在 `.lineage/<hypothesis_id>/receipt.json`。
    *   收据内容包含：`{git_commit_sha, event_dataset_hash, test_spec_hash, p_value, metrics}`。
    *   CI 门禁只校验：`receipt.json` 内声明的 `git_commit_sha` 是否与当前提交祖先匹配，以及纯逻辑重算结果是否与 JSON 完全一致。

## 七、红队行动总结与最终备忘

1. **放弃在动态语言（Python）中搞「防君子不防小人」的极权安全设计**（污染标记、封闭 AST 谓词、无 `.path` 句柄）。把防线收缩到「数据管道的输入输出契约」上。
2. **直面外置机械盘的物理极限**：唯一的生路是在初期执行单向、批量的「Tick $\to$ 核心事件流」降维抽取，将 2.585 TB 过滤为 SSD 可容纳的 8 GB 黄金事件库。否则任何上层精妙的架构都会被 234 ms/op 的寻道延迟击得粉碎。
3. **拥抱量化研究的探索本质**：预注册与盲验的真正价值在于「记录探索轨迹与多重比较惩罚」，而不是试图在代码里造一个无法修改的审判法庭。让工具提供透明的血缘审计，把定性判断交给具备完整上下文的隔离 Agent。
