# 结构复审：V1 为什么变成平铺，V2 现在哪里已经露出同样的苗头（2026-09-02，过程文档）

> 用户担心 V2 步 V1 后尘。本文用数字回答，评判词汇按 codebase-design：模块 / 接口 / 缝 / 深度 / 杠杆 / 局部性。

## 一、V1 的数字

| 量 | V1 | 含义 |
|---|---|---|
| `src` | 51 文件 · 8,164 行 | 有接口的代码 |
| `scripts` | 1,011 文件 · 198,279 行（顶层 684 + archive 321） | 无接口的代码，**24 : 1** |
| 被 import 过的脚本 | 5 / 684 | 99% 的脚本是终点，不是模块 |
| `tests` | 87 文件 · 11,687 行 | 只覆盖 `src`，即全部代码的 4% |
| `doc` | 1,698 个 md · **113 万词** | 文档是代码的 14 倍；事实登记 F1–F177 |
| `read_parquet` 调用点 | 1,279 | 没有数据访问层 |
| 有真实 fan-in 的模块 | 1（`preserve_schema`，47 处引用） | 全项目只有这一条缝 |
| CI | 无 | 门禁靠纪律 |
| 最大文件 | 1,506 行（脚本） | |

诊断：V1 只有一条缝（列位常量），没有一个深模块。每个脚本各自实现「读 → 过滤 → 聚合 → 判断」，杠杆为零（同一逻辑写 39 遍 `simulate*`）、
局部性为零（修一处要修 39 处）。**文档膨胀到 113 万词不是原因，是结果**：代码没有接口，事实只能写进文档；写进文档的事实又和代码脱节。
这不是「代码写得差」，是「研究即写脚本」+ LLM 高速产脚本的必然产物——单个脚本质量再高也救不了结构。

## 二、V2 的数字（同日）

| 量 | V2 | 评语 |
|---|---|---|
| `src` | 12 文件 · 1,173 行；最大 333 行 | 两个深模块：`ingest()` 一个函数藏 7zz / 校验 / 原子写 / 幂等；`RawStore` 5 个方法藏 pre_buffer / 裁剪 / 还原 / 账本 |
| `tests` | 2,097 行（1.8 : 1） | 今天重写 decode 一行没改测试全过 ⇒ 测的是接口，不是实现 |
| 门禁 | ruff · import-linter · 私有符号 · 词汇 · pytest · diff-cover · crapkit ratchet，全在 CI | V1 一条都没有 |
| `docs` | 1.6 万词 + 三份 HTML；design-log **22 个文件 / 2 天** | ← 苗头 1 |
| 没入库的脚本 | **16 个**（scratchpad：bench × 5、compare × 2、驱动 × 3、扫描 × 2……） | ← 苗头 2 |
| 三份活文档 | 手改 HTML，今天同一事实改了 5 处 | ← 苗头 3 |
| 形状登记 | 机器可读账本 6 条 vs HTML 表 12 行，两处分叉 | ← 苗头 4 |

## 三、V2 已经露出的四个苗头（按危险度）

1. **scratchpad 里的 16 个脚本就是 V1 `scripts/` 的胚胎。** 它们装着真知识（与 V1 逐 row group 比对、全语料形状扫描、提取耗时下界、批量摄取驱动），
   要么变成有接口有测试的模块（`ftbv2.io.raw.audit`：`compare_with_v1(day)` / `shape_scan(days)`；驱动：`ingest_days(archives, root)`），要么下次重写。
   **规则**：仓库永远没有 `scripts/` 目录；任何跑第二次的东西必须变成函数 + 测试；一次性探针死在 scratchpad，**它的结果**进账本或数据表。
2. **三份活文档手改 HTML = 113 万词的病根。** 今天「停牌心跳」这一个事实写了 5 遍（docstring、CONTEXT、词汇表、数据表、架构图）。
   事实单源原则说「能被代码执行出来的事实不得被文档声明」。**规则**：数据表第四节从 `ledger/*.toml` 生成，词汇表从 CONTEXT.md 生成，
   架构图模块表从 `__init__` 的接口签名生成；手改 HTML 的行为本身应被门禁挡住（HTML 与生成结果 diff 非空即红）。
3. **形状登记正在分叉。** `DefectCode` 是代码里的闭合枚举，所以今天发现的 4 个形状全进了 HTML 散文而不是账本。
   V1 的 F1–F177 就是这么来的。**规则**：一个注册表（账本）收全部形状，含良性的；枚举从账本生成或账本用自由码 + 门禁校验。
4. **design-log 两天 22 个文件。** 归档本身无害，危险是事实只活在日志里。**规则**：日志写一次不再改；它记录的每个事实必须在 24 小时内落到活文档 / 账本 / 代码之一，否则视为丢失。

次要：`core.raw` 五个文件（schema / types / ledger / decode / plan）对一个概念偏散，`types.py` 是杂物箱；现在 1,173 行无所谓，
但如果 11 个模块每个复制这个五件套就是 55 个浅文件。规则：模块的公开接口 = `__init__` 导出的名字，其余一律私有（私有 import 门禁已有）。

## 四、真正的结构性风险在研究阶段

V1 的 684 个脚本是研究探针，不是工程代码。V2 的答案是「验证执行器 + 预注册 + 证据包」——研究问题的答案是收据，不是脚本。
但那个模块还不存在。**在它存在之前，每一个研究问题都会诱惑出一个脚本。** 已定第一步（窄实验工厂：扫描闭环 → 账本进 CI → 第一个假设）的顺序是对的：
先有「实验 = 函数 + 收据」的形状，再提第一个假设。

## 五、结论

V1 不是最佳实践，也不是「一堆狗屎」——它是没有缝的仓库在 LLM 产能下的必然形态。V2 的骨架（深模块 + CI 硬门禁 + 纯核 / IO 分离）是对的，
今天暴露的四个苗头全在**代码之外**：脚本、文档、登记、日志。工程上防住它们只需要四条门禁，而且每条都能机械执行。
