## 二、已定决策（Q1–Q9）

### Q1 — V1 的研究结论：命题继承，结论全部降级为待验证

**决定**：命题（研究假设）全部继承；**正面结论与负面结论同等对待，一律不继承**，须在 V2 重新裁决。

**理由（用户裁定，修正了最初的建议）**：不能一刀切地认为「证伪比证实稳健」。V1 的负面结论同样
建立在不干净的数据上，且 V1 内部出现过负面翻正的情况。F182 提供了机制解释：若某特征的信号集中在
涨停日附近（对「准备拉升的庄」这一命题极可能如此），它在 V1 会被**系统性地测成无效** ——
**在这份数据上，负面结论比正面结论更脆弱，而非更稳健。**

**推论**：复验范围是全部命题（含已证伪清单），计算量比初估大一个量级 ⇒ IO 与算力成为可行性问题，非优化问题。

### Q2 — 技术栈：纯 Python

**决定**：纯 Python + Polars / DuckDB。Rust 只在有测量证据证明瓶颈后引入。

**理由**：第三方库生态可用；有提升效能的手段；多一门语言就要多一套质量门禁工具链。
（另：V1 的 `rust_core/` 是空的，只有一个 README，Rust 代码从未存在——不存在「保留」问题，只有「引入」问题。）

### Q3 — 数据复用：只信原始层的字节，派生层全部重算

**决定**：
- 原始层 2.5TB 只读复用，**V2 任何代码对 V1 目录无写权限**（文件系统权限层面保证）。
- 派生层（ad / ice / state / zb_panel / panels 等）**一个字节都不带进 V2**，全部用 V2 代码重算。
- **原始层本身也需先 review**：schema 已被摧毁，且 V1 的摄取代码正确性存疑。
- 后续从 7z 抽取数据依然走 V2 的摄取路径。

**理由**：把 V1 有效的因子计算取出来的难度与成本，高于重新写干净脚本并重算；且算式正确性本身就需要跑全量。

### Q4 — 治理机制：只继承「事实单源」原则

**决定**：V1 的九层看板、三态文档机、doc_source_gate、bootstrap payload 全部不继承。
只继承「事实单源」这一条原则，形式重做。

**判据**：**一个事实如果能被代码执行出来，就不得被文档声明。**

### Q5 — 质量门禁：全部硬拒，不可绕过

**决定**：门禁必须硬拒，能被越过就没有建立的意义。
**纯逻辑核与 IO 必须分属不同模块**，且二者质量标准不同：
- IO：求快，逻辑简单，主要处理异常。
- 纯逻辑：抽象复用、可解释性。

**约束链**：门禁不可绕过 ⇒ 门禁跑在 CI ⇒ CI 跑不了 TB 级数据 ⇒ 能进 CI 硬门禁的只有不碰数据的部分
⇒ **任何既碰数据又含判断的代码两套门禁都进不去，必须拆开**。这条分割线是被门禁要求倒逼出来的，不是风格偏好。

### Q6 — 不存在「V1 复验模块」（用户纠正）

**决定**：V2 建立的是一套**假设验证体系**，不是一个「V1 导入/复验」模块。

- 命题可来自论文、观察、或 V1 的历史工作。
- **V1 只是灵感的来源与可能结果的来源。**
- 真正的运行完全在 V2 上。**运行时不知道 V1 跑出了什么结果、V1 的数据长什么样。**
- 最终结论只依赖 V2 的运行。

### Q7 — IO 与存储：换存储引擎（用户纠正）

**纠正**：内置盘空闲空间**不到 200GB**（非此前误记的 1.79Ti）⇒ 「全量重编码迁入内置盘」方案作废。

**决定方向**：调研**换存储引擎 / 换格式 / 换压缩**。用户判断：当前的格式与压缩格式可能不是最优，
导致计算耗时过长。

**待调研**（子 agent 进行中）：瓶颈究竟是磁盘 IO 还是「ZSTD 解压 + `large_string` 解析」的 CPU 开销；
Parquet 重编码 / DuckDB 原生 / Lance / Arrow IPC 的定量对比；row group 重排收益；
不到 200GB 的内置空间最划算的用途。

**硬约束**：2023 年后 7z 已删 ⇒ 任何重编码只能从现有 `large_string` 反解，不能从 CSV 重来。
反解正确性被证明前，原 preserve 一个字节不得删除。

### Q8 — 代码即文档：结论写回代码注释（用户纠正）

**决定**：长期维护的只有**代码 + 代码注释**，不维护设计文档与运行结果文档（会分散注意力）。

- 设计文档、讨论记录是**实现过程中的副产品**，实现完成后**归档**。
- **代码执行完毕后，把执行结果与结论反写进该代码的注释。** 读注释即可知道：
  之前有没有执行过、执行结果如何、结论是什么。
- **结构化复验台账本身就是一组代码** —— 由代码驱动的一组验证，包含在一个完整的模块里；
  这组代码跑完后，结论写回它自己的注释。
- 应当避免的是反复读过程文档，而应直接读结果代码。
  **如果需要回头读过程文档，说明代码里记的文档不全面或信息不足。**

### Q9 — 不可绕过的保证：GitHub + 分支保护

**决定**：独立 git 仓库 + GitHub 远程 + CI，PR 为唯一合并路径，main 分支保护。

**理由**：门禁不能跑在提交者的机器上、由提交者触发。多 agent 并行写码且 agent 有 shell 权限，
本地 hook（`--no-verify`）必然可绕过。唯一真正不可绕过的形态是：门禁跑在 agent 写不到的地方，
且合并权限由它把持。

## 三、CRAP 调研结论（改变了 Q5 的实现，未改变 Q5 的要求）

**要求不变（硬拒、不可绕过），但 CRAP 撑不起这个重量。**

- **作者本人书面反对把它当质量门禁。** Savoia 2007-10-02 Disclaimer：*"highly experimental in nature"*、
  *"the actual numerical values… should only be considered a starting point"*、
  ***"It should not be abused or misused as a proxy for code quality"***、
  *"the metric should work for you, you should not have to work for the metric"*。
  自称 v0.1，承诺的 0.2 **从未发布**；crap4j.org 冻结在 2011-11。
- **硬门禁的真实语义被隐藏了。** `CRAP = comp²×(1−cov)³ + comp`，覆盖率趋近 100% 时退化为 `CRAP = comp`。
  故「CRAP ≤ 30」等于偷偷给全仓上了「圈复杂度硬上限 30」，且阈值 30 处的断点无任何依据。
- **数学上不可聚合。** JaCoCo 项目 lead 因此拒绝实现（issue #196, `declined: wontfix`）：
  *"Due to the non-linear nature I'm afraid not."* ⇒ 任何模块级/全仓级 CRAP 均无意义，只能逐函数取 max。
- **零学术验证** —— 不是被驳倒，是从未被认真评估过。
- **整类静态产品度量判别力弱**：Majumder/Mody/Menzies (2022) EMSE，722,471 commits / 700 项目 ——
  过程度量 recall 98% / AUC 95%，**静态产品度量 recall 44% / AUC 54%（接近抛硬币）**。
- **Maintainability Index 明确不用**：Borg et al. (2024) ICSME —— 纯 LOC 阈值 AUC 0.95，MS-MI 仅 0.89；
  SonarQube TD Ratio 默认阈值 AUC 0.60，比随机还差。

**替代方向（有证据支撑的确定性门禁）**：
- **门增量，不门全局** —— Google 成文立场：per-commit 覆盖率目标 99% 合理、90% 为下限；全仓 >90% 不值得。工具 `diff-cover`。
- **断言覆盖率才是因果变量**（Zhang & Mesbah 2015 FSE）；行覆盖率是有损代理 —— 门代理正是 Goodhart 最易惩罚的结构。
- **变异测试须增量 + 强过滤** —— Google：变异体从 820 降到中位数 7 才可用。
- **Google 对 blocking 静态检查的三条标准**：可操作易修复 / 无「有效误报」/ 只管正确性不管风格。CRAP 至少违反后两条。
- 若仍要上 CRAP：用 **crapkit**（0.4.11，14 个版本，MIT，有文档）而非 crap4py（0.1.1，无 license），
  且只用 **baseline/regression 模式**（只拦让情况变差的提交），上线前须读源码验证其覆盖率短路漏洞。

**更重要的转向**：V1 的四起真实事故 —— 涨停日被删、`-0.12` 常量漂移致 20pp 误差、preserve 表头丢失、
深模块被私有符号捅穿 —— **没有任何一个能被 CRAP 拦住**。它们全部是**数据语义与统计推断纪律**的失效。
本项目正确的门禁方向应是：同一常量全仓只出现一次 / 路径字面量出现次数上限为 1 /
纯逻辑核不得 import IO 模块 / 不得跨模块 import 下划线私有符号 / 派生数据必须带血缘 /
预注册判据必须在接触数据前落盘。这些均可机器判定、零误报、直接对应真实事故。

## 六、第二批决策（Q10–Q15）

### Q10 — 「命题」改称「假设」；层级不用 L1/L2/L3

**决定**：全项目统一使用**假设（Hypothesis）**，废弃「命题」（太抽象、无指向性）。
假设分三个层级：**因子 / 组合 / 策略**（最终命名待确认）。

**形态**：机器可读的预注册块 + 代码执行体，**预注册块的哈希在执行前固定并写入证据指纹** ——
改判据不被禁止，而是被检测到。

**⚠️ 否决了 `L1/L2/L3` 这套编号**（核对 V1 实际定义后）：

| 记号 | V1 的实际含义 | 证据 |
|---|---|---|
| `L2` | **Level-2 数据本身**（快照/逐笔成交/逐笔委托/日级聚合/bar 级/委托生命周期）| 九层看板卡片 |
| `L1` | 日级 / 因子确认层 | `confirmed_factors.json`：「已确认因子数（过完 L1 判 PASS 的因子）」|
| `L3` | 把幸存候选写成**可证伪的赚钱解释**（因果链），非策略执行 | 「L1/L2 负责研究筛选，L3 负责…，L0 以上才进入交易」|
| `L0/Pool/Buy` | 交易层 | `gate_rule_m3.json` |

否决理由：① `L2` 在本项目已等于「Level-2 行情数据」，是数据源本身的名字，复用造成三义；
② V1 的 L1/L2/L3 是**流程阶段**（初筛/入选/签发），用户表达的是**对象层级**，两条不同的轴；
③ `L0` 比 `L1` 更靠近交易，编号方向与层级高低不对应。

**补充约束**：三层的**判据类型根本不同**（因子→IC/分层/置换检验；组合→多重检验/共线性；
策略→路径依赖/滑点/资金约束），且三层有依赖 ⇒ **假设不是平表，是一个 DAG**。

### Q11 — V1 只进队列，不进判据

**决定**：只搬**假设**、剥离**结论**。搬入时按 V1 的成败判断排优先级：**V1 认为成功的优先验证，
其次才是 V1 认为失败的**。用户原话：**「V1 不能白干，但 V1 干的不能全信。」**

**角色切分（解决排序与盲验的冲突）**：为假设队列排优先级的角色**可以**看到 V1 的成败判断
（只影响先验哪个，属资源分配）；**编写预注册判据的角色不得看到**（会污染结论）。

**两类 V1 遗产分开处理**：
- **研究结论** → 被污染的判断，只作灵感，剥离后进候选队列。
- **数据缺陷事实**（F182/F40/F19/F61/F62…）→ 关于世界的事实，**必须知道**，
  且应落成**摄取层的校验代码与断言**，不是 md。

### Q12 — 结论由工具写回，解读由异构 agent 产出

**决定**：工具自动回写，**且只写数据**。理由：自己设计的代码执行完毕后，可能因设计者偏见对结果有异常解读。

| | 谁产出 | 性质 |
|---|---|---|
| **裁决** | 工具**机械计算**（预注册判据 + 数据 → 三态）| 不可解读、不可争辩。预注册的全部意义即在此 |
| **解读** | **异构 agent**（未参与实现）| 「这意味着什么、值不值得继续、下一个假设是什么」，明确标注为非权威 |

**防陈旧（硬要求）**：结论块必须含证据指纹〔代码哈希 + 数据版本 + 判据哈希〕，
**与当前实际值不符即 CI 硬拒** —— 要么重跑，要么显式标记过期。注释不可能默默撒谎。
格式必须机器可解析。副作用：源文件被机器修改 ⇒ **git 历史即实验台账**。

### Q13 — 存储分层：刻意推迟

**决定**：现在不定。理由（用户）：计算层到底什么是派生、派生多少、怎么派生全都不知道，
所以定不了；分层是从结构与规范衍生出来的，不是先验的。

**现在该定的是**：数据计算的格式、如何优化速度、底层结构与规范。
**待验的核心问题**：能否通过压缩与数据结构优化，把原始数据也拿进来？
（IO agent 正在验的关键假设：瓶颈究竟是磁盘 IO，还是「ZSTD 解压 + `large_string` 解析」的 CPU 开销
—— 若是后者，换介质完全无效，只有换编码有效。）

### Q14 — CI：托管 + 自托管 runner 各担其责

**决定**：两者都要，分工不同。GitHub 托管 runner 跑纯逻辑核门禁；自托管 runner 跑碰数据的重活。

**硬约束**：自托管 runner 必须以**独立 OS 用户**运行，写码的 agent 无 sudo、无法写 runner 工作区；
**合并决定权只能由 GitHub 侧持有**，自托管 runner 只上报结果。否则退化回「跑在提交者机器上」。

### Q15 — 标的宇宙：沿用主板

**决定**：沿用 `000/001/002/003/600/601/603/605`。不扩创业板/科创板/ETF/基金/B 股。

**理由（用户）**：ETF 与主板的相关性尚未探索出来，已有数据还没试完；多的处理不过来，也没有精力。

**已知代价**：2023-01 → 2026-07 的创业板（1396 只/天）与科创板（612 只/天）逐笔数据永久不可恢复。
唯一还能重抽的窗口 = 幸存的 2022 全年 242 天 + 202608 的 14 天（685 GB 7z），该窗口不因本决定而删除，
但随磁盘衰减。

**附带记录（假设候选，非本期工作）**：ETF / 基金与主板的相关性是否存在、是否值得为此存储更多数据。
