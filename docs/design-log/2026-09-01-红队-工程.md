结论：**第五节最可能失败**。它把太多东西寄托在流程纪律、多 agent 分工、收据、代码注释和“不可绕过门禁”上，但真正的防线不够物理。第七节明显更强，因为它把成本、扫描计划、缺陷账本、预算做成可检查接口。第八节最强但最危险：它把问题收敛到少数高复杂接口，失败形态会从“到处烂”变成“核心接口没人敢改”。

**总判**
1. **第五节会先退化回 V1**：因为它仍允许“我临时读一天数据看一下”的旁路脚本自然生长。
2. **第七节更可建**：成本等级、`plan -> execute -> reduce`、缺陷账本进 CI，这些是真约束。
3. **第八节工程约束最硬**，但有几条“聪明机制”会变成维护炸点，尤其污染标记、代码注释写回、过窄但复杂的扫描接口。
4. 最好的第四版不是继续切模块，而是先建一个**最小闭环实验工厂**：只支持 1 个 stream、20 个交易日、3 个假设、完整跑通血缘/成本/裁决/回归，再扩大。

**第五节的问题**
`原始层访问` 的深度有一半是真的，一半是假的。它想隐藏路径、`pre_buffer`、下推、`column_N`、dtype、时间归一化、枚举、NUL、缺陷表、性能契约。问题是：这些不是同一种知识。调用者仍然必须知道“我要哪些字段、哪些天质量可用、哪些缺陷会改变样本、哪些字段能下推、哪些请求会全扫”。接口表面是 `read(...)`，实际接口是一整本操作手册。

`删除测试 N≈1,123` 被高估。你不是删除 1,123 个调用点，而是把 1,123 个调用点压成了 1 个万能入口。旁路脚本不会消失，它会变成：

```python
raw.read("trades", days, fields=[...]).filter(...)
```

然后每个研究脚本继续自己做时间过滤、样本过滤、异常日处理、聚合口径。V1 的事故不是只有 `read_parquet` 分散，而是**读完之后的语义判断分散**。

`ingest` 的不变量做不到你写的那么硬。2023-01 到 2026-07 原始 7z 已删除，你没法逐字节 round-trip，也没法对源 CSV 做真行数比对。对 77% 数据，ingest 只能验证 preserve 层自洽，不能验证“原始无损”。所以这个模块的接口如果承诺“原始层逐行无损副本”，就是伪承诺。

`materialize(table, days, force)` 里的 `force` 是退化入口。所有“血缘不匹配但我知道没问题”“账本错了先强跑”“这次只是探索”的压力都会集中到 `force`。只要 `force` 存在，它就会被脚本包一层，最后变成 V1 的 `audit_v4.py`。

“builder 不得过滤行，只能加标记列”也会误伤。事件表、候选池、成交簇、撤单簇本来就可能是稀疏派生对象。强制保留全行会把派生层打爆，尤其你自己承认 tick 级特征不压缩。正确规则应该是：**不得在未声明样本宇宙前删除行**，而不是一律不得过滤。

`验证执行器` 是一个 god module：解析 DAG、取数、注入、指纹、写回、陈旧检测、盲验。它的接口看似两个方法，实际要理解整个研究生命周期。这个模块一旦出 bug，所有裁决都一起失效。

`Hypothesis` 用 Python 对象不是银弹。Python 对象引用不能天然解决静态循环检测、稳定哈希和重命名安全。动态 import、闭包、默认参数、全局常量、依赖库版本、环境变量、函数源码格式化，都会影响“同一个假设”的身份。YAML 不是问题本身，**无稳定 AST/IR 才是问题**。

**第七节的问题**
第七节强在成本等级和扫描计划，但它最大风险不是只在 100GB SSD，而是**横向模块会把业务语义打散**。每个假设切片都要穿过 H1-H6，一旦切片薄，研究者会嫌慢，开始写“临时直连 H1/H2 的分析脚本”。

`max_cost_class` 必填会产生有效误报。研究早期经常不知道请求是 C2 还是 C3，计划器估错一次就硬失败。久了以后大家会统一写 `max_cost_class=C4`，门禁失去信息量。更好的做法是强制写 `cost_budget_id`，预算来自队列/周配额，而不是让每个调用者手填等级。

“IO 段不允许基于数据内容分支”太绝对。真实扫描会遇到缺陷日、停牌、空表、半日交易、损坏 row group、枚举漂移。完全禁止内容分支，会把异常处理推到 reduce 阶段，产生更大的中间数据和更差的错误定位。应改成：**IO 阶段只能基于缺陷账本和元数据分支，不能基于研究统计结果分支**。

H4 “明确不建通用回测框架”是对的，但容易走反面极端。你不需要大而全框架，但需要一个非常窄的执行语义核：撮合、滑点、涨跌停、停牌、成交量约束、路径依赖。否则 39 个 `simulate*` 会以“这不是框架，只是本假设专用执行器”的名义重生。

H5 `bundle` 作为解读者唯一输入通道是对的，但盲验仍会漏。字段名、假设命名、样本区间、特征选择本身就会泄露 V1 历史偏好。你挡不住“灵感污染”，只能记录污染级别，不能宣称物理保证。

H6 100GB 硬上限会制造有效误报。很多 tick 级中间产物短期很大、长期可丢。硬拒写入会逼人写到仓库外、外置盘临时目录或 notebook cache。预算应区分：持久派生、短期 scratch、可重建缓存、一次性审计产物。只给一个 100GB 阀门太粗。

**第八节的问题**
不透明句柄能减少路径字面量，但挡不住旁路。任何能实际执行扫描的代码最终都知道底层 URI、文件描述符或 pyarrow filesystem。没有 `.path` 属性只是提高正规接口纯度，不是安全边界。它还会伤害调试：错误日志、审计、人工恢复都需要可定位的物理位置。正确做法是：生产接口返回句柄，审计接口可受控解析路径并记录调用者。

封闭谓词构造子是对的，但会迅速膨胀。量化研究会要复杂条件：集合、区间、交易时段、跨日窗口、停牌状态、涨跌停状态、盘口状态。你如果只给少数构造子，研究者会绕开；如果不断加构造子，扫描器接口变成小型查询语言。需要把谓词分两层：**可下推谓词**和**扫描后过滤表达式**，并在计划里明确哪些部分不能下推及其成本。

“补丁必须在投影之后、任何过滤之前应用”方向是对的，但会遇到字段依赖问题。某些缺陷补丁可能需要原始列、质量列、stream 交叉信息。调用者投影没选这些列时，补丁无法执行。解决方式：投影要分为用户字段和补丁所需字段，扫描器自动扩展内部投影，返回前再裁剪。

“回测内核签名没有 `stop_loss`，只有参数集句柄”会防住散装 kwargs，但会拖慢研究。参数台账如果太重，大家会建 `tmp_param_set_20260901_7`。你需要的是：参数集可以临时创建，但必须内容寻址、不可变、自动进入多重检验族，而不是禁止临时参数。

“裁决器必须一次看到整批假设”统计上对，但工程上很难。什么叫“整批”？同一主题？同一数据窗口？同一研究季度？同一人脑里想过但没写下来的假设算不算？这个机制会被通过拆 family 规避。应要求每个假设声明 `correction_family_id`，并对 family 的新增、关闭、分裂做审计。

污染标记是最像安全剧场的一条。进程读取 V1 区就污染后续证据，听起来硬，但实际做不到完整传播：复制文本、截图、口头记忆、另一个进程、notebook、缓存、shell history 都能绕过。它还会误伤工具链，比如索引器、备份、全文搜索。更现实的机制是：隔离 V1 材料，限制可读角色，并要求假设来源声明污染级别；不要假装 taint tracking 能解决人脑污染。

CI 断言 pyarrow IO 字节数也会有效误报。pyarrow 版本、压缩块、row group 大小、metadata 读取策略、filesystem adapter 都可能改变计数。字节数适合作回归指标，不适合硬门禁。硬门禁应断言扫描计划；字节数用阈值区间和趋势告警。

**多 Agent 会怎么崩**
设计 agent 写的接口会过度理想化，实现 agent 会补隐藏前提，测试 agent “不看实现”只会测文字表面，增强 agent 会扩大接口，review agent 最后看到的是一堆互相正确但整体不工作的产物。

具体退化路径：

1. 接口评审时人签字，因为接口看起来窄。
2. 实现时发现真实缺陷太多，于是加内部 escape hatch。
3. 测试 agent 没看实现，漏掉 escape hatch 的语义后果。
4. 增强 agent 为了性能加缓存、批处理、`force`、`skip_bad_day`。
5. review agent 只能查局部 diff，看不到研究结论是否被污染。
6. 两个月后，每个假设都有自己的“薄 wrapper”，V1 的 684 个脚本换了名字回来。

多 agent 适合并行做粗活，不适合把责任切碎。这里应该只有三个角色：接口 owner、实现 owner、敌对 reviewer。验证可以异构，但必须验证同一个可执行契约，而不是各写各的理解。

**收据机制会失效**
HMAC 收据只能证明“某个持 key 的 runner 为某个 `tree_sha("src")` 签过名”，不能证明：
- 跑的是正确数据。
- 数据挂载没错。
- 参数没被偷偷放在 `scripts/`、环境变量或外部文件。
- runner 没复用旧缓存。
- HMAC key 没泄露。
- 结果有科学意义。

`tree_sha("src")` 还太窄。改 `pyproject.toml`、lockfile、schema ledger、缺陷账本、参数台账、SQL、notebook、测试夹具，都可能改变结果。收据应该绑定 **source tree + dependency lock + data manifest + defect ledger + parameter set + runner image digest + command spec**。

自托管 runner 也会成为瓶颈和权力中心。队列积压后，人会绕过；runner 状态漂移后，结果不可复现；挂载或权限出错后，会出现“CI 绿但研究假”的情况。runner 必须是 cattle，不是 pet：固定镜像、只读数据挂载、无交互 shell、作业级 scratch、完整输入输出 manifest。

**结论写回代码注释是坏主意**
它会制造更大的麻烦。代码注释是源码，不是实验数据库。写回会导致：
- 合并冲突。
- 无意义 diff 淹没 review。
- rerun 后源码变脏。
- cherry-pick/backport 困难。
- 同一假设多样本区间、多 runner、多版本结果塞不下。
- 格式化或移动代码导致证据指纹失配。
- CI 因“注释陈旧”拒绝非语义改动。

替代方案：结论写到内容寻址 evidence bundle，代码里只保留稳定 hypothesis id 或 prereg hash。CI 校验“当前代码声明的 prereg hash 是否存在对应 bundle”，不要把 bundle 内容写回注释。

**最容易被关掉的门禁**
- `diff-cover` 增量覆盖率：重构、移动文件、生成代码会大量误伤。
- ruff 复杂度：Polars 表达式和统计逻辑天然密集，容易被拆成更差的小函数。
- 禁跨模块 import 私有符号：测试、性能优化、内部 schema 工具会首先撞上。
- 金标准回归：Polars/pyarrow 版本、浮点、排序稳定性、字典编码都会造成“合理变化”。
- 血缘校验：如果 hash 包含太多环境细节，会频繁误报；包含太少又没意义。
- 字节数门禁：库版本和 parquet metadata 行为会抖。
- “无 override” 缺陷策略：账本错时无法救火，最后会在仓库外绕过。
- “builder 不得过滤行”：存储爆炸后必被关。
- 全局多重检验批裁决：阻塞研究节奏后会被拆 family 绕过。

**语义和方法论漏洞**
预注册在量化研究里最容易被“假设生成阶段”规避。你可以不改判据，只改特征、样本宇宙、异常日处理、调仓频率、成本模型、候选池定义。每一步都不是判据，但都能改变结论。

三态裁决是对的，但“功效不足不许推翻”会被滥用成永不失败。稀有信号项目尤其危险：每个烂假设都可以说样本不够。你需要第四态或附加标签：`abandoned_for_cost`、`underpowered_but_negative`、`not_worth_more_data`。否则队列会堆满无定论尸体。

证据指纹证明可追溯，不证明有效。错误 schema、错误缺陷补丁、错误幸存者处理、错误涨跌停处理，都可以被完美指纹化。

盲验挡不住研究者先验。V1 成败结论不能给预注册者，但 V1 留下的字段选择、命名、样本期、事故修复方式都会泄露。真实机制应该是记录污染，而不是承诺纯净。

**第四种切法**
不要先建完整架构。先建“窄实验工厂”：

1. `Catalog`：唯一数据目录、schema version、缺陷账本、路径句柄。
2. `Planner`：纯扫描计划，带成本预算和可下推谓词解释。
3. `Scanner`：唯一 IO 执行点，单读者锁。
4. `DatasetBuilder`：只产内容寻址 dataset ref，绑定血缘。
5. `Criterion`：稳定 IR，不直接用任意 Python 对象当哈希主体。
6. `Adjudicator`：批量裁决，按 correction family。
7. `EvidenceStore`：bundle 是唯一结论落点，不写源码注释。
8. `ExecutionKernel`：窄版回测核，参数集内容寻址。

第一步：**只做 H1/H2/H3 的最小闭环**。用 200–500MB 合成语料，加 20 个真实交易日抽样，跑通：
`request -> plan -> cost check -> execute -> defect patch -> canonical frame -> evidence manifest`

时间判断：
- 3–5 天能看到第一个可运行扫描闭环。
- 1–2 周能把缺陷账本、成本计划、合成语料金标准接进 CI。
- 3–4 周能跑第一个真实 prereg 假设。
- 在第一个假设跑通前，不要建多 agent 流水线、收据写回注释、全量自托管 runner 编排。这些现在都会先制造流程复杂度，而不是降低失败概率。
