该实现虽然在纯计算计划与 IO 隔离、行组剪裁观测性及缺陷账本数据化上建立了良好骨架，但在短时间缺陷判定、并发原子写、跨 Stream 计划校验及行组元数据容错等关键缝隙处存在致命逻辑穿透与崩溃漏洞。

### 【致命】

1. **`short_time_present` 误将空串/短字符归因于 `time_6digit` 且判据与解码能力脱节**
   - **证据**：`decode.py:84` 与 `store.py:68`
     ```python
     # decode.py:84
     def short_time_present(column: str) -> pl.Expr:
         return (pl.col(column).str.strip_chars().str.len_chars() <= 7).fill_null(False).any()

     # store.py:68
     if time_column in raw.columns and "time_6digit" not in fp.patches and raw.select(short_time_present(time_column)).item():
         raise RuntimeError(f"time_6digit 未登记：{fp.day:%Y-%m-%d} {request.stream} 出现六位时间")
     ```
   - **攻击路径**：若数据中某行时间为空串 `""`、空白符 `' '` 或 7 位异常串，去空后长度为 0 或 7，均满足 `<= 7`。`RawStore.execute` 会直接抛出 `RuntimeError: time_6digit 未登记...` 误判。若运维因此在账本中登记 `time_6digit`，在 `to_time_ms` 中 0 或 7 位长度依然无法被 9/6/5 位分支命中，直接落入 `otherwise(None)` 产生静默 `null`，导致错误诊断与异常掩盖。
   - **修正**：将短时间存在性校验严格限制在 5 位或 6 位纯数字，避免与空值或脏数据混淆：
     ```python
     def short_time_present(column: str) -> pl.Expr:
         raw = pl.col(column).str.strip_chars()
         return raw.str.contains(r"^\d{5,6}$").fill_null(False).any()
     ```

2. **`_atomic_write` 全局通配清理破坏并发写隔离，导致并发任务文件被误删**
   - **证据**：`ingest.py:206-212`
     ```python
     def _atomic_write(target: Path, write) -> None:
         for stale in target.parent.glob(target.name + "*.tmp"):
             stale.unlink()
         tmp = target.with_name(f"{target.name}.{os.getpid()}.tmp")
         write(tmp)
         os.replace(tmp, target)
     ```
   - **攻击路径**：在多进程并发摄取或重试场景下，当进程 A 正在向 `date=20240101.parquet.1001.tmp` 写入数 GB 数据时，若另一并发进程 B 触发同路径写入，B 的 `target.parent.glob(target.name + "*.tmp")` 会直接将进程 A 正在写入的临时文件 `unlink` 删除。进程 A 在 `os.replace` 时将遭遇 `FileNotFoundError` 崩溃，破坏原子写不变量。
   - **修正**：移除写入前的通配符清理，改用带 UUID 的私有临时文件名，并仅在当前上下文异常时清理自身临时文件：
     ```python
     def _atomic_write(target: Path, write) -> None:
         tmp = target.with_name(f"{target.name}.{os.getpid()}.{uuid.uuid4().hex[:8]}.tmp")
         try:
             write(tmp)
             os.replace(tmp, target)
         except Exception:
             tmp.unlink(missing_ok=True)
             raise
     ```

### 【严重】

1. **`plan()` 未校验 `Request` 与 `Catalog` 的 Stream 一致性，且对非完整 Catalog 产生静默误归因**
   - **证据**：`plan.py:27-37`
     ```python
     def plan(request: ReadRequest, catalog: Catalog, ledger: DefectLedger) -> ScanPlan:
         output_tail, projected = _output_and_projection(request)
         by_day = {meta.day: meta for meta in catalog.files}
         missing = set(catalog.missing_days)
         files = tuple(
             _file_plan(request, by_day[day], ledger, projected)
             for day in request.days
             if day not in missing and day in by_day
         )
         return ScanPlan(request, files, (*RESERVED, *output_tail), _post_filters(request), ledger.sha256)
     ```
   - **攻击路径**：
     1. 若调用方将 `orders` 的 `request` 与 `trades` 的 `catalog` 混传，`plan()` 完全未校验 `request.stream == catalog.stream`，将按 `orders` 的物理投影去计划读取 `trades` 文件，导致后续执行层静默解析出完全错位的字段类型与数据。
     2. 若传入的 `catalog` 仅包含部分天元数据，不在 `catalog` 范围内的 `request.days` 会被静默忽略；后续 `attribute_gaps` 会将其全部标记为 `GapReason.DAY_MISSING`，违反「查不到 = 没有 被禁止」原则。
   - **修正**：在 `plan()` 入口增加严格的契约校验：
     ```python
     if request.stream != catalog.stream:
         raise ValueError(f"Stream 不一致：request={request.stream} vs catalog={catalog.stream}")
     catalog_days = {meta.day for meta in catalog.files} | set(catalog.missing_days)
     uncovered = set(request.days) - catalog_days
     if uncovered:
         raise ValueError(f"Catalog 未覆盖请求的全部交易日: {sorted(uncovered)}")
     ```

2. **`_row_group_meta` 缺失 min/max 保护导致 `TypeError` 崩溃或非空 Row Group 静默漏读**
   - **证据**：`store.py:100-106` 与 `plan.py:84-90`
     ```python
     # store.py:100-106
     def _row_group_meta(meta: pq.FileMetaData, index: int, symbol_index: int) -> RowGroupMeta:
         group = meta.row_group(index)
         stats = group.column(symbol_index).statistics
         byte_size = sum(group.column(i).total_compressed_size for i in range(group.num_columns))
         if group.num_rows == 0 or stats is None:
             return RowGroupMeta(index, group.num_rows, byte_size, "", "")
         return RowGroupMeta(index, group.num_rows, byte_size, stats.min, stats.max)

     # plan.py:84-90
     chosen = tuple(
         rg for rg in row_groups
         if rg.num_rows > 0 and any(rg.symbol_min <= s <= rg.symbol_max for s in symbols)
     )
     ```
   - **攻击路径**：
     1. 当 Parquet 文件中包含 statistics 对象但 `stats.has_min_max` 为 `False` 时，`stats.min` 为 `None`，`_select_row_groups` 中执行 `None <= s` 会直接引发 `TypeError: '<=' not supported between instances of 'NoneType' and 'str'`。
     2. 若非空 row group 的 statistics 缺失（`stats is None`），`symbol_min` 被设为 `""`，`"" <= s <= ""` 恒为 `False`，导致该非空 row group 在按标的过滤时被直接丢弃，造成真实数据漏读。
   - **修正**：严谨处理统计值缺失情况，并在无统计元数据时保守保留 row group（禁止裁剪）：
     ```python
     has_stats = stats is not None and getattr(stats, "has_min_max", False) and stats.min is not None and stats.max is not None
     min_val = stats.min if has_stats else None
     max_val = stats.max if has_stats else None
     ```
     在 `_select_row_groups` 中：
     ```python
     chosen = tuple(
         rg for rg in row_groups
         if rg.num_rows > 0 and (
             rg.symbol_min is None or any(rg.symbol_min <= s <= rg.symbol_max for s in symbols)
         )
     )
     ```

3. **`ingest` 内存累积三个 Stream 全量 DataFrame，引发峰值内存暴涨与 OOM**
   - **证据**：`ingest.py:65-72`
     ```python
     frames: dict[Stream, pl.DataFrame] = {}
     receipts: list[StreamReceipt] = []
     for stream in STREAMS:
         frame, receipt = _load_stream(stream, csvs[stream])
         frames[stream] = frame
         receipts.append(receipt)
     sizes = _write_streams(root, day, frames)
     ```
   - **攻击路径**：全市场单日 `orders`、`trades`、`xinqing` 三个流展开为全字符串 DataFrame 时，总内存占用可达 30GB~50GB+。`ingest` 将全部三流 DataFrame 同时累积在 `frames` 字典中才统一落盘，使内存峰值放大 3 倍，极易在生产容器中直接被 Linux OOM Killer 强杀。
   - **修正**：改为单流流水线模式，单流加载后立即落盘并释放 DataFrame，最后汇总元数据写入 manifest：
     ```python
     receipts = []
     sizes = {}
     for stream in STREAMS:
         frame, receipt = _load_stream(stream, csvs[stream])
         sizes[stream] = _write_single_stream(root, day, stream, frame)
         receipts.append(receipt)
         del frame
     ```

### 【建议】

1. **`to_int64` 的 `integer_like` 正则未剥离空白，导致带空格超精度数值逃逸**
   - **证据**：`decode.py:27-34`
     ```python
     exact_int = raw.cast(pl.Int64, strict=False)
     integer_like = raw.str.contains(r"^[+-]?\d+$")
     loses_integer_precision = integer_like & (exact_int.is_null() | (candidate != exact_int))
     ```
   - **攻击路径**：若输入带有首尾空格的超精度整数串（如 `' 9007199254740993 '`），`raw.cast` 成功但 `integer_like` 判定为 `False`，导致 `loses_integer_precision` 失效，错误返回精度失真后的浮点转换值。
   - **修正**：在 `to_int64` 入口对 `raw` 执行 `.str.strip_chars()`。

2. **`_load_stream` 对 0 字节文件缺乏前置拦截，后续 DataFrame 纵向拼接易崩溃**
   - **证据**：`ingest.py:166-175`
   - **攻击路径**：若归档中存在 0 字节异常 CSV 文件，`header` 为空串，`len(header.split(","))` 为 1，解析出的 1 列 DataFrame 与其他正常标的的 58 列在 `pl.concat` 时将抛出 Schema 不一致异常。
   - **修正**：在读取字节流后断言 `if not data or newline < 0: raise RuntimeError(f"CSV 损坏或无表头: {path}")`。
