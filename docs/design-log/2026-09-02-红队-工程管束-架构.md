总判：该方案企图用机械指标与自动化硬门禁遏制混乱，但混淆了先验契约与后验产物，在核心边界制造了自我指涉的死锁，并将核心域逻辑合法泄露至外围工具层，上线即会引发协作瘫痪与规避性代码形变。

### 【致命】

#### 1. 活文档裁决权与代码生成产物的循环死锁
* **证据**：
  * R2：“架构图模块表从各模块 `__init__` 的导出名与 docstring 生成。”
  * R4：“活文档（三份 HTML + CONTEXT.md + `docs/STATE.md`，唯一裁决）。”
  * 背景与原则：“图上没有的模块视为不存在。”
* **攻击路径**：
  架构规范在“先验契约”与“后验镜像”之间发生因果倒置。
  * **死锁路径**：若要新增合法模块 $M$，按“图上没有视为不存在”，必须先在架构图中登记；但架构图是由代码 `__init__` 反向生成的，且 CI 强制执行逐字节 diff。此时开发者陷入先有鸡还是先有蛋的死锁：先加代码，在生成文档前属于“图上不存在的非法模块”；先改 HTML，CI 重新生成后与手动修改产生 diff，直接报红。
  * **防御穿透路径**：任何人在 `src` 滥写浅模块并在 `__init__` 暴露，生成器会机械地将其合入 HTML 架构图并绿灯通过。“图上没有的模块视为不存在”对代码膨胀完全丧失防守能力，架构图沦为代码混乱的自动盖章机。
* **修正**：
  剥离 HTML 架构图的裁决权。将模块拓扑与可见性边界移至独立于实现的静态声明文件 `architecture.toml`（或基于 `import-linter` 的 contract 配置）。
  * 判据：CI 仅检验 `src/**/` 的模块拓扑与依赖是否为 `architecture.toml` 声明集合的严格子集；HTML 架构图降级为纯只读展示层，不再作为裁决依据。

#### 2. “单调用者下沉”导致核心 IO 逻辑泄露至工具层
* **证据**：
  * R1：“`tools/` 是唯一放可执行入口的目录... 不含判断逻辑（有第二个调用者的逻辑下沉进 `src`）。”
  * R1：“`tools/ingest_days.py`（批量摄取驱动：非规范文件名跳过、磁盘余量下限、幂等、逐日日志）。”
* **攻击路径**：
  “有第二个调用者才下沉”在接口边界开出了巨大后门。
  * 摄取驱动程序在系统生命周期内通常长期只有 CLI 这一个调用者。按此规则，“非规范文件名跳过规则”、“磁盘余量水位熔断保护”、“数据摄取幂等性状态机”等原本属于核心 IO 层的核心不变式与域逻辑，全部被合法留在 `tools/ingest_days.py` 中。
  * 攻击者可借此逃避 `src` 的深模块检查与七道硬门禁，将大量脏逻辑、重试状态机与边缘修复分支堆砌在 `tools/` 单脚本内（只需每文件切在 300 行内并补一个合成 fixture 测试），直接击穿“纯逻辑核与 IO 层分离”的设计意图。
* **修正**：
  废除“第二个调用者”判据。重定义 `tools/` 的深度契约：`tools/` 内所有入口必须为无状态的薄适配器（Thin CLI Wrapper），严格限定只做命令行参数解析（argparse）、调用 `src` 顶层暴露的服务接口、格式化标准输出。
  * 判据：`tools/*.py` 内禁止出现业务决策控制流；“文件名规范校验器”、“磁盘空间探针与熔断”、“摄取幂等管理器”强制作为 `src.io.ingest` 的内部组件。`tools/` 单文件行数阈值收紧至 80 行。

### 【严重】

#### 1. 账本强不可变与枚举单向包含导致类型系统死锁与不可逆污染
* **证据**：
  * R3：“`DefectCode` 枚举从账本校验：CI 检查账本 code 集合 ⊆ 代码枚举；账本 **append-only**：已存在条目的 id / code / days 只能增不能删改。”
* **攻击路径**：
  * **代码枚举永久不可回收**：一旦在 `ledger/defects.toml` 登记了一个临时或误判的缺陷代码 $C_1$，由于账本 append-only 禁止删除修改历史行，且 CI 强制要求 `ledger.code ⊆ DefectCode`，则代码中的枚举值 $C_1$ 永远无法被重命名、废弃或删除。任何试图清理过时枚举的重构均会被 CI 永久拦截。
  * **无 tombstone 逃逸**：当出现缺陷合并或被证明是误报时，开发者无法在账本中注销，只能不断追加带后缀的衍生条目，造成账本与枚举的双重语义污染。
  * **文本级 diff 误杀**：基于 `git diff` 检查“只能增不能删改”，一旦 TOML 格式化工具重排了字段顺序或调整了数组换行，将产生删除行 diff，导致合法的格式整理被 CI 误判击杀。
* **修正**：
  * 在账本条目中引入显式生命周期状态：`status = "active" | "deprecated" | "superseded"` 与 `superseded_by = "ID"`。
  * 门禁判据改为：`ledger.active_codes ⊆ DefectCode`；废弃代码允许从当前活动枚举移入 `DeprecatedDefectCode` 或彻底解耦。
  * 门禁校验工具改为基于 TOML 结构化 AST 的语义比较脚本，禁止使用文本级 `git diff`。

#### 2. 全局机械硬指标（文件数/词数硬顶）诱发公地悲剧与对抗性破坏
* **证据**：
  * R4：“门禁：design-log 顶层文件数 ≤ 30 即红（逼归档）；`docs/` 总词数 ≤ 5 万即红。”
* **攻击路径**：
  * **无辜 PR 全局阻塞**：当 design-log 顶层文件累积到第 31 个时，系统中所有正在提交的功能性 PR（即使仅修改了一行无关核心逻辑）将全部被 CI 挂红。系统陷入公地悲剧，开发者为了尽快合入代码，会盲目将他人未消化的日志直接丢入 `archive/`。
  * **对抗性压缩导致事实丢失**：5 万词的全局硬顶无法约束信噪比。随着模块复杂度自然演进，一旦总词数逼近上限，开发者将通过缩写变量、删除关键上下文、抹去边界 case 说明或将文档隐藏为散落的代码长注释来规避门禁，重新退化为 V1 的“事实丢失”。
* **修正**：
  * 将全局存量门禁转为**单次提交增量门禁（Ratchet / Delta Gate）**：PR 规则为“单次 PR 禁止在顶层新增超过 1 个 design-log；修改文档时严禁在未补充事实前直接归档”。
  * 废除总词数硬门禁，替换为结构完整性校验器：限制单篇 design-log 词数（如 ≤ 2000 词），必须包含固定的问题、决策、落地点三段结构，禁止直接粘帖未经提炼的原始终端输出。

#### 3. 定时任务引入非确定性外部 LLM 破坏状态裁决权威
* **证据**：
  * R4：“每周一次（或 design-log 顶层新增满 20 个）由 CI cron 跑 `tools/digest_logs.py`：用 MiniMax（CI 已有 key）读新日志，产出 STATE.md 草案与归档移动，以 PR 提交，人合并——模型只起草，不裁决。”
* **攻击路径**：
  * **幻觉渗透核心裁决树**：Design-log 是探索性记录，充斥着被推翻的猜想与失败的实验。LLM 无法百分之百区分“探讨过的备选方案”与“已敲定的架构决策”。当模型把推测性假设写入 `STATE.md` 草案并伴随几十个文件的移动时，评审人面临严重的审查疲劳（Review Fatigue），极易出现闭眼合并，使未经验证的假说升格为“活文档唯一裁决”。
  * **外部脆性阻断工程流水线**：CI cron 依赖外部第三方 API。API 限流、超时、Token 额度耗尽或输出格式解析失败，均会导致归档任务中断，继而引发“顶层文件 > 30”规则红灯，造成持续集成主干瘫痪。
* **修正**：
  * 剥离 LLM 对文件状态和生命周期的裁决权。物理归档必须由开发者在落地该日志事实时显式发起（作为代码/账本 PR 的联动变更）。
  * 限制模型生成物的作用域：`tools/digest_logs.py` 的产物仅允许写入无裁决效力的周报参考目录 `docs/digest/YYYY-WW.md`，严禁直接对具备唯一裁决权的 `STATE.md` 发起覆盖性 PR。

#### 4. 手写/生成混合 HTML 的逐字节 diff 门禁缺乏工程稳健性
* **证据**：
  * R2：“HTML 里用 `<!-- generated:begin name -->` / `<!-- generated:end -->` 标记生成区块，其余手写区块保留。门禁：CI 重新生成后与仓库 HTML 逐字节 diff，非空即红。”
* **攻击路径**：
  * 逐字节（byte-level）对比是脆弱的“伪深模块”。由于各操作系统换行符差异（CRLF/LF）、不同环境 Python 解析库对 HTML 属性序列化顺序的非确定性，哪怕语义完全一致，也会持续触发 CI 假红。
  * 一旦手写区块包含未闭合标签或损坏的结构，生成器解析与正则替换将引发区块吞噬与内容截断；且 CI 仅校验“代码与文件是否一致”，无法校验“生成的 HTML 是否符合语法”。
* **修正**：
  * 彻底放弃在手写 HTML 中打洞注入的方案。活文档源文件全面采用 Markdown。
  * 若必须保留渲染，门禁必须比对 AST 语义（如解析为 DOM 树对比节点文本与属性字典），或在 diff 之前强制通过统一版本的代码格式化器（如 prettier）标准化，消除空白与换行漂移。

### 【建议】

#### 1. 存量脚本清理账目不对账
* **证据**：
  * R1：“今天 16 个脚本的处置：工具化 4 个... 死在 scratchpad 8 个...”。
* **攻击路径**：
  $4 + 8 = 12$。剩余 4 个脚本去向不明，在基线迁移首日即制造账实不符，可能导致部分探针中的事实隐性灭失。
* **修正**：
  补齐完整的 16 个脚本迁移矩阵，对未列出的 4 个脚本逐一明确打上“工具化”、“废弃”或“沉淀进 src”的单向流转标记。

#### 2. “跑第二次即必须工具化”属不可验证的道德条款
* **证据**：
  * R1：“scratchpad 探针允许存在但不入库；**跑第二次即必须工具化**。”
* **攻击路径**：
  本地离线运行次数无法由 CI 捕获。该规则无法机械执行，直接违背原则 0“无门禁的规则不算规则”，会导致开发者常驻本地重型脚本而不受任何约束。
* **修正**：
  将门禁前移至 PR 准入界限：不限制本地运行次数，但规定任何入库的事实（数据表、收据、账本条目），其提交 PR 中必须包含可在独立沙箱通过一键命令复现结果的 `tools/` 入口；无法复现的结论视为无效。

#### 3. 形状账本缺少良性形状在读取层的断言机制
* **证据**：
  * R3：“扩展为全部形状的登记（含良性形状）... `read_layer_action(patch|gap|none)`。”
* **攻击路径**：
  登记了良性形状（如 `action=none`），但未在读取层建立反向守卫。后续开发者若误将良性形状识别为 defect 并错误应用 patch，系统门禁将对此毫无反应。
* **修正**：
  在 `src/tests/read_layer/` 建立与账本联动的自动化表驱动测试：凡登记为 `none` 的形状，其测试用例必须断言读取层透传原格式；登记为 `patch` 的必须断言修复契约。

---

裁决：不得合并
