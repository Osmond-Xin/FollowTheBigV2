该设计简报表面上形式化严密，但核心缝（Seam）发生严重越界：在单 Stream 读取链路中强行嵌入跨 Stream 隐式扫描、多日读取输出维度坍塌（丢失日期主键导致时间序列不可用）、且计划级补丁破坏了按天缺陷隔离，无法作为生产级接口落地。

---

### 【致命】

#### 1. 跨 Stream 缺口归因破坏单 Stream 读取的 IO 隔离与纯计划契约
* **证据**：
  * `types.py:ReadRequest.stream: Stream`（单次请求严格限定单个 Stream）
  * `types.py:GapReason.STREAM_PARTIAL`（定义为「该标的在别的 stream 有、在这个没有」）
  * `test_store.py:test_execute_gap_stream_partial_on_rescue_day`：
    `read(RawStore(root, ledger), ledger, days=(DAY_RESCUE,), fields=("oid",), symbols=frozenset({"000002.SZ"}))` 仅针对 `orders` 发起读取，却断言返回 `GapReason.STREAM_PARTIAL`。
* **攻击路径**：
  `ScanPlan` 仅声明了 `orders` 物理文件的投影与扫描范围。`RawStore.execute(plan)` 接收单 Stream 计划执行。若要在此处判定 `000002.SZ` 是否在 `trades` 或 `xinqing` 中存在，`execute` 必须脱离 `ScanPlan` 的管辖，在底层私自对同级其他 Stream 目录发起未声明的隐式 IO 扫描。当 sister stream 尚未就绪、目录受限或处于分布式读取时，该调用将直接崩溃；同时彻底击穿了「`ScanPlan` 是 IO 意图与执行的完整事实」这一架构不变量。
* **修正**：
  剥离 `RawStore.execute` 的跨 Stream 归因能力。单 Stream 存储算子层只产出物理事实 `DAY_MISSING` 与 `SYMBOL_ABSENT`。多 Stream 救援日的对齐与 `STREAM_PARTIAL` 语义升级，上移至多 Stream 对齐层（Alignment / Dataset Engine）或基于 `manifest` 摘要判定，严禁底层单 Stream IO 算子越权扫描无关目录。

#### 2. 多日批量读取时输出 DataFrame 丢失日期主键（维度坍塌）
* **证据**：
  * `types.py:ReadRequest.days: tuple[Day, ...]`（接口支持多日批读）
  * `schema.py:FIELDS` 中全部 Stream 均未映射日期物理列（`column_3` 仅作为 `raw:` 未注册旁路存在）
  * `types.py:ReadResult.frame: pl.DataFrame`（列严格等于 `plan.output_fields`，首列为 `symbol`，无 `date` 列）
  * `schema.py:Kind` 中 `time_ms` 的定义为「自午夜起毫秒 Int64」。
* **攻击路径**：
  调用方传入多天（如 `days=(2022-01-04, 2022-01-05)`），`execute` 将各天数据垂直拼接（`pl.concat`）。由于没有 `date` 列，且 `time_ms` 每天都从 `09:30:00 (34,200,000 ms)` 重新归零计数，拼接后的 DataFrame 中 Day 1 下午与 Day 2 上午的数据在时间维度上完全重叠且无法区分。下游做跨日排序、时序切窗或截面计算时数据完全错乱。
* **修正**：
  在 `schema.py` 中为各 Stream 显式注册 `date` 字段（物理映射 `column_3`，Kind 为 `date`），并在 `ReadResult.frame` 中作为系统级保留主键（与 `symbol` 一同固定在最前列）；若坚持存储层单日纯粹性，则收紧 `ReadRequest.day: Day` 为单日标量，将多日合并责任显式移交给上层 Dataset 聚合器。

#### 3. `ScanPlan` 级全局补丁导致多日扫描时的缺陷隔离击穿
* **证据**：
  * `types.py:ScanPlan.patches: tuple[str, ...]`（挂在整个计划根节点上）
  * `types.py:FilePlan` 仅有 `path, day, row_groups, columns`，无 `patches` 字段。
* **攻击路径**：
  当 `ReadRequest.days` 跨越正常交易日（如 `2022-01-04`）与账本登记了 `time_6digit` 的缺陷交易日（如 `2024-02-06`）时，`plan()` 计算出的 `ScanPlan.patches` 包含 `"time_6digit"`。`execute` 执行该计划时，对全量文件启用宽松时间解析（`allow_6digit=True`），导致正常交易日中原本未登记、理应硬失败（Fail-loud）的脏数据被静默吞掉，账本「未登记形状硬失败」的核心约束被一次多日请求彻底穿透。
* **修正**：
  将 `patches` 从 `ScanPlan` 根节点下移至 `FilePlan`（每个文件携带自己独立的 `patches: tuple[str, ...]`）。`execute` 在遍历执行单个文件时，仅针对该文件的 `FilePlan.patches` 应用解码规则与异常校验。

### 【严重】

#### 4. `ReadStats` 无法在纯计划执行中闭环（元数据丢失与二次 IO）
* **证据**：
  * `store.py:RawStore.catalog(stream, days)` 读取 Footer 产生 `FileMeta.row_groups`（包含 `byte_size`）
  * `plan.py:plan(request, catalog, ledger)` 产出 `ScanPlan`，其 `FilePlan` 仅保留 `row_groups: tuple[int, ...] | None`，丢弃了 `RowGroupMeta`
  * `store.py:RawStore.execute(plan: ScanPlan) -> ReadResult`（入参仅有 `ScanPlan`，且 docstring 声称 `stats.bytes_read 来自 footer 元数据，不是估算`）。
* **攻击路径**：
  `execute` 只接收 `ScanPlan`。由于 `FilePlan` 中已无各 Row Group 的压缩字节数，`execute` 要么必须违背「passes == 1」的承诺在执行期重新解析一次 Parquet Footer，要么必须靠估算（违背不变量）。
* **修正**：
  在 `FilePlan` 中保留 `selected_row_groups: tuple[RowGroupMeta, ...] | None`，或由 `plan()` 纯函数直接在 `ScanPlan` 中算好 `planned_stats: ReadStats`，`execute` 仅负责回填实际读到的 `rows`。

#### 5. 未登记六位时间硬失败与列剪裁（Column Pruning）存在实现死锁
* **证据**：
  * `store.py:RawStore` 不变量声明：「未登记形状硬失败：账本未登记 time_6digit 的天出现六位时间 ⇒ RuntimeError」
  * `test_plan.py:test_plan_projection_minimal_and_expanded_for_filters`：仅请求 `("price", "vol")` 时，投影列为 `{"_symbol", "column_9", "column_10"}`，不包含 `column_4`（时间列）。
* **攻击路径**：
  当查询未请求 `time_ms` 且无 `windows` 过滤时，`plan()` 进行了严格的列剪裁，底层 Parquet 根本不加载 `column_4`。此时 `execute` 无法察觉数据中是否存在未登记的六位时间。若 `execute` 强行加载 `column_4` 做全量扫描，则 338× 字节剪裁性能契约破产；若跳过检查，则「未登记形状硬失败」沦为仅在请求时间列时才生效的偶发逻辑。
* **修正**：
  严格厘清职责边界：读取层（`RawStore.execute`）仅对**本次查询实际投影/参与计算的列**执行解码与未登记形状拦截；全局数据完整性与全字段缺陷校验属于摄取层（`ingest`）和离线校验工具的职责，不转嫁为查询期隐藏 IO 负担。

#### 6. `days(quality)` 与 `quality(day)` 存在缺失 Manifest 时的语义冲突
* **证据**：
  * `store.py:RawStore.days(quality: Quality | None = None)`：「quality 给定时按 manifest 过滤」
  * `store.py:RawStore.quality(day: Day) -> Quality`：「manifest 里没有记录 ⇒ UNVERIFIED，不是异常」
  * `test_store.py:test_days_requires_all_three_streams_and_sorts`：3 个 stream parquet 齐全但无 manifest 的天，`days()` 返回该天。
* **攻击路径**：
  若存在 100 天历史数据（parquet 完整但无 V2 manifest）：`store.quality(day)` 对其中任一天均返回 `Quality.UNVERIFIED`；但调用 `store.days(quality=Quality.UNVERIFIED)` 时，因其按 manifest 过滤，这 100 天被全部丢弃并返回空元组，造成 `day in store.days(store.quality(day))` 恒为 False 的自相矛盾。
* **修正**：
  规范化 Manifest 缺失时的回退规则：`days(quality=Quality.UNVERIFIED)` 必须包含「无 manifest 但 3 个 stream 文件齐全」的交易日，保证集合过滤与单日查询的语义对称。

#### 7. `raw:` 旁路缺乏生产环境防护机制（非法逃生口）
* **证据**：
  * `schema.py:RAW_PREFIX = "raw:"`
  * `schema.py:field()` 遇到 `raw:` 无条件生成 `Field(name, name[4:], "str")`
  * docstring 注释要求：「不得在因子里使用（未登记的形状硬失败是原始层存储的不变量，旁路只给人看）」。
* **攻击路径**：
  代码中无任何环境约束或调试守卫。研究人员可在因子逻辑中直接传入 `ReadRequest(..., fields=("raw:column_13",))` 提取未登记列。这绕过了 Schema 显式注册与 `DefectLedger` 审查，导致未经洗净的脏字符串渗透入核心计算链路。
* **修正**：
  移除 `ReadRequest` 对 `raw:` 列的隐式支持；或将 `raw:` 旁路收敛为独立的调试专用方法（如 `RawStore.inspect_raw(...)`），在常规 `execute(plan)` 路径中遇到 `raw:` 字段直接抛出 `PermissionError` 或 `KeyError`。

### 【建议】

#### 8. `ScanPlan` 混入执行器配置旋钮（深度错位）
* **证据**：`types.py:ScanPlan` 中包含 `passes: int = 1`, `pre_buffer: bool = True`, `engine: str = "pyarrow"`。
* **攻击路径**：
  `ScanPlan` 是纯函数 `plan()` 输出的数据结构，而 `engine`、`pre_buffer` 是底层 IO 执行器（`RawStore`）的内部固定策略。将其作为带默认值的字段挂在 `ScanPlan` 上，不仅泄露了实现细节，还提供了无效的伪配置项（`RawStore` 内部实则写死 pyarrow）。
* **修正**：
  将 `engine`、`pre_buffer` 移出 `ScanPlan`，下沉为 `RawStore` 内部的不变私有常量；CI 验证性能特征应通过测试中的实际 IO 耗时与 Profile 进行断言，而非断言 Plan 数据类上的字段值。

#### 9. `IngestReceipt` 与 CSV 独立行数校验对末尾空行脆弱
* **证据**：`ingest.py:StreamReceipt.n_rows_csv`（「独立计数：CSV 字节流里的换行数减表头，不是从 parquet 反推」）。
* **攻击路径**：
  真实行情 CSV 末尾常带有无数据的空换行（`\r\n`）。按字节换行符计数的 `n_rows_csv` 会产生 $N+1$ 行，而标准 CSV 解析与 Parquet 写入会自动忽略末尾空行产出 $N$ 行，导致 `n_rows_csv != n_rows_parquet`，触发误判并中断合法摄取。
* **修正**：
  在独立行数计数逻辑中明确剔除文件末尾连续空换行符，并在 `test_ingest.py` 中补充末尾带冗余换行符的容错测试用例。

#### 10. `DefectLedger` 解析缺少 Stream 枚举校验
* **证据**：`ledger.py:parse_ledger` 中直接使用 `row.get("stream")`。
* **攻击路径**：
  若在 `defects.toml` 中将 `stream = "orders"` 误拼为 `stream = "order"`，`parse_ledger` 静默接受；运行时 `d.stream == stream` 永远无法匹配，导致针对特定 stream 的缺陷补丁静默失效。
* **修正**：
  在 `parse_ledger` 中加入强校验：若 `stream is not None`，必须断言 `stream in STREAMS`，否则抛出 `ValueError`。
