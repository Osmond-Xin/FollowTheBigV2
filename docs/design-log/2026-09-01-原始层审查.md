# 原始层（preserve）正确性审查

> 过程文档。相应校验实现为 V2 摄取层的代码与断言后归档。
> 审查对象：V1 的 7z → CSV → `data/preserve/{orders,trades,xinqing}` 这一条链。

## 结论：**(B) 大体可信，但有已知污染区间，必须标注**

**一句话：preserve 的「转录」是可信的；preserve 的「验收」是不可信的。缺陷不在数据，在证明。**

## 一、转录本身经得起检验（实测证据）

- **行数 36/36 精确相符**。从 7z 直接 `wc -l` 拿到 CSV 行数减表头，对 6 只标的 × 3 stream × 2 个年份
  逐一比对 preserve，零偏差。
- **5 个完整文件逐字节 round-trip 相同**（把 preserve 行重拼回 CSV 字段用 latin-1 逐行比对）：
  `orders/trades/xinqing 603999.SH 20260803`、`trades 600000.SH 20220104`、`orders 000021.SZ 20220104`
  —— 全部 IDENTICAL，连 SH 那 5300 万行的 `\x00` 都原样保留。
- **列映射经真 GBK 表头逐字段确认全部正确**，且 2022 与 2026 表头完全一致（schema 跨度内未漂移）。
  `OB_TIME=c4` / `OB_ASK_PX=c18..27` / `OB_BID_PX=c38..47` / `TRADE_CODE=c6` / `TRADE_BS=c8` /
  `ORDER_OID=c6` / `ORDER_TYPE=c7` … 逐条对上真表头。
- **十档单调性 + 量价共存**，跨 2022/2023/2025/2026 四天约 5000 万行，**零违例**。
- **1122 天 = 完整交易日历，零缺失**；三 stream 天数完全对齐；19 处 >4 天的缺口全部核对为法定假期。
- **行序 = 原始序**，在 1.2 亿行上实证：每标的行完全连续（n_runs = n_unique = 3188）、
  时间与成交编号单调不减。逐笔的顺序信息被完整保留。
- **`_i64` 的空值/哨兵处理正确**：`''`→None、`' '`→None、`'\x00'`→None、
  UINT64 哨兵 `18446744073709551615`→None、科学计数法 `1.2018e+006`→1201800。**不存在 `""→0`。**
- **价格量纲有外部锚点**：20220104 连续竞价 ask1 最大值 = ¥2068.59，与当日贵州茅台盘中价相符。
  `PRICE_SCALE = 10000` 确认无误。
- **`utf8-lossy` 未造成损坏**：表头是 GBK 中文但被 `skip_rows=1` 丢弃；数据行是纯 ASCII；
  三个 stream 里根本没有「证券简称」这类中文值列。四个年份采样扫 U+FFFD 替换字符，**命中 0**。
- **无静默列截断**：针对 `truncate_ragged_lines=True` 的最阴险失效（首行字段偏少 → 推断列宽 →
  静默截掉后续所有行尾部字段），逐标的检查末列是否全空，**六天（含两个残缺日）全部 0 命中**。

## 二、验收机制不可信（这才是问题）

1. **链上唯一的行数校验是同义反复。** `s0_c:131` 的 `n_rows_csv_total` 与 `:142` 的 `n_rows_parquet`
   同源，**必然相等**。所以 manifest 里那 3360 个 `row_count_match=True` **不是证据**。
   `ignore_errors=True` + `truncate_ragged_lines=True` 若吞掉行或截掉列，它照样是 True。
2. **承诺的 round-trip diff 从未实现。** docstring 写「抽样 10 行 round-trip diff」，
   实现是 `s0_c:191` 的 `csv_first10.height == parq_back.height` —— 即 `10 == 10`。
3. **`sha256_first_1mb` 语义在两条路径下不同**（一条读整个文件、一条只读前 1MB），
   且**全仓没有任何脚本读回 manifest 校验这些哈希**。manifest 是纯写入端遥测。
4. **`self_check` 是死代码**：全仓 grep 只有定义那一行，**零调用点**。且校验面极窄
   （只取 ask1/ask2/bid1/bid2 四列）。
5. **行数不符不阻塞**：`s0_c:146-151` 只 print 就继续写 parquet 和 manifest。
6. **非原子写 + 幂等判据错位**：`j1_daily.sh:57` 只看 `trades` 文件在不在；
   而 `write_parquet`/`sink_parquet` 是非原子直写（只有 rescue 路径用了 tmp+`os.replace`）。
   ⇒ 若在写 orders 或 xinqing 时被 kill（该项目因 kernel panic 被 kill 过多次），
   **trades 已存在 → 此后永远跳过这一天，残缺文件永久留存且无人知晓。**

## 三、必须标注的四类边界

| 边界 | 区间 | 性质 |
|---|---|---|
| **宇宙裁剪：无 300/301（创业板）、688/689（科创板）、ETF、B 股** | 2023-01 → 2026-07 | **永久不可逆**（源 7z 已删）|
| 厂商 `成交编号`(c5) 缺陷：7 天整列全空 + 10 天稀疏重复键 | 见 F61 | 数据在，需 seq_mode 兜底 |
| **混单位时间戳（6 位 HHMMSS）** | 已确认 20240206/08，**范围未知** | **解析原语未修，会静默吞掉整所数据** |
| 结构性残缺日（7z Data Error 救援入库）| 20260805, 20260811 | 按 F138 设计，不在 manifest |

### 宇宙裁剪的规模（实测单日 7z）

| | 7z 内 | 进 preserve |
|---|---|---|
| 000/001/002/003 + 600/601/603/605 | 3188 | **3188 ✅** |
| **300 / 301（创业板）** | **1396** | **0 ❌** |
| **688 / 689（科创板）** | **612** | **0 ❌** |
| ETF/基金/债 | ~2000 | 0 |
| B 股（900/200）| 77 | 0 |

来源：`utils/constants.py:32` 的 `MAIN_PREFIXES`。这是 `doc/design/02` 明写的设计决策，不是 bug，
但**后果是 2023-01→2026-07 的创业板/科创板逐笔数据已随 7z 一起永久消失**。
**唯一还能拿回它们的窗口 = 幸存的 2022 全年 242 天 + 202608 的 14 天（共 256 天 / 685 GB 7z）。**

### 混单位时间戳的杀伤机制（最危险的一条）

20240206 / 20240208 的 preserve 里同一文件混着 6 位与 9 位时间（`t_min=84500`、`t_max=150000000`）。
这是厂商格式漂移（F62），preserve 忠实保留原样是对的，但**共享解析原语至今没有归一化**：

- `_cont_session_mask`：`84500 < 93000000` ⇒ 那天**所有 SH 行被静默剔除**，连续竞价段变成 SZ-only，**不报错**。
- `_hhmmssmmm_to_ms(84500)` → `h=0, mn=0, s=84, ms=500` ⇒ 垃圾值。
- `self_check(20240206)` 因此返回全 0 —— **假绿灯**（没数据可违例）。

F62 的修法只补在了 `daily.py`，**没有回流到 `preserve_schema.py`**，而后者被 **56 个文件**引用。
**全语料 `column_4` 格式扫描在外置盘上跑 40 分钟未完成 ⇒ 中招天数至今未知。**

## 四、其它必须登记的事实

- **SH 逐笔成交的 `column_6`/`column_7` 是 NUL 字节 `'\x00'`**，20260803 全天 SH 侧 **53,541,722 行**
  都是这个值。**它不是 null，不是空串**——下游写 `.is_null()` 或 `== ""` 在 SH 上会全假。
  （`_i64` 转成 null，所以数值路径无害；字符串路径有害。）
- **`SIDE_UNKNOWN = "U"` 在 trades 里根本不存在**；SZ 撤单行的 BS 标志是**空格 `' '`**（1873 万行/天）。
  任何 `== SIDE_UNKNOWN` 的过滤静默命中 0 行。
- **SH `ORDER_TYPE` 漏登记 `'S'`**（产品状态订单，6784 行/天，price=0 vol=0）。下游普遍用**否定式**
  判 add（`!= 'D'`），**幸好**同时 AND 了 side ∈ {B,S} 且 price>0 才意外挡住。
  `window_state_sh.py:97` 的肯定式 `== SH_ADD` 是唯一天然正确的写法。**又一处「靠巧合正确」。**
- **两个 rescue 日的 stream 成员数不对称**：20260805 orders 3138 / trades 3139（差 1）；
  20260811 orders 3180 / trades 3177（差 3）。⇒ **任何 orders⋈trades 的组件在这两天会遇到单边缺失的标的。**
  现有的 F48 守卫是**天级**的，必须改成**标的级**。
- **F61 事实库与数据不符**：20240208 的 `column_5` 空值率实测 **47.8%（单所）**，
  不是事实库写的「SZ+SH 两所都空」。
- **未登记的列**：`column_5`（委托编号）、trades `column_7`、xinqing `column_58..67`。
- **编码层在事实库中完全空白**：`GBK`/`utf8`/`lossy` 在 `ESTABLISHED-FACTS.md` 全文命中数为 **0**。

## 五、V2 接管前必须先做的验证（P0）

1. **补做真行数校验**：对唯一可验窗口（2022 全年 242 天 + 202608 的 14 天 = 256 天）全量跑
   `7zz e -so → wc -l` 对 preserve 每标的行数。若 256/256 全过，可外推到 866 个不可验天的
   **过程可信度**（不是数据可信度）。
2. **逐字节 round-trip 抽样扩到有统计意义的规模**（建议每月随机 20 只标的 × 3 stream，覆盖 256 个可验天）。
   这是唯一能同时证伪「编码损坏 / 列截断 / 行丢失 / 顺序错乱」的单一测试。
3. **跑完全语料 `column_4` 格式扫描**（1122 天 × 3 stream，取字符串长度 min/max，登记所有 ≠9 的天）。
   **在此之前，任何走 `_cont_session_mask` 的 V2 组件都可能在未知天数上静默丢掉整个交易所。**
   建议用本地盘或分月并行跑完。
4. **修两个解析原语**：把 F62 的按文件时间归一化（`max(t)<1e6 → ×1000`，混单位 fail-loud）
   落进 `_hhmmssmmm_to_ms` 与 `_cont_session_mask`。**fan-in = 56，全项目杠杆最高的单点修复。**
5. **对 866 个不可验天做内部一致性全扫**：全十档 + 量列 + SH/SZ 分别统计 + 时间格式 +
   `column_5` 空值率 + 每所标的数，落成可查询的 QC 表。任何一天某所标的数为 0 / 十档违例 > 0 /
   时间长度异常，必须标红。

## 六、P1 / P2

**P1**：`self_check` 从死代码变成 CI 闸（**先修假绿灯再挂**）并扩到全十档 + trades/orders + 分所；
补齐 20260805/20260811 的 manifest 行并加 `partial` / `rescue_path` / `seq_mode` 三列；
preserve 写入改原子（tmp+`os.replace`），幂等判据从「trades 文件存在」改为「manifest 三 stream 齐全」；
补齐 schema 文档缺口（SH `'S'`、`SIDE_UNKNOWN` 实为 `' '`、`\x00` 事实、未登记列）；
否定式 add 判据全改肯定式；事实库补一条编码事实；更正 F61 的 20240208 条目。

**P2**：**决定是否用幸存的 2022 + 202608 的 7z 重抽扩展宇宙（300/301/688）。这是唯一窗口。**
给 V2 建立「数据可验证性」标签：每天打上 `source_7z_available` / `verified_byte_exact` /
`known_vendor_defect`，使任何结论都能回答「它依赖的天里有多少是真验过的」。
